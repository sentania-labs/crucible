# S14: Can Crucible observe current subscription quota state per harness, and use it for routing and for a wait-and-resume strategy?

Run 2026-09-17, 10:25 to 10:28 CDT, on the reference workstation, against
`quota-axi` 0.1.46 installed into a scratch prefix (never globally) and
pointed at Crucible's dedicated credential directories as they stand on
this host, one per harness under a single private root
(spec 12's `credentials.<harness>.path`; `<CRED_ROOT>` below). No task was
run and no model was called; this spike
reads quota state only. Every captured line below is redacted: account
identifiers, emails, tokens, and paths outside the dedicated root are
replaced with placeholders, and no credential value was recorded anywhere.

Decision: **adopt with conditions.** quota-axi answers the question for two
of the three harnesses today, from the dedicated directories only, without
spending provider quota and without touching the operator's daily-use
state, and it degrades honestly to "unknown" rather than to a fabricated
number. The conditions are that Crucible pins it by version and by resolved
dependency tree, treats every reading as an advisory observation that can
be absent or stale, and never lets a missing or stale reading block a
launch. Claude Code is the gap: Crucible's dedicated Claude credential is a
`setup-token` long-lived token (S1b), and Anthropic's usage endpoint refuses
it (403), so Claude Code has no reading at all. A wait-and-resume strategy
is supportable for Codex and AGY, where a real reset timestamp exists, and
not supportable for Claude Code.

## Isolation from the operator's daily-use directories

This was the blocking constraint, and it holds, with one mode caveat.

The `--profile-only` mode exists for exactly this problem. It takes one
`--provider`, supports Claude and Codex only, requires an explicit non-blank
`CLAUDE_CONFIG_DIR` or `CODEX_HOME`, and has **no default-location
fallback**: it reads only `$CLAUDE_CONFIG_DIR/.credentials.json` or
`$CODEX_HOME/auth.json`, never a keychain, never another CLI's store, never
a CLI RPC fallback, never a delegated credential refresh, and it neither
reads nor writes its own quota cache. AGY has no `--profile-only`; it is
isolated by `HOME` instead, which is the same lever S1b used for AGY's
dedicated login.

Every run in this spike used `env -i` with `HOME` and all four XDG roots
pointed into a scratch tree, so any default-location lookup would land in
the scratch tree rather than in the operator's home.

Evidence, three independent kinds:

1. **Its own source reporting.** `quota-axi auth --json`, run scoped, named
   every path it would consult. Nothing outside the dedicated root or the
   scratch tree appears:

   ```json
   { "provider": "codex", "sources": [
       { "source": "auth-json", "path": "<CRED_ROOT>/codex/auth.json", "status": "available" },
       { "source": "pi:openai-codex", "path": "<SCRATCH>/qhome/.pi/agent/auth.json", "status": "missing" },
       { "source": "cli-rpc", "path": "<node-bin-dir>/codex", "status": "available" } ] }
   { "provider": "claude", "sources": [
       { "source": "env", "status": "available" },
       { "source": "oauth-file", "path": "<CRED_ROOT>/claude_code/.credentials.json", "status": "missing" } ] }
   { "provider": "agy", "sources": [
       { "source": "loopback", "status": "missing" } ] }
   ```

2. **A negative that only isolation explains.** The dedicated Claude
   directory holds `oauth-token` and `.claude.json`, not a
   `.credentials.json`. Pointed at it, quota-axi reported
   `credentials_missing` and exited 1. The operator's own
   `~/.claude/.credentials.json` exists and is valid; had any fallback been
   taken, the run would have reported a percentage instead. Its `--full`
   attempt list says the same thing per source:

   ```json
   [ { "source": "oauth-file", "status": "skipped", "error": "credentials_missing" },
     { "source": "env",        "status": "failed",  "error": "Claude quota unavailable (403)" } ]
   ```

3. **A filesystem watch with a positive control.** A read-only `inotifywait`
   watch was placed on `~/.codex/auth.json`,
   `~/.gemini/antigravity-cli/antigravity-oauth-token`, and
   `~/.cache/quota-axi/`. Nine quota-axi invocations (three per harness) ran
   between 10:27:38 and 10:27:46 CDT and produced **zero** open or access
   events on any of them. A deliberate read of the same three files at
   10:27:47 CDT fired all six expected events, proving the watch was live.

Two honest caveats on this evidence. First, `~/.claude/.credentials.json`
could not be watched usefully: the session running this spike is itself
Claude Code on the operator's own credential and touches that file about
once a second, so its events are indistinguishable background noise. Point
2 above is what carries Claude Code, and it is the stronger evidence.
Second, access-time comparison was abandoned as self-contaminating: the
fingerprint script's own `sha256sum` updates the access times it is meant
to measure. No operator file's size, modification time, or content hash
changed across the whole spike.

The mode caveat, which is a design constraint rather than a finding:
`--profile-only` accepts exactly one provider, so a single combined call
covering all three harnesses cannot use it. One combined call was run to
measure it (1.9 s for all three), and it stayed inside the dedicated
directories only because `HOME` was scoped too. Crucible should make three
separate scoped calls, not one, so that Claude and Codex keep the mode whose
guarantee is written down.

The four windows come back with headroom and a reset, but Antigravity's
snapshot carries no cycle history, so pace, runway, and spend priority are
all `unknown` and the tool says so in `attention[]` rather than guessing.
Note also that the `claude_gpt_5h` reset moved between consecutive calls
(15:26:58, then 15:27:54, then 15:28:07 CDT, each exactly five hours after
the call that produced it): on a wholly unused window that
timestamp is "now plus the window length", not a clock that is already
running. Crucible must not read a reset on a 100 percent window as an event
that will happen.

Without the `agy` binary on `PATH` and with no Antigravity process running,
the same call degrades to `stale` with `headroom_unknown` per scope and no
`quota[]` rows at all. It never invents a number.

### Claude Code

Three attempts, all against the dedicated directory:

| Attempt | Result |
|---|---|
| `--profile-only`, no environment token | exit 1, `state.status: unavailable`, `error: Claude profile credentials missing`. The dedicated directory has no `.credentials.json`. |
| `--profile-only`, with `CLAUDE_CODE_OAUTH_TOKEN` set from the dedicated `oauth-token` file | identical: profile-only reads the file and nothing else, so the environment token is ignored by design |
| default mode, with `CLAUDE_CODE_OAUTH_TOKEN` set from that file, `CLAUDE_CONFIG_DIR` at the dedicated directory | exit 1, `state.status: error`, `error: Claude quota unavailable (403)`; default TOON renders it as `attention[1]: claude,all,error,Claude quota unavailable (403),none` |

| Field | Value |
|---|---|
| percent remaining, window, runway, runway seconds, projected exhaustion, reset, confidence, spend priority | all absent |
| what is reported instead | one `attention[]` row naming the provider, the scope `all`, kind `error`, and the 403 |

The cause is the credential shape, not the tool. S1b established that
Crucible's dedicated Claude Code session is a `setup-token` long-lived
token held in a file and delivered through the CLI's environment variable,
which spec 07 already names as the one exception to file-only delivery.
Anthropic's usage endpoint answers that token with 403. quota-axi treats
403 as insufficient evidence of a sign-out, by its own documented rule, and
reports an error rather than claiming the credential is dead. Whether a
`.credentials.json`-shaped OAuth session would be readable was **not
tested**: the only such file on this host is the operator's own, and reading
it is exactly what this spike is forbidden to do.

## Is a reset time actually available

| Harness | Reset available | Usable as a wait-and-resume deadline |
|---|---|---|
| codex | yes, per bounding window (`weekly`, 2026-09-19 10:57 CDT), plus an independent `projectedExhaustedAt` and `usableRunwaySeconds` | yes for the deferral horizon; **no** as a completion deadline |
| agy | yes, per window, plus the vendor's own human reset text; but the reset on a wholly unused window is "now plus the window length" and moves on every call | yes, only for a window that is actually drawn down |
| claude_code | no reading at all today | no |

firstmate's own rule is that a reset is never a deadline: its
`quota-array-dispatch` skill passes `through_reset` on the feasibility floor
precisely because the window reaches its refill without exhausting, and it
forbids comparing `resetsAt` against a completion horizon as though reset
were an exhaustion deadline. That rule is correct and Crucible should inherit
it. The right reading is the opposite direction: a reset says *when a
deferred attempt is worth trying again*, not *how long the current attempt
has*. For "how long do I have", the field is `usableRunwaySeconds` under
`projected_exhaustion`, which Codex supplies and AGY does not.

Where no reset is available, Crucible does not need one. The behaviour that
does not depend on a reset is: observe the exhausted state, mark the pool
ineligible, defer the attempt, and re-probe on the supervisor's existing
tick until the reading says otherwise. That is strictly better than today
(fail into the exhausted window, report `quota_exhausted`, wake Foundry) and
it costs no new mechanism. For Claude Code specifically, with no reading at
all, Crucible keeps exactly today's behaviour, which is the degradation path
the design needs anyway.

## Integration shape, if adopted

Nothing below is built. It is what adoption would look like against the
mechanisms that already exist.

- **Where.** In the `crucible` service only. The service holds the dedicated
  credential directories; workers never do (12), and a worker has no reason
  to know a pool's headroom. The reading is three scoped subprocess calls,
  one per harness, each with `env -i`, a scratch `HOME`, scratch XDG roots,
  and only that harness's own variable set: `CODEX_HOME` and
  `CLAUDE_CONFIG_DIR` with `--profile-only`, and `HOME` at the dedicated AGY
  directory for `agy`. Never one combined call.
- **How often.** On the reconcile tick, rate limited, not per launch. The
  measured cost is 0.5 s to 5 s per harness, and AGY's path launches the
  `agy` CLI, so a per-launch call would be both slow and a new failure mode
  in the launch path. firstmate's mid-task watcher polls at 60 s; a tick-rate
  observation is the same order and needs no daemon.
- **How it is stored.** As an observation row, never as authority: harness,
  pool, scope, `effectivePercentRemaining`, window identity, runway status,
  `usableRunwaySeconds`, `projectedExhaustedAt`, `resetsAt`, confidence,
  `spendPriority`, the tool's own `generatedAt`, the reading's local
  observation timestamp, and a source string carrying the tool name and
  version. Default `--json` and default TOON carry no account identity; only
  `--full` does, and Crucible must never run `--full`, because its `account`
  object holds `accountId` and `email` (confirmed in this spike, recorded
  here as field names only).
- **How routing uses it.** As a negative signal only, applied at the
  authoritative check at attempt launch, where 05b already reserves pool
  capacity in the fenced transaction that moves the attempt to `launching`.
  A pool whose most recent observation is `exhausted_now`, or zero percent
  remaining, becomes ineligible, and the launch is refused with the existing
  `quota_exhausted` class. Everything else, `unknown` included, stale
  included, absent included, is eligible. Missing data never blocks a launch;
  that is the rule that makes the dependency safe to remove.
- **How a deferred attempt resumes.** Through the existing deferral path, not
  a new one. 05b already defines `harness_launch_deferred` for a launch over
  the per-harness concurrency cap: it waits and records, and it is not a
  failure. A known-exhausted pool is the same shape, re-evaluated on each
  tick against the newest observation. The reset timestamp, where one exists,
  sets the earliest tick worth re-probing on; where none exists, the
  re-probe interval alone carries it. A deferral that outlives the contract's
  timeout ends as it does today.
- **What Foundry and the admin status see.** `GET /routing/usage` already
  reports per-pool usage and is where an observed headroom figure belongs,
  beside the counted one, clearly labelled as observed and carrying its
  own timestamp. The `harnesses[]` part of `GET /v1/admin/status` (25)
  already carries per-harness status; an observation age and a last-reading
  outcome fit there as additional fields. The wake contract needs nothing
  new: `quota_exhausted` is already a wake reason (17), and Foundry choosing
  another harness on that wake is already the documented response.

Spec changes adoption would need, listed rather than made:

1. **05b**, `RoutingPolicyV1` pools: a field for the observation source and
   for how stale a reading may be before it is ignored, plus the statement
   that an observation can only make a pool ineligible, never eligible.
2. **05b** validation: the new fields, and the rule that an absent or stale
   observation is not a policy error.
3. **25**: the observation fields on `harnesses[]`, and the statement that
   the reader runs in the service and never in a worker.
4. **13**: the pinning rule for a non-harness npm dependency in the
   credential path, which today's text covers only for images and harnesses.
5. **12**: an explicit entry for a third-party reader that opens the
   dedicated auth files, with the `--profile-only` and scoped-environment
   requirements written down as requirements rather than as this spike's
   method.
6. **16**: nothing changes in the failure table; `quota_exhausted` keeps its
   meaning and its default. Only the deferral, which is 05b's, is new.

## Risks

| Risk | Assessment |
|---|---|
| A third-party dependency in the credential path | Real and the largest one. quota-axi opens Crucible's dedicated auth files and sends the credential to the provider's own endpoint. Its documented posture is strong (never prints, logs, or caches a credential value; never mints, rotates, or exchanges one) and this spike saw no credential file change on any run. Crucible cannot verify that posture continuously. The mitigations are the `--profile-only` narrowing, one harness per call, the scoped environment, and that the reader runs where the credentials already are rather than widening anything. |
| An output contract we do not own | Real but evidenced. firstmate pinned a 0.1.29 floor and a jq validator asserting `schemaVersion: 5` in August; at 0.1.46, seventeen releases later, the schema version and the TOON headers are unchanged. That is a good track record, not a guarantee. Crucible should validate the same way: check the version floor, check `schemaVersion`, and discard a reading that does not parse rather than acting on a partial one. |
| Version drift | `axi-sdk-js` is a caret range (`^0.1.10`), and today's install resolved 0.1.12. The exact code in the credential path can therefore change without the quota-axi version changing. A version pin alone is not enough: the resolved tree must be pinned too, through a committed lockfile installed with `npm ci`, or by vendoring the resolved tree into the image at build time. |
| Supply chain and pinning under 13 and S11 | 13 requires declared pins, never "the newest", reproducible builds, and recorded digests; S11 requires self-update to be off. quota-axi fits that shape: pin `quota-axi@<version>` with its registry integrity hash recorded beside the image's other pinned inputs, install into the image at build time with a lockfile, never install it at runtime, never call its `update` command, and let Renovate propose a bump the same way it proposes a harness bump (ADR 0011), with a re-run of the isolation evidence in this spike as the promotion check. The 0.1.46 evaluated here was published about thirty minutes before the spike ran, which is itself an argument for a floor plus a deliberate pin rather than tracking `latest`. |
| The tool is absent or incompatible | Must degrade to today's behaviour. No reading means every pool stays eligible, routing proceeds as it does now, and an exhausted window is discovered the way it is discovered today: the harness reports it, the adapter classifies `quota_exhausted`, the task is `reported` with the class visible, and Foundry is woken. This is the condition that makes the dependency removable, and it should be an integration test, not a comment. |
| Codex's `cli-rpc` fallback | Outside `--profile-only`, quota-axi may fall back to launching the Codex CLI's read-only app-server probe, which also rewrites `auth.json`. With `--profile-only` it is disabled outright. This is a second reason the mode is not optional for Codex. |
| AGY's loopback fallback | When the `agy` CLI is unavailable, quota-axi discovers *already-running* Antigravity or `agy` processes and reads their loopback endpoints. On a workstation the operator's own session is such a process, so that fallback could report the operator's account rather than Crucible's. It did not fire in this spike (the CLI answered), and in the deployed shape the service has its own process space, but Crucible should treat an AGY reading whose source is `loopback` rather than the CLI as untrusted and discard it. |
| Claude Code has no reading | Not a risk of adopting, but a limit on the value. Two of three pools would be observed and one would not, which is exactly why "never block on missing data" has to be the rule rather than a nicety. |

## What was not done

- No task was run and no model was called, so no reading was validated
  against an actual exhausted launch. The Codex weekly window sat at 2
  percent with a projected exhaustion of 12:54 CDT today, which is a natural
  opportunity to observe `exhausted_now` on a later date, not something to
  force.
- Whether a `.credentials.json`-shaped Claude session is readable was not
  tested, because the only one on this host is the operator's.
- Behaviour under the egress proxy (S6) was not tested. quota-axi honours
  `HTTPS_PROXY` and `NO_PROXY`, and its endpoints are the providers' own, but
  the service's allowlist entries for the usage endpoints are not established
  here.
- No container run. Everything ran on the host as the operator's uid.
  A service-user run inside the deployed shape, with the credential
  directories at their configured paths, is the C3 repeat.
- The isolation evidence is a filesystem watch plus the tool's own
  provenance, not a syscall trace. `strace` is not installed, and
  unprivileged user namespaces are denied on this host, so neither `bwrap`
  nor `unshare -r` could provide a hard mount-namespace proof.
- Nothing was installed globally on the host, and the scratch install is
  outside the repository and is not committed.

## Recommendation

**Adopt with conditions**, as a proposed ADR (0014) for the operator's
decision, not as an accepted one.

Building a per-harness reader instead would mean owning three vendor usage
endpoints, three credential-store shapes, three window taxonomies, and the
projection maths, for a signal that is advisory by construction and that
Crucible must be able to run entirely without. quota-axi already does that
work, its `--profile-only` mode is built for exactly Crucible's isolation
constraint, its behaviour under missing data is to say "unknown" rather than
to guess, and firstmate has run it in production against the same three
provider families for months.

The conditions are:

1. Pin by version **and** by resolved dependency tree (lockfile plus
   recorded integrity hash), installed at image build, never at runtime,
   with `update` never invoked.
2. Validate every reading: version floor, `schemaVersion`, and full parse.
   A reading that does not validate is discarded, not partially used.
3. `--profile-only` for Claude and Codex, one harness per call, `env -i`
   with a scratch `HOME` and scratch XDG roots always, `--full` never.
4. Observation only. A reading can make a pool ineligible; it can never make
   one eligible, and its absence or staleness never blocks a launch.
5. An integration test that removes the binary and asserts that routing and
   launch behave exactly as they do today.
6. Re-run this spike's isolation evidence on every version bump, as the
   promotion check.
