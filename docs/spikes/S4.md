# S4: With harness sandboxes disabled, does the container hardening hold?

Run 2026-09-16, 14:04 CDT, rootful Docker 28.3.1 (seccomp builtin profile,
AppArmor docker-default, cgroupns), image
`crucible-worker:claude_code-2.1.273-5bb76fb777d0` (the probes are shell,
curl and git only; no model, no credential mounted). Worker shape from spec
08: `--user 1000:1000 --cap-drop ALL --security-opt no-new-privileges
--read-only`, tmpfs `/tmp` and `/home/worker`, checkout rw at
`/crucible/repo` with an `https://github.com/...` origin and no credential
helper, identity ro, report rw, attached only to an `internal: true` network
(`10.10.24.0/24`) with a CONNECT proxy (tinyproxy 1.11.1, S6) as the only
way out, `HTTPS_PROXY`/`HTTP_PROXY` set to it.

Decision: **proceed, partial.** Every attempt failed, but three of the
checks were made against an empty environment. This run mounted no
credential at all, and no PostgreSQL, no Compose control plane and no
socket proxy were running, so the other-credential, database and proxy
rows below prove only that nothing was reachable from the worker in that
empty environment, not that a real worker's wiring (one credential mounted
for its own harness, the other two present on the host, the control plane
up on the Compose network) keeps those targets out of reach. The process,
filesystem, network-route and git rows do not depend on that and stand.

Completion condition: the C3 re-run on the rootless daemon (the uid
mapping differs, S9 Test E), with the real control plane running
(`postgres`, `crucible`, the socket proxy and the egress proxy from
`compose.yaml`), a real credential mount for the worker's own harness, and
the other two credential directories present on the host, asserting that
the worker reaches none of them. One more note for C3: the egress
allowlist is the proxy's filter, not the network, so a discovery proxy
with no filter lets everything through (first row of the network table;
the filtered proxy refuses).

|---|---|---|
| `curl https://example.com/` through the proxy | `200` (expected: this proxy logs everything, S6) | refused: `http=000`, no `Established` line in the proxy log |
| `curl https://api.anthropic.com/` through the proxy | `404` (reached) | `404` (reached) |
| `curl https://github.com/` through the proxy | not run | refused: `http=000` |
| `curl --noproxy '*' https://example.com/` (bypass by name) | `Could not resolve host` (no external resolver on an internal network) | same |
| `curl --noproxy '*' https://23.192.228.80/` (bypass by IP) | `Failed to connect ... Couldn't connect to server` (no route) | same |

The internal network gives a worker no route and no resolver; the only
path out is the proxy, and the proxy's filter is the allowlist. A worker
that unsets `HTTPS_PROXY` gets nothing.
