# S7: Can harness versions be pinned and updated predictably in images?

Run 2026-09-16 (11:31 to 11:56 CDT, including the review fixes) on the reference workstation, Docker
28.3.1, buildx 0.25.0, BuildKit 0.32.2 in a docker-container builder.

Decision: **proceed, partial.** Same inputs produce the same image digest
for all three harnesses, after two fixes found by this spike and its review
(below). Every CLI reports the pinned version as uid 1000 on a read-only
root with no network, and each CLI's update path fails inside the image.
Partial because one version per harness was built; the "update to a second
version" half of the question is a pin change and a rebuild by the same
procedure, exercised the first time a new harness version is promoted.

## What was built

`images/build.sh` builds `images/<harness>/Dockerfile` with pins from
`images/pins.env`. Tag is `crucible-worker:<harness>-<version>-<build>`
where `<build>` is the first 12 hex digits of `crucible.build_inputs`, the
sha256 over `pins.env`, the Dockerfile, and `build.sh`.

| Harness | Version | Source of the binary | Verified by | Auto-update opt-out in the image |
|---|---|---|---|---|
| claude_code | 2.1.273 | `downloads.claude.ai/claude-code-releases/2.1.273/linux-x64/claude` (the native release, what `claude.ai/install.sh` fetches) | sha256 from that release's `manifest.json`; identical to the host's installed binary | `DISABLE_AUTOUPDATER=1` and `DISABLE_UPDATES=1`, both in the CLI's environment variable reference |
| codex | 0.153.4 | `github.com/openai/codex/releases/download/rust-v0.153.4/codex-x86_64-unknown-linux-musl.tar.gz` (static musl binary) | sha256 of the tarball as downloaded on 2026-09-16; extracted binary byte-identical to the host's install. Upstream publishes no plain checksum for this asset (`codex-package_SHA256SUMS` covers the npm tarballs only) and its `.sigstore` file is a cosign-format signature that `gh attestation verify` rejects; cosign is not on the workstation, so it was not verified | none exists as an environment variable. AGY is not on any package registry. `npm view agy` is an unrelated
placeholder package and `@google/gemini-cli` is a different product. The
installer at `https://antigravity.google/cli/install.sh` resolves "latest"
from a per-platform manifest on a Cloud Run endpoint and downloads from the
public GCS bucket above. The bucket path carries a build number, so a
specific version stays addressable after a newer one ships; the manifest
itself only ever names the latest, so taking a new pin means reading the
manifest on the day and recording the URL.

Neither Claude Code nor Codex needed Node in the image: both ship
standalone binaries at the pinned versions, so the images hold Debian
bookworm-slim, `git`, `curl`, `jq`, `ca-certificates`, the CLI, and a
`worker` user (uid 1000), nothing else. No `gh`, no `node`, no `npm`.
`ca-certificates` is not in spec 13's list but `curl` and every CLI need
it for TLS; the spec line should name it so the "nothing else" audit
stays exact. Setuid and setgid bits are stripped from every binary in the
image, so per-project images built `FROM` these inherit none.

The AGY manifest excerpt the pin was taken from, 2026-09-16 11:27 CDT:

```
{"version": "1.2.4",
 "url": "https://storage.googleapis.com/antigravity-public/antigravity-cli/1.2.4-6085322963025920/linux-x64/cli_linux_x64.tar.gz",
 "sha512": "5811d39ec1bf96a82ed06de6b8ee2bb7f5be8d74423b8c52b6b975e8f0e2c84c6cc2fa0baf902aad942c7566509c3ba6ddb5ef076260c6a635c4616e6ae17897"}
```

Reproducibility mechanics in `build.sh` and the Dockerfiles:

- base image by digest; apt reads `snapshot.debian.org` at
  `20260916T000000Z` with package versions pinned on top, so the package
  set is frozen even after the live mirror moves on;
- CLI binaries fetched with `ADD --checksum=sha256:...`;
- `SOURCE_DATE_EPOCH=1789516800` (2026-09-16 00:00:00 UTC, 2026-09-15
  19:00 CDT) declared as `ARG` in both stages of every Dockerfile and
  passed as a build argument, plus `rewrite-timestamp=true` on the
  exporters, so image `created`, every history entry, and the mtime of
  every file the build writes are that instant (files copied unchanged
  from the base layer keep their upstream mtimes, which are part of the
  pinned base). The fetched CLI binaries are `touch`ed to the epoch
  explicitly, because `ADD` from a URL takes the CDN's `Last-Modified`
  and a tar entry keeps its own mtime, and `rewrite-timestamp` only clamps
  mtimes newer than the epoch;
- `--provenance=false --sbom=false`, since attestations carry wall-clock
  time;
- apt lists, caches, and logs removed in the same layer.

## Differences found, and the fixes

Two, one by the spike and one by its review.

The first pair of clean builds differed for all three images, in one
layer, in one file:

```
== content differences (apt layer, 2094 files compared by sha256, mode, owner, mtime)
< ./var/cache/ldconfig/aux-cache
> ./var/cache/ldconfig/aux-cache
```

`ldconfig` writes `aux-cache` with the inode and device numbers of the
libraries it scanned, and those differ per build. The fix is
`rm -f /var/cache/ldconfig/aux-cache` at the end of the apt `RUN`; ldconfig
rebuilds it if ever needed and the runtime loader does not read it. The
base layer, the CLI layer, and the image config were already identical
before the fix.

The second would not have shown up on the day: `useradd` writes the
password-change day into `/etc/shadow` from the wall clock unless
`SOURCE_DATE_EPOCH` is in its environment, and the Dockerfiles passed the
build argument without declaring `ARG SOURCE_DATE_EPOCH` in the stage, so
it never reached `useradd`. The builds matched only because they ran on the
epoch's own date (day 20712). Fixed by declaring the `ARG` in both stages;
proof, a build of the Claude image with `SOURCE_DATE_EPOCH=1000000000`:

```
$ docker run --rm --user 0 crucible-epoch-probe sh -c 'grep ^worker /etc/shadow | cut -d: -f1-3'
worker:!:11574                         # 1000000000 / 86400, not today's 20712
```

The same review pass caught the CLI mtimes (fixed with `touch`, above) and
led to stripping setuid bits.

## Version reporting inside the image

Each CLI run as uid 1000, all capabilities dropped, `no-new-privileges`,
read-only root, tmpfs `/tmp` and `/home/worker`, `--network none`:

```
$ docker run --rm --user 1000:1000 --cap-drop ALL --security-opt no-new-privileges --read-only \
    --tmpfs /tmp:size=64m --tmpfs /home/worker:size=64m,uid=1000,gid=1000 --network none <image> ...
=== crucible-worker:claude_code-2.1.273-e3dc809a1678
2.1.273 (Claude Code)
update: Updates are disabled by your administrator. Contact your IT team to get the latest version.
=== crucible-worker:codex-0.153.4-58ac880fc6c0
codex-cli 0.153.4
update: Error: Could not detect the Codex installation method. Please update manually: https://developers.openai.com/codex/cli/
=== crucible-worker:agy-1.2.4-e95b3a11b631
1.2.4
update: Error: directory /usr/local/bin is not fully accessible (readable: true, writable: false)
```

Reported versions match `crucible.harness_version` on each image. Exit 0
from every `--version`. `claude --version` left `/home/worker` empty;
`codex --version` created `/home/worker/.codex` and `agy --version` created
`/home/worker/.gemini`, both on the tmpfs, which is where the credential
mounts will sit anyway (S1 records what they write).

Update attempts: Claude Code refuses by policy (the environment variable),
Codex cannot find an installer to run, AGY checks for an update even with
`AGY_CLI_DISABLE_AUTO_UPDATE=1` set when `agy update` is invoked explicitly
and then fails on the read-only `/usr/local/bin`. So the opt-out variable
governs the background path only, and the read-only root is what makes the
explicit path impossible, as ADR 0011 assumes. S11 repeats this with a
network attached and an observing proxy.

## Limitations

- One version per harness was built, not two. The question was whether a
  version can be pinned and reproduced; moving to a second version is a
  pin change and a rebuild (new `<build>` hash, new tag) with the same
  procedure, and the pinned URLs above are the ones to change.
- The build depends on four external hosts (`snapshot.debian.org`,
  `downloads.claude.ai`, `github.com`, `storage.googleapis.com`). Every
  fetch is checksum-verified so a changed upstream fails the build instead
  of changing the image, but an upstream that removes a file makes the
  pinned version unbuildable. Publishing to GHCR (C8) is what makes a built
  digest durable.
- The AGY manifest only ever names the latest version; there is no
  version-addressed manifest, so the pin URL is recorded from the manifest
  on the day the pin is taken.
- Reproducibility was checked on one machine and one BuildKit version.
  CI runs the same script; a digest mismatch there is a real finding.
- The builder is a docker-container BuildKit with a pinned image, because
  the docker driver in dockerd cannot emit OCI output and this daemon
  cannot `docker load` an OCI tar; hence the dual output in `build.sh`.
- Images were never pushed anywhere.
