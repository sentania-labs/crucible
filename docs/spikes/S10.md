# S10: App installation token, publisher container, push and tag without the token leaving tmpfs

Result: **pass**. Decision: proceed with the publication design in spec 23
and ADR 0007, with the adjustments recorded below (token hand-over by
stdin rather than `docker cp`, a host check in the credential helper, and
the exact permission each call needs).

Run on 2026-09-16 (America/Chicago) on the development workstation against
the throwaway repository `sentania-labs/crucible-spike-target` (private,
one `init` commit on `main`) and the throwaway App `crucible-spike`
(App id 4969317, installation 162289684 on the `sentania-labs` org with
`repository_selection: selected`, one repository). The rootful daemon was
used because the codex base image lives there; nothing in this spike is
daemon specific.

## Question

Can Crucible mint a repository-scoped installation token from a mounted
App private key and push a branch and an annotated tag from a publisher
container without the token touching env, logs, or disk outside tmpfs?
(spec 21, S10; spec 12 "GitHub App credentials"; spec 23 "Publication")

## Scripts

Throwaway, under `tools/spikes/s10/` (not product code):

| File | Role |
|---|---|
| `s10.py` | Crucible's side: signs the JWT in memory with `cryptography`, lists installations, mints the token, builds the publisher image, creates the egress network and proxy, runs the publisher, hands the token over on stdin, then runs the absence proof. Subcommands `run`, `observe` (S12), `cleanup`. |
| `publisher.sh` | Runs inside the container as uid 1000: receives the token on stdin, clones, commits, pushes the branch, pushes the annotated tag, opens the PR with `curl`. |
| `cred-helper.sh` | git credential helper: parses git's request on stdin and answers `get` with `x-access-token` and the tmpfs token **only** for `protocol=https host=github.com`. |
| `Dockerfile` | `FROM crucible-worker:codex-0.153.4-fdfc3a7c883e`, `USER root` to `COPY --chmod=0755` the two scripts (BuildKit required), back to `USER 1000:1000`, `ENTRYPOINT` the publisher. No credential of any kind in the image. |
| `squid.conf.in` | CONNECT-only proxy, port 443 only, `dstdomain github.com api.github.com`, source restricted to the internal network's subnet (rendered in at run time). |

Prerequisites the publisher takes from the codex base image, which a C3
implementation must not assume of a different base: `git`, `curl`, `jq`,
`bash`, and a GNU `date` supporting `+%s%3N`.

## Token minting and scoping evidence

JWT: RS256, `iss` = App id, `iat` = now-60, `exp` = now+540, signed with
the key read from `~/.local/state/foundry/crucible-credentials/github/app.pem`
into process memory only. `GET /app` confirmed slug `crucible-spike`.
`GET /app/installations` returned one installation (162289684). The token
was requested with `{"repositories": ["crucible-spike-target"]}`.

| Field in the `POST /app/installations/{id}/access_tokens` response | Value |
|---|---|
| `repository_selection` | `selected` |
| `repositories[].full_name` | `sentania-labs/crucible-spike-target` (only) |
| `permissions` | `actions: read, checks: read, contents: write, metadata: read, pull_requests: write` |
| `expires_at` | 2026-09-16 16:09:31 CDT, one hour after minting at 15:09:31 CDT |
| token shape | `ghs_` prefix, **390 characters**, alphabet alphanumerics plus `.`, `-`, `_`. Not the 40-character `ghs_` plus 36 form that older documentation and most regexes assume. The value is recorded nowhere; only its SHA-256 existed, in process memory, for the absence proof. |

The length and alphabet are a finding in their own right: the first
version of this spike's scanner used `ghs_[A-Za-z0-9]{36}` and matched
nothing, including a buffer that contained the token. Any redaction or
secret-scanning pattern Crucible ships for installation tokens (spec 12,
"Logs and artifacts") must not pin the length or exclude `.`.

Minting latency, measured across the four full-permission runs:
read key and sign JWT 41 to 46 ms; `GET /app` plus `GET /app/installations`
361 to 615 ms; `POST access_tokens` 246 to 539 ms; total 654 to 1202 ms.
The two GETs are avoidable once the installation id is recorded at
repository registration (spec 23), which removes roughly half the path.

## Publisher container

Image `crucible-s10-publisher:<stamp>` built from the codex base. The argv
below is the run of 2026-09-16 15:09:30 CDT verbatim from the run record,
including the per-run container name:

```
docker run -i --name s10-publisher-20260916-150930 \
  --user 1000:1000 --cap-drop ALL --security-opt no-new-privileges \
  --read-only --pids-limit 256 --memory 512m \
  --tmpfs /tmp:rw,nosuid,nodev,size=256m,mode=1777 \
  --tmpfs /home/worker:rw,nosuid,nodev,size=512m,mode=0700,uid=1000,gid=1000 \
  --tmpfs /run/crucible-token:rw,nosuid,nodev,noexec,size=64k,mode=0700,uid=1000,gid=1000 \
  --network crucible-s10-internal \
  -e HTTPS_PROXY=http://s10-egress:3128 -e https_proxy=http://s10-egress:3128 \
  -e NO_PROXY=localhost,127.0.0.1 \
  -e S10_REPO=sentania-labs/crucible-spike-target \
  -e S10_BRANCH=crucible/S10-20260916-150930 -e S10_TAG=s10-20260916-150930 \
  -e S10_STAMP=20260916-150930 -e S10_MODE=full \
  -v <scratch>/out-20260916-150930:/out \
  crucible-s10-publisher:20260916-150930
```

Network: `crucible-s10-internal` (`--internal`, subnet 10.10.24.0/24),
`s10-egress` running `ubuntu/squid` by the S9 digest on the default bridge
and connected to the internal network. The container's only route out is
the CONNECT proxy, which admits `github.com:443` and `api.github.com:443`
from that subnet and nothing else.

Token hand-over: **stdin**. `docker run -i` with Crucible writing the token
to the pipe and closing it; `publisher.sh` does `umask 077; cat >
/run/crucible-token/token` as its first action. The plan in spec 23
(`docker cp` into the tmpfs) does not work: `docker cp` into a
`--read-only` container is refused by the daemon with "container rootfs is
marked read-only" (tested), and even without `--read-only` the copy
targets the container's writable layer, which is disk. A bind of a
memory-backed host file (`/dev/shm`) would also work but puts the value in
a host path for the container's lifetime and needs ownership by the
daemon's uid 1000 (a subordinate uid under rootless, S9); stdin needs
neither.

Inside the container the value is read only by bash builtins (`$(< file)`
and `printf` into a curl config file on the same tmpfs) and by the
credential helper, so no process ever carries it on argv. `git` is run
with `-c credential.helper=` (reset) then `-c credential.helper=<helper>`,
`GIT_TERMINAL_PROMPT=0`, and `GIT_CONFIG_GLOBAL=/dev/null`. `curl` reads
`-K /run/crucible-token/curlrc`. `GIT_TRACE_CURL` and `GIT_CURL_VERBOSE`
must never be set in a publisher: they print the `Authorization` header.

The credential helper checks the request git hands it and answers only for
`protocol=https host=github.com`; `store` and `erase` are ignored. A helper
that answers unconditionally gives the token to whatever remote git was
pointed at, which matters for a product helper even though the egress
allowlist contains it here. Verified: `host=evil.example` and
`protocol=http` both produce no output.

## Run: downscoped token, `contents=write` only (14:34 CDT)

The mint endpoint accepts a `permissions` object to narrow the token below
the App's grant. With `{"permissions": {"contents": "write"}}` the token
came back with `contents: write, metadata: read` and nothing else. This
run used `--light`, which skips the whole-`/tmp` walk; its absence proof
covers every other location and says so in the record.

| Step | Result | Time |
|---|---|---|
| push branch `crucible/S10-20260916-143422` | ok | 1283 ms |
| push annotated tag `s10-20260916-143422` | ok | 2716 ms |
| `POST /repos/.../pulls` | 403 "Resource not accessible by integration", `X-Accepted-GitHub-Permissions: pull_requests=write` | 325 ms |

## Permissions actually required per call

| Call | Evidence | Needs |
|---|---|---|
| `git push` of a branch (no force) | succeeded with `contents=write` only | Contents write |
| `git push` of an annotated tag | succeeded with `contents=write` only; **Contents write is enough to push a tag** (a tag-protection ruleset, if one existed, would be the thing that changes this) | Contents write |
| `POST /pulls` (create PR) | 201 with the full token, 403 with contents-only; header names `pull_requests=write` | Pull requests write |
| `GET /pulls/{n}` | 200; header `pull_requests=read; contents=read` | Pull requests read |
| `GET /pulls/{n}/reviews`, `/pulls/{n}/comments` | 200 in S12; header `pull_requests=read` | Pull requests read |
| `GET /issues/{n}/comments`, `/issues/comments/{id}/reactions` | 200 in S12; headers `issues=read; pull_requests=read` and `issues=read` | Pull requests read is sufficient in practice |
| `GET /issues/{n}/reactions` (reactions on the PR itself) | **403** in S12; header `issues=read` | Issues read, which the App does not have (S12) |
| `GET /commits/{sha}/check-runs`, `check-suites` | 200 in S12; header `checks=read` | Checks read |
| `POST /issues/{n}/comments` | 201 in S12; header `issues=write; pull_requests=write` | Pull requests write |
| `PATCH /pulls/{n}` (close) | 200 at cleanup; header `pull_requests=write` | Pull requests write |
| `DELETE /git/refs/heads/...` and `/git/refs/tags/...` | 204 at cleanup; header `contents=write` | Contents write |
| `POST /app/installations/{id}/access_tokens` | JWT, not a token | none (App identity) |

The App's grant (Metadata read, Contents read/write, Pull requests
read/write, Checks read, Actions read) covers publication, the PR
lifecycle, and check observation. It does not cover reactions on the PR
itself, which spec 23 relies on for the reviewer's "no findings" signal;
S12 has the detail. Actions read was not exercised here (it is for
workflow-run logs after a CI failure). A publisher that only pushes
(release tagging, spec 24) can be handed a token narrowed to
`contents=write` by the same mint call.

## Absence proof

Method: the orchestrator holds the token in memory and its SHA-256. Every
location below was read as bytes and checked two ways: a direct substring
search for the value (never printed) and a regex for the token shape with
each candidate hashed and compared to the token's digest. Process state
was sampled twice a second while the publisher was alive.

Three guards make a silent pass impossible:

- a **positive control**, a synthetic buffer containing the token, which
  must produce a substring hit *and* a hash match, and which caught the
  broken shape regex described above;
- an **empty-scan check**: any location that returned zero bytes (a failed
  `sudo`, a missing container) fails the proof rather than counting as
  clean;
- counts of files and directories the scan could not read, reported per
  location rather than discarded.

no empty scans.

container's tmpfs (`token` and the derived `curlrc`, both `0600`, removed

## Limitations

- Single workstation, single day, warm network; timings are indicative.
- The proxy config is the S9 spike shape with the source ACL narrowed to
  the internal subnet and non-CONNECT methods denied; C3 takes its
  allowlist from policy (spec 13).
- The absence proof scans what a process can read. It does not scan swap,
  kernel memory, or the daemon's memory, and on the `/tmp` walk 7
  directories and 20 files were unreadable or oversized (counted, not
  silently skipped). The control is structural (stdin to tmpfs); the scan
  is the check on that structure, not a proof about the whole machine.
- `docker export` deliberately excludes tmpfs, so it cannot show the token
  file that existed during the run. The in-run `/proc` sampling and the
  `stat` line in the container log are what show it was there, mode 600.
- The container log is stamped UTC by `date -u` inside `publisher.sh`;
  every time in this write-up is CDT, five hours behind those stamps.
- No test of a push rejected by an out-of-band remote move (spec 23 step
  4); that is deterministic git behavior, not an App question.

## Risks

- Anything that turns on git or curl tracing in a publisher prints the
  bearer header. The publisher image must not inherit a `GIT_TRACE*`,
  `GIT_CURL_VERBOSE`, or `CURL_*` environment from the daemon or Compose.
- A redaction or scanning pattern built for the old 40-character token
  shape will not match a current installation token (390 characters, dots
  included). This is a live gap in anything that assumes the short form.
- The token is valid for one hour regardless of container lifetime;
  Crucible should not mint until the container is ready to start, and
  should treat a publisher that outlives ten minutes as failed.
- Under the rootless daemon the container's uid 1000 is a subordinate uid;
  `--tmpfs ...,uid=1000` is interpreted inside the user namespace and
  still works, but a `/dev/shm` bind alternative would not without a
  chown. Stdin avoids the question.

## Follow-ups

1. Spec 23 step 3: replace "`docker cp` or a bind of a memory-backed file"
   with stdin delivery (`docker run -i`, or the Docker API attach stream
   through the socket proxy, which must then allow
   `POST /containers/{id}/attach` for the publisher only; check S9's
   socket-proxy rules).
2. Spec 12 "Logs and artifacts": specify the installation-token redaction
   pattern as `ghs_` plus at least 20 characters from `[A-Za-z0-9._-]`,
   with no upper length bound, and add a test that the pattern matches a
   real token's shape.
3. Spec 23 step 5 keeps PR creation on Crucible's side for body rendering;
   the container can do it too, as shown. Either way the call needs
   `pull_requests=write`.
4. Spec 24 tagging: mint the release publisher's token narrowed to
   `contents=write` through the `permissions` field, since a tag push
   needs nothing else.
5. Record the installation id at repository registration and skip
   `GET /app/installations` on the hot path.
6. The credential helper in C3 must check `protocol` and `host` from git's
   request before answering, as this spike's does.
