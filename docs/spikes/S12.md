# S12: what the external reviewer emits on a PR, under which login, and how it is triggered

Result: **pass with a design correction**. Decision: adjust spec 23 and
05b before C1. The reviewer login default is confirmed, the signal shapes
are confirmed from the live record on `sentania-labs/crucible`, but the
trigger does not work the way spec 23 assumes: a PR opened by the App
(`crucible-spike[bot]`) received no automatic review in 20 minutes, and an
`@codex review` comment posted under the App identity was answered with
"create a Codex account and connect to github". The reviewer is triggered
by the identity of the PR author or commenter, and an App is not an
identity Codex knows. Also: the App's permission set cannot poll reactions
on the PR itself (`GET /issues/{n}/reactions` is 403 without Issues read),
so the "no findings" thumbs-up is invisible to Crucible as specified.

Run on 2026-09-16 (America/Chicago) against `sentania-labs/crucible-spike-target`
PR #1, opened by the S10 publisher container at 14:27:34 CDT with the
`crucible-spike` App token. The Codex GitHub App
(`chatgpt-codex-connector`, installation 111576857, `repository_selection:
all` on the org, permissions `actions: write, checks: read, contents:
write, issues: write, metadata: read, pull_requests: write, statuses: read,
workflows: write`) covered the repository. Observation was REST polling
every 60 s with an installation token of the `crucible-spike` App
(`tools/spikes/s10/s10.py observe`); no webhook receiver was run.

## Question

What does the configured external reviewer actually emit on a PR, under
which login, and how does it get triggered? (spec 21, S12; spec 23
"External review"; 05b `external_review` defaults)

## What was polled, every 60 seconds

Rows marked "observer" are the cycle `s10.py observe` runs. Rows marked
"probe" were issued once by hand with an App token to establish what the
grant does and does not reach; the observer does not call them.

| Endpoint | Source | Status with the App token | `X-Accepted-GitHub-Permissions` |
|---|---|---|
| `GET /pulls/{n}` | observer | 200 | `pull_requests=read; contents=read` |
| `GET /pulls/{n}/reviews` | observer | 200 | `pull_requests=read` |
| `GET /pulls/{n}/comments` (review comments) | observer | 200 | `pull_requests=read` |
| `GET /pulls/comments/{id}/reactions` | observer | not exercised (no review comments arrived) | documented as `pull_requests=read` |
| `GET /issues/{n}/comments` | observer | 200 | `issues=read; pull_requests=read` |
| `GET /issues/comments/{id}/reactions` | observer | 200 | `issues=read` |
| `GET /issues/{n}/reactions` (reactions on the PR itself) | observer | **403** "Resource not accessible by integration" | `issues=read` |
| `GET /issues/{n}` | probe | 403 (not needed; `GET /pulls/{n}` carries the PR) | `issues=read` |
| `GET /issues/{n}/timeline` | probe | 200 | `issues=read; pull_requests=read` |
| `GET /commits/{sha}/check-runs` | observer | 200 | `checks=read` |
| `GET /commits/{sha}/check-suites` | observer | 200 | `checks=read` |
| `POST /issues/{n}/comments` (the trigger comment) | observer | 201 | `issues=write; pull_requests=write` |

There is no REST endpoint for reactions on a pull request review object
(only on review comments and issue comments); GraphQL exposes them. The
403 on PR reactions is the one that matters: with the App grant from ADR
0007 (Metadata, Contents, Pull requests, Checks, Actions) Crucible cannot
see a thumbs-up on the PR. The comment-reaction endpoints accepted the
same token, so GitHub's enforcement differs between the two; the PR-level
one is the documented "no findings" signal.

Coverage has no gap despite the restart: every object is fetched by list
endpoint with its own `created_at`, so anything that appeared between
14:40:15 and 14:40:34 would have been picked up by invocation 2 and dated
correctly. Nothing had.

Two further observer defects worth recording for C3, since spec 23's
polling design has the same shapes to get right: the settle rule keyed on
a one-second-resolution timestamp string, so two signals seen in the same
poll could leave the window measured from the wrong one (now keyed on the
signal count); and `note()` dedupes on `(kind, id)` and never re-emits, so
an issue comment edited in place is invisible to it. The second one is why
the "edited in place" finding below comes from reading the live record
with `gh`, not from the observer.

## What the reviewer emits when it does run (live record, `sentania-labs/crucible`)

Read read-only through `gh` from PRs #1 to #5 on the Crucible repository,
all opened by the operator's user `sentania`, whose GitHub account is
connected to a Codex account:

| PR | Opened | Summary comment (`chatgpt-codex-connector[bot]`) | Review (`chatgpt-codex-connector[bot]`) |
|---|---|---|---|
| #1 | 09:50:05 | 09:50:18 (+13 s) | 09:53:51 (+3 min 46 s), `COMMENTED`, 7 review comments |
| #2 | 11:30:45 | 11:30:54 (+9 s) | 11:35:30 (+4 min 45 s) |
| #3 | 11:51:05 | 11:51:15 (+10 s) | 11:57:05 (+6 min 0 s) |
| #4 | 11:57:50 | 11:58:08 (+18 s) | 12:02:06 (+4 min 16 s) |
| #5 | 12:14:08 | 12:14:20 (+12 s) | 12:19:32 (+5 min 24 s) |

Shape of the signals, from PR #1's objects:

- **Trigger**: PR opened, with no `@codex review` comment anywhere in the
  thread. The reviewer ran automatically for a PR authored by a connected
  user.
- **Issue comment** first, within about 10 to 20 s of open, login
  `chatgpt-codex-connector[bot]`, `user.type: Bot`, body starting with the
  HTML marker `<!-- codex-pull-request-review-summary -->` and the heading
  "Codex Review Summary". It is a placeholder that the reviewer edits in
  place when the review completes ("This comment shows the latest Codex
  review activity"). Crucible must therefore treat an edited issue comment
  as a change (poll `updated_at`, not only new IDs).
- **Review** 4 to 6 minutes after open, same login, `state: COMMENTED`,
  body "Codex Review ... Reviewed commit: `<sha>`". The reviewed SHA is in
  the review's `commit_id` field and is repeated in the body text.
- **Review comments** attached to that review (`pull_request_review_id`),
  each with `commit_id` (the reviewed head), `path`, sometimes `line`
  (null when the comment spans a range or is file-level), and a body that
  opens with a P1 or P2 badge image, then the finding.
- **Reactions**: none observed on any of the five PRs. Every one had
  findings, so the "no findings" thumbs-up was not exercised in the live
  record either. Its existence rests on the provider's documentation, and
  spec 23's polling cannot see it (above).
- No check run, check suite, or status from the reviewer on any PR.

All times in this file are CDT. Raw GitHub timestamps in the run record
are UTC, five hours ahead.

## Answers

1. **Login**: `chatgpt-codex-connector[bot]` for the summary comment, the
   review, and every review comment. The 05b default
   `reviewer_logins: ["chatgpt-codex-connector[bot]"]` is confirmed. The
   summary comment posts under the same login, not a different one.
2. **Signal kinds**: issue comment (summary, edited in place), review with
   state `COMMENTED`, review comments. `accepted_signals: ["review",
   "comment", "reaction:+1"]` is right as a list, with two corrections:
   the summary comment must not count as a round on its own (it appears
   before the review and is edited later), so "comment" should mean an
   issue comment from the reviewer that is not the summary marker, or the
   round should key on the review; and `reaction:+1` cannot be observed
   with the current App grant.
3. **Reviewed SHA**: `commit_id` on the review and on each review comment;
   also in the review body as "Reviewed commit".
4. **Trigger**: PR opened, automatic, when the PR author is a GitHub user
   connected to Codex. A PR opened by an App installation token is not
   reviewed (20 minutes, no signal), and `@codex review` from the App is
   refused with an account prompt. Codex therefore does not treat the
   `crucible/*` PRs Crucible will open as reviewable under the current
   design, whatever the org-wide installation says.

## What 23 must poll to see the thumbs-up

`GET /repos/{o}/{r}/issues/{n}/reactions` filtered to `content: "+1"` and
`user.login` in `reviewer_logins`. That call requires **Issues read** on
the App, which ADR 0007 does not grant. Either the App grant gains Issues
read (a one-line change to the App and a re-approval of the installation),
or the thumbs-up is dropped from `accepted_signals` and a round with no
findings is recognized some other way (for example, the summary comment
edited to a "no findings" body, which Crucible can read with Pull
requests read through `GET /issues/{n}/comments`).

## Spec changes needed

- **23 External review, trigger**: state that the reviewer runs on PR open
  only for PRs authored by a connected user, and that Crucible cannot
  trigger it. Options for the operator to decide: (a) the PR is opened by
  the operator's own account through a device flow, which contradicts ADR
  0007's identity model; (b) after Crucible opens the PR, a connected user
  (the operator) posts `@codex review` by hand, which makes the external
  round an operator step, not an automatic one; (c) accept that Codex
  reviews Crucible's PRs only when configured to do so for bot authors,
  which is not offered today; (d) the external round is optional per
  repository (`required_rounds: 0`) until one of the above lands.
- **23 Observation**: PR-level reactions need Issues read; add it to the
  App grant in 23 and ADR 0007, or remove `reaction:+1`. Issue comments
  from the reviewer are edited in place; poll `updated_at`. Remove
  "reactions on each review" (no REST endpoint; comment reactions only).
- **05b**: `reviewer_logins` default stays. `accepted_signals`: keep
  `review`; define `comment` as a non-summary issue comment from an
  allowlisted login; keep `reaction:+1` only if Issues read is granted.
- **21**: S12's expected "reviewer_logins default confirmed" holds; add
  "trigger requires a connected human author or commenter" as the finding.

## Limitations

- One throwaway PR, one 20-minute window, one `@codex review` attempt.
  Codex's automatic-review setting for the throwaway repository could not
  be inspected from the GitHub side; the live record on `crucible`
  (same org installation, same day) shows automatic reviews work there for
  the operator's PRs, so the difference is the author identity, not the
  installation.
- No webhook deliveries were captured; there was no receiver. Polling is
  the complete path in spec 23 anyway.
- The thumbs-up was not observed anywhere, so its exact object (reaction
  on the PR versus on the summary comment) is unconfirmed.
