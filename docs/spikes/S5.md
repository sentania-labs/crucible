# S5: Is exit-code and report-file detection reliable across the three harnesses?

Run 2026-09-16, 14:08 to 14:15 CDT, rootful Docker 28.3.1, all three base
images in the spec 08 worker shape with `--network none` and the report dir
mounted rw. The forced cases are shell stand-ins running inside each image
(no model); the real-harness rows come from the S1 and S6 runs.

Decision: **proceed, with one launch-spec change.** Exit codes and report
files arrive exactly as written, on all three images. (An OOM kill was not
forced here; S9 recorded `OOMKilled=true` with exit 137 for one, which is
what separates it from a plain kill.) But a SIGTERM sent to a worker whose harness
runs as PID 1 and has no handler is silently ignored by the kernel, so
`terminate(drain)` degrades to the SIGKILL after the grace period and
`143` never appears. `--init` fixes it; the Docker provider adds `--init`
(Docker's bundled tini as PID 1) to every worker.

## Forced cases, per image

Each row: a container started with `bash -c '<case>'`, waited on, then
inspected. Identical results on the Claude Code, Codex and AGY images.

| Case | Command | Exit | `OOMKilled` | Report dir | Wall |
|---|---|---|---|---|---|
| success with report | write `report.yaml`, `exit 0` | 0 | false | `report.yaml` | 0.1 s |
| blocked | write `blocked.md`, `exit 75` | 75 | false | `blocked.md` | 0.1 s |
| software failure | `exit 70` | 70 | false | empty | 0.1 s |
| crash of the harness process | child `sleep` killed with `SIGSEGV`, `wait` propagates | 139 | false | empty | 0.4 s |
| hang, `docker stop -t 10` (drain) | `exec sleep 600` as PID 1 | 137 after 10 s | false | empty | 10.1 s |
| hang behind a shell, `docker stop -t 10` | `bash -c 'sleep 600'` (bash is PID 1) | 137 after 10 s | false | empty | 10.1 s |
| hang, `docker kill` | `exec sleep 600` | 137 | false | empty | 1.1 s |
| hang that ignores SIGTERM, `docker stop -t 3` | `trap "" TERM; loop` | 137 after 3 s | false | empty | 4.2 s |
| hang, `docker stop -t 10` with `--init` | `sleep 600` under tini | **143 at once** | false | empty | 0.1 s |
| exit 0, 75, 70 with `--init` | `bash -c "exit N"` under tini | 0, 75, 70 (unchanged) | false | empty | 0.1 s |

`kill -SEGV $$` inside `bash -c` does not produce a crash (bash handles the
signal and exits 0), which is why the crash row kills a child and waits;
the Docker exit code for a real signal death is 128 + signal.

The PID 1 row is the finding: `sleep` has no SIGTERM handler, and Linux
does not deliver default-action signals to the init process of a pid
namespace, so `docker stop` waits out the grace and sends SIGKILL, giving
137, the same code as `docker kill` and as an OOM kill (which differs only
in `OOMKilled=true`). With `--init`, tini is PID 1, forwards SIGTERM to the
harness, and the harness's default action gives 143 immediately. Wrapping
the harness in `bash -c` does not help (second hang row: bash as PID 1
ignores the signal in the same way, 137 after the grace).

## Real harness evidence

| Harness, run | Exit | stdout / stderr tail | Report dir | Class |
|---|---|---|---|---|
| Claude Code, trivial prompt, authenticated (S1) | 0 | stream-json `result` line, `stop_reason: end_turn` | empty (the prompt asked for no report) | `completed_without_report` |
| Claude Code, not logged in (empty config dir, S6 proxy) | 1 | `result: "Not logged in · Please run /login"` in stream-json; stderr empty | empty | `auth_failure` (stderr is empty; parse the `result` text) |
| Claude Code, `--network none`, launched as `claude -p ...` directly (PID 1, no `--init`), SIGTERM through the client after 120 s (S6) | 143 | `api_retry` events, attempt 9 of 10 logged by 120 s | empty | `timeout` (Claude Code installs its own SIGTERM handler: 143 even as PID 1) |
| Codex, trivial prompt, authenticated (S1) | 0 | `turn.completed`, `codex-last-message.md` written | last message only | `completed_without_report` |
| Codex, not logged in (S6) | 1 | `turn.failed` with `401 Unauthorized: Missing bearer or basic authentication` after 5 websocket and 5 https reconnects, about 15 s | empty | `auth_failure` |
| AGY, trivial prompt, authenticated (S1) | 0 | `result` line, `status: SUCCESS` | empty | `completed_without_report` |
| AGY, not logged in (S6) | 1 | `result` line `status: ERROR`, `error: authentication failed or timed out`; stderr `authentication required` | empty | `auth_failure` |

AGY exits 1 for an auth failure even though it emits a well-formed
`result` line; the adapter should classify on `status`, not on the presence
of the line. Codex's 401 message and Claude Code's `Not logged in` text are
the patterns for `auth_failure`, and for Claude Code and AGY they are on
stdout (the `result` line) with an empty stderr. Spec 07's
`classify_exit(exit, stderr_tail)` therefore needs the stdout tail (or the
parsed stream) as well; that is a design consequence, not a parsing detail. Quota exhaustion was not
triggered; Claude Code's `rate_limit_event` stream lines (S1) are the
signal to look for there.

## `classify_exit` table as confirmed

| Evidence | Class |
|---|---|
| exit 0 and `report.yaml` parses | `completed` |
| exit 0, no `report.yaml` | `completed_without_report` |
| exit 75 and `blocked.md` | `blocked` |
| exit 75, no `blocked.md` | failed (spec 07: never `blocked`) |
| exit 1 with an auth pattern in the tail (`Not logged in`, `401 Unauthorized`, `authentication failed`) | `auth_failure` |
| exit 70 | `environment` (spec 16; nothing in this spike argues for a change) |
| any other non-zero without a pattern | `crashed` (with the tail stored) |
| exit 128 + signal (134, 139) | `crashed` |
| exit 143 or 137 after a signal Crucible sent | `timeout` if Crucible sent it for the contract timeout or a stall, `killed` if for a cancel (spec 16). The code says only that the signal landed (143: harness exited on SIGTERM; 137: SIGKILL, either `kill` or a drain whose grace ran out); the class comes from the recorded reason for sending it |
| exit 137, `OOMKilled=true`, no signal from Crucible | `environment` |
| container gone | `lost` |

Provider-side requirement so the table holds: `--init` on every worker,
`terminate(drain)` = SIGTERM plus policy grace, `terminate(kill)` =
SIGKILL, and the attempt records which one Crucible sent and why, because
the exit code alone cannot tell a timeout from a cancel, or a drained 143
from a harness that chose to exit 143.
