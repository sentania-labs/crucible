# S15: quota-axi validated across all three providers

Run 2026-09-18, 23:46 to 23:54 CDT, on the reference workstation, against
`quota-axi` 0.1.47 installed into a scratch prefix with `--ignore-scripts` and
never globally. Follows S14 (ADR 0014, proposed), which left three gaps. This
spike closes two of them, opens one new risk that S14 did not see, and stops
gap 1 at an operator blocker as the contract directs.

No task was run and no model was called. Every reading below is a quota read.
No credential value was printed, logged, hashed, or stored, and `--full` was
never used.

Decision: **adjust design, and proceed with conditions.** The reader works in
the container against read-only credential mounts for Codex. It does not work
for AGY in the shipped image, and the AGY path is not read-only on a writable
mount. Claude remains unreadable and is blocked on an operator login.

## Method

```sh
# Pinned, local, reproducible. Nothing installed globally, nothing committed,
# nothing added to an image.
npm install --prefix <scratch>/qa-prefix --ignore-scripts quota-axi   # resolved 0.1.47

# Host runs used a sanitized environment: scratch HOME and scratch XDG roots,
# so any default-location lookup lands in the scratch tree.
env -i PATH=... HOME=<scratch>/scratch-home \
    XDG_CONFIG_HOME=<scratch>/xdg/config XDG_CACHE_HOME=<scratch>/xdg/cache \
    XDG_DATA_HOME=<scratch>/xdg/data TERM=dumb NO_COLOR=1 <cmd>

# Container runs used the shipped service image, pulled by tag, with the
# dedicated credential directories bound read-only at the paths compose uses.
docker run --rm --user <uid>:<gid> \
  -v <node-prefix>:/opt/node:ro -v <scratch>/qa-prefix:/opt/qa:ro \
  -v <CRED_ROOT>/codex:/var/lib/crucible/credentials/codex:ro \
  -v <CRED_ROOT>/agy:/var/lib/crucible/credentials/agy:ro \
  -v <CRED_ROOT>/claude_code:/var/lib/crucible/credentials/claude_code:ro \
  -v <scratch>/ctr-home:/scratch/home -v <scratch>/ctr-xdg:/scratch/xdg \
  -e HOME=/scratch/home -e XDG_CONFIG_HOME=/scratch/xdg/config \
  -e XDG_CACHE_HOME=/scratch/xdg/cache -e XDG_DATA_HOME=/scratch/xdg/data \
  ghcr.io/sentania-labs/crucible:latest \
  /opt/node/bin/node /opt/qa/node_modules/.bin/quota-axi <flags>

# The three per-harness readings, one provider per call, never combined.
```

### Two deliberate deviations from the deployed shape, declared

1. **Node reaches the container by bind mount.** The service image carries no
   node, so the reader cannot run in it as shipped. A host node prefix was
   bound read-only at `/opt/node`. That prefix also contains a `codex` binary,
   so `quota-axi auth` reported `cli-rpc` as `available` inside the container
   where the shipped image would report it missing. `--profile-only` disables
   that source, and run A below confirms it was not used. Every other
   observation is unaffected.
2. **The container ran as the host uid, not uid 1000.** The dedicated
   credential files are mode 0600 owned by the operator, and the image user is
   uid 1000. On a real deployment the credential root is owned by the service
   user, which spec 13 already requires; this is an artifact of running the
   spike against the live dedicated directories rather than a copy.

## Gap 3: `exhausted_now`, captured

**Closed.** The first real `exhausted_now` this project has ever recorded, on
Codex, taken while the operator reported his Codex out.

Host reading, **2026-09-18 23:47:05 CDT**, `--profile-only` with `CODEX_HOME`
at the dedicated directory:

```text
quota[1]{provider,scope,effectivePercentRemaining,spendPriority,runway,confidence,limitedBy,resetsAt}:
  codex,all_models,0,-1.0712,exhausted_now,unknown,weekly,"2026-09-19T15:57:21.000Z"
exhaustion[1]{provider,scope,usableRunwaySeconds,projectedExhaustedAt,limitingWindowId}:
  codex,all_models,0,"2026-09-19T04:47:15.637Z",weekly
attention[0]:
```

The `resetsAt` is **2026-09-19 10:57:21 CDT**.

`--json` at the same moment adds: `plan: "prolite"`; one `weekly` window with
`percentRemaining: 0`, `pace.status "ahead"`, `reservePercentPoints -6.6493`,
`burnMultiple 1.0712`; `credits.remaining 2258.11098` with
`unlimited: false`, unit `credits`; `state.status "fresh"`, `stale: false`;
`quotaSemantics.status "known"` with one scope `all_models`,
`effectivePercentRemaining: 0`, `boundedBy ["weekly"]`,
`limitingWindowIds ["weekly"]`, `runway.status "exhausted_now"` with
`usableRunwaySeconds: 0` and `projectedExhaustedAt` equal to `generatedAt`,
and `selection.status "known"` with `spendPriority -1.0712`.

Readings taken at the same moment for contrast:

| Local time | Provider / scope | effectivePercentRemaining | runway | limitedBy |
|---|---|---|---|---|
| 23:47:05 CDT | codex / all_models | 0 | `exhausted_now` | weekly |
| 23:47:29 CDT | agy / gemini | 96 | `unknown` | gemini_weekly |
| 23:47:29 CDT | agy / claude_gpt | 100 | `unknown` | claude_gpt_5h + claude_gpt_weekly |
| 23:47:31 CDT | claude | no reading | none | none |

Four things worth carrying forward.

- **`attention[]` is empty on an exhausted reading, and `exhaustion[]` carries
  it.** A consumer that watches only `attention[]` sees nothing at the moment
  that matters. The exhausted state is in `quota[].runway`, in
  `exhaustion[]`, and in `effectivePercentRemaining: 0`, and those three
  agreed on every reading.
- **`projectedExhaustedAt` equals `generatedAt` under `exhausted_now`**, and
  `usableRunwaySeconds` is 0. It is not a forecast, it is a restatement of
  now. Do not render it as a prediction.
- **`confidence` read `unknown`, not `established`.** S14 saw `established`
  on a Codex row at 2 percent under `projected_exhaustion`. A validator that
  requires `confidence == "established"` before acting would discard the one
  reading the design exists to act on. Ineligibility must key on
  `runway == "exhausted_now"` or `effectivePercentRemaining == 0`, not on
  confidence.
- **Credits remained at 2258.11 while the weekly window read 0.** Headroom and
  credits are different bounds. The window is what refuses work.

Repeated in the container configuration at **23:48:29 CDT** and again at
**23:51:26 CDT**: identical scope, `effectivePercentRemaining 0`,
`exhausted_now`, `limitedBy weekly`, same `resetsAt`. `spendPriority` drifted
with elapsed time only, `-1.0712` to `-1.0707` to `-1.0704`.

**The refill was not observed.** The window resets at 10:57 CDT on
2026-09-19, outside this run. The last reading, at 23:54:04 CDT, was still
`exhausted_now`. What the tool reports as the window refills is therefore
still unobserved, and is left open rather than guessed.

### What this says about FDY-0019

The dedicated Codex credential read exhausted at the same moment the operator
reported his own Codex out. The two are on the same account, and the binding
window is `weekly`, which the vendor bounds per account. This is the
negative answer to the hopeful version of FDY-0019 for Codex: **Crucible's
dedicated Codex session does not have its own window.** It shares the
operator's, and a week the operator spends is a week Crucible does not have.

The spike cannot separate "shared window" from "both independently
exhausted", because taking a reading from his daily directory is out of
bounds. But the account-level weekly bound makes the shared reading the
ordinary explanation, and nothing observed contradicts it.

## Gap 2: in-container, against read-only mounts

**Closed for Codex. Open for AGY, for a reason that is architectural.**

### Codex: works, reads exactly one file, writes nothing

The in-container reading matched the host reading taken minutes apart, field
for field. With all three credential directories mounted read-only and an
inotify watch on the whole dedicated root, the 23:51:26 CDT run produced
exactly two events:

```text
23:51:26 ACCESS /…/crucible-credentials/codex/auth.json
23:51:26 OPEN   /…/crucible-credentials/codex/auth.json
```

Nothing under `agy/`, nothing under `claude_code/`, although both were
mounted. No cache and no state file appeared in the container's scratch
`XDG_CACHE_HOME` or scratch `HOME`: `--profile-only` writes nothing at all.
This confirms and extends S14's finding that `--profile-only` reads the
directory it is given and nothing else.

### The read-only mount is enforced, but the reader never challenged it

Across every in-container run, the watch recorded **zero** `MODIFY`,
`CREATE`, `DELETE`, `MOVED` or `ATTRIB` events on the credential root: 41
`ACCESS`, 16 `ACCESS,ISDIR`, 36 `OPEN`, 8 `OPEN,ISDIR`, and nothing else.

So the honest answer to "how does the read-only mount answer a write the tool
attempts" is: **in the container the tool attempted no write, so the mount was
never asked.** A separate control confirms the mount would have refused one:

```text
touch: cannot touch '/var/lib/crucible/credentials/agy/s15-probe': Read-only file system
agy-create rc=1
touch: cannot touch '/var/lib/crucible/credentials/codex/auth.json': Read-only file system
codex-touch-existing rc=1
sh: 1: cannot create /var/lib/crucible/credentials/codex/auth.json: Read-only file system
```

`codex/auth.json` was unchanged at 4126 bytes with its 2026-09-16 17:08
mtime afterwards, and no `s15-probe` was created.

This matters because ADR 0014 states the read-only mount "would also stop any
write the tool attempted". That is true of the mount. It is not evidence that
the tool is read-only, and on the host it is not (see the next section).

### AGY: the shipped service image cannot read it at all

In the container, with the dedicated AGY directory mounted read-only and
`HOME` pointed at it, the reader failed outright at 23:48:40 CDT:

```json
{ "provider": "agy", "windows": [],
  "state": { "status": "error", "stale": false,
             "error": "Antigravity process discovery failed" },
  "quotaSemantics": { "status": "unknown", "effectiveAvailability": [] } }
```

The cause is that the AGY path needs the `agy` CLI, and spec 13 is explicit
that "the Crucible service image carries none of them". Verified directly
against the pulled image rather than taken from the spec:

```text
claude not present
codex  not present
agy    not present
node   not present
npm    not present
```

Note that `node` is absent too, which is why this spike had to bind-mount a
node prefix and why putting the reader in the image is its own build
question. A negative control on
the host pins this down: the same call, with the `agy` binary removed from
`PATH` and no Antigravity process running, degrades to
`state.status "stale"`, `error: "Antigravity/agy is not running"`, every
scope `status: "unknown"`, and no usable `quota[]` row. It served the four
windows from its own cache and refused to claim them as current. It never
invented a number.

Binding the `agy` binary into the container read-only made it work: at
23:49:43 CDT the reading came back `fresh`, matching the host, with the same
four windows and the same two scopes. So the reader is not the obstacle. The
obstacle is that observing AGY requires a second, separately versioned copy
of a harness CLI, a 224 MB binary, inside the one process that holds every
credential, outside ADR 0011's per-image pinning. ADR 0014 already names that
cost and leaves it to the operator. This spike confirms the cost is real and
adds two reasons below to weigh it higher.

### The AGY source: CLI, not loopback, and how that was established

No Antigravity or `agy` process was running on the host, and no loopback
listener answered for it, yet the host reading came back `fresh`. With the
`agy` binary off `PATH` the same call degraded to `stale`. The source was
therefore the CLI in every fresh reading here, never the loopback fallback,
which is the source ADR 0014 accepts.

That is the good news. The bad news is that **the reading still carries no
source discriminator.** The source was inferred from a negative control, not
read off a field. ADR 0014 requires Crucible to discard a loopback-sourced
AGY reading, and there is no field in `schemaVersion: 5` output that lets it
do so. `quota-axi auth --json` for `agy` lists only
`{"source":"loopback", …}` with no path, which tells Crucible nothing about
which source a given quota row came from. This is an unresolved integration
detail, not a solved one, and it is carried into the amendment below.

### New risk S14 did not see: the AGY read is not read-only, and it self-updates

On the host, where `HOME` was the dedicated directory and therefore writable,
the AGY read at 23:47:16 to 23:47:31 CDT wrote into the credential directory:

| File | mtime after the read | What it is |
|---|---|---|
| `.gemini/antigravity-cli/antigravity-oauth-token` | 23:47:17.778 CDT | the credential, rewritten (1658 bytes to 1663 bytes) |
| `.gemini/antigravity-cli/last_check.timestamp` | 23:47:17.599 CDT | updater check marker |
| `.gemini/antigravity-cli/updater/update_status.json` | 23:47:20.172 CDT | `{"success":true,"message":"Update successful, restart CLI to use"}` |
| `.gemini/antigravity-cli/cli.log`, `log/`, `cache/`, `crashes/`, `conversation_summaries.db` | 23:47:29 to 23:47:31 CDT | CLI state |

Two separate problems.

- **A quota read rotated the credential.** S14 reported the AGY token was
  byte-identical after its run. This spike contradicts that: the token was
  rewritten within two seconds of the read. Under spec 12's `rw-narrow` and
  `issued_at = token.expiry`, a service-side quota read that rotates the
  token while an attempt holds a per-attempt copy is exactly the two-refresh
  race that spec 12 caps per-harness concurrency at 1 to avoid. The quota
  reader is not covered by that cap today.
- **The `agy` CLI self-updated in place during the read.** The chain is
  timestamped end to end: the CLI the reader launched opened its log
  `log/cli-20260918_234717.log` at 23:47:17 CDT; the updater wrote
  `{"success":true,…}` at 23:47:20.172 CDT; the host binary
  `~/.local/bin/agy` carries mtime 23:47:20.165 and ctime 23:47:20.171 CDT;
  and the displaced `agy.<id>.old` beside it carries the same ctime,
  23:47:20.171 CDT, which is the rename. All of it falls inside the
  23:47:16 to 23:47:31 CDT read, and the only process started in that window
  was the one the reader started. ADR 0011's posture is that harness CLIs do
  not self-update. A quota read that upgrades a harness CLI in place, and
  that upgrades the same binary on the operator's `PATH` that his own use
  depends on, is a drift path ADR 0011 closed for workers and that ADR 0014
  would reopen in the service.

`--no-credential-refresh` fixes the first of these and only part of the
second. At 23:53:47 CDT it produced an identical AGY reading (gemini 96,
claude_gpt 100, same `limitedBy`, same two `attention[]` rows) and left the
token's size and mtime unchanged at 1663 bytes, 23:47:17.778 CDT, and left
`updater/update_status.json` unchanged at 23:47:20.172 CDT. It did **not**
stop the CLI launching: a third log, `log/cli-20260918_235347.log`, 19651
bytes, was written into the credential directory at 23:53:49 CDT. So the
flag makes the **credential** read-only, which is what the tool's help
claims ("keeps a read strictly read-only"), and does not make the
**directory** read-only. Only the read-only mount does that.

In the container against the read-only mount, none of these writes landed,
and the reading still came back `fresh`. The read-only mount absorbs the
attempt silently. That is a safe outcome and a fragile one to rely on: it
means the reading Crucible trusts is produced by a code path that believes it
is allowed to write.

## Isolation, re-run in the container configuration

S14 proved isolation with a decoy credential and an inotify watch. Both were
re-run here, with one method change stated plainly.

### The decoy runs, all five, inside the container

A scratch `HOME` was seeded with a decoy `.codex/auth.json`, a decoy
`.claude/.credentials.json` and a decoy
`.gemini/antigravity-cli/antigravity-oauth-token`, each valid JSON holding
one non-secret marker field and no credential. The decoy is what a
default-location fallback would find, and it is loud.

| Run | Invocation | Result |
|---|---|---|
| A | codex, `--profile-only`, `CODEX_HOME` at the dedicated mount, decoy present | returned the dedicated account's real reading, `codex,all_models,0,-1.0706,exhausted_now,…,weekly`. The decoy was not consulted. |
| B | codex, no `--profile-only`, no `CODEX_HOME`, decoy present | `quota[0]`, `attention: codex,all,error,Codex quota unavailable,none`. It found and used the decoy. |
| C | `auth --json` for run B | `{"source":"auth-json","path":"/scratch/decoyhome/.codex/auth.json","status":"invalid"}` |
| D | claude, `CLAUDE_CONFIG_DIR` at the dedicated mount, decoy present | `{"source":"oauth-file","path":"/var/lib/crucible/credentials/claude_code/.credentials.json","status":"missing"}`. The decoy was not consulted. |
| E | claude, no `CLAUDE_CONFIG_DIR`, decoy present | `{"source":"oauth-file","path":"/scratch/decoyhome/.claude/.credentials.json","status":"invalid"}`. It found and used the decoy. |

A and D establish that the scoped mode reads the directory it is given and
nothing else, in the container exactly as on the host. B, C and E establish
that the fallback being avoided is real and would otherwise fire. S14's
conclusion holds unchanged: the mode is load-bearing on its own, and the
scoped `HOME` is defence in depth.

### Isolation by construction, which the container adds

In the deployed shape the operator's directories are not merely unvisited,
they are unreachable. Inside the service container, with only the credential
mounts bound:

```text
-- bind mounts --
/var/lib/crucible/credentials/codex ro,relatime
-- /home --
.  ..  crucible
-- daily dirs reachable? --
/home/scott/.claude: absent (ENOENT)
/home/scott/.codex: absent (ENOENT)
/home/scott/.gemini: absent (ENOENT)
/home/scott/.config: absent (ENOENT)
```

This is a stronger guarantee than the host runs could give, and it is the one
the design actually ships. The mount namespace, not the tool's good
behaviour, is what keeps the operator's credentials out of reach.

### The watch, and what was deliberately not re-run

The inotify watch here covered the **dedicated** credential root only, all
three harness directories, recursive, on modify, create, delete, move, open,
access and attrib. Results are in the sections above.

S14 additionally placed a read-only watch on the operator's own daily files.
**This spike did not**, because its contract forbids reading, referencing,
mounting or probing those directories at all, and a watch on them is a probe.
The substitute is the mount-namespace evidence above, which proves
unreachability rather than non-access. This is a real difference in what is
proven, and it is recorded as a gap rather than papered over: on the host,
this spike did not independently re-verify that the reader leaves the
operator's daily files untouched. S14's evidence for that stands and was not
contradicted.

## Gap 1: Claude, up to the operator blocker

**Unchanged and still blocked.** The dedicated directory holds `oauth-token`
(109 bytes) and `.claude.json` (423 bytes). It holds no `.credentials.json`.
The reader asks for exactly that path and reports it `missing`, in the
container as on the host (run D above), and the setup token gets 403 from the
usage endpoint. Nothing in this spike changes that.

### What the dedicated oauth credential would look like on disk

The reader needs `<CLAUDE_CONFIG_DIR>/.credentials.json`, which run D names
explicitly. Per S1, that file holds a `claudeAiOauth` object with a
short-lived access token (hours) and a refresh token (about a month). That is
a shape the CLI rewrites in place on refresh, unlike the setup token, which
never refreshes.

### What `ClaudeCodeAdapter.credential_spec` would need

Today both entries are `sync_back=False` with no `issued_at`, which is
correct for a token that never refreshes and wrong for an oauth session. The
two working patterns in the tree are Codex, `AuthFile("auth.json", json=True,
json_keys=("tokens",), issued_at=("last_refresh",))`, and AGY,
`AuthFile(TOKEN_FILE, json=True, json_keys=("token",),
issued_at=("token","expiry"))`.

An oauth Claude entry would follow them: a `.credentials.json` entry with
`json=True`, `json_keys` naming `claudeAiOauth`, an `issued_at` path into the
nested expiry field, `sync_back=True`, and `required=True`. The `oauth-token`
entry with its `CLAUDE_CODE_OAUTH_TOKEN` delivery would either be dropped or
kept as a non-required alternative. `minimum_mode` is already `RW_NARROW`, so
the mount mode does not change; what changes is that the sync-back would
finally have a file to carry, which is the part that has never run for Claude.

**Whether `rw-narrow` handles the refresh correctly is therefore still
unproven for Claude**, and cannot be proven until the credential exists. The
mechanism is specified and exercised for Codex and AGY; for Claude it has
never had an input.

### Operator blocker: the Claude oauth login

This is the whole of what is needed. It can be acted on without reading
anything above.

**Command**

```sh
mkdir -p /home/scott/.local/state/foundry/crucible-credentials/claude_code_oauth
chmod 700 /home/scott/.local/state/foundry/crucible-credentials/claude_code_oauth

CLAUDE_CONFIG_DIR=/home/scott/.local/state/foundry/crucible-credentials/claude_code_oauth \
  claude auth login --claudeai
```

`claude auth login` is the subcommand that signs in to the Claude
subscription and writes a credentials file; `--claudeai` is its default and
is spelled out here so the Console variant, which bills API usage, cannot be
picked by accident. This is **not** `claude setup-token`, which is what S1b
ran and which produced the unreadable credential this spike is working
around.

**Target directory**

`/home/scott/.local/state/foundry/crucible-credentials/claude_code_oauth`,
created beforehand, owned by you, mode 0700. **A new directory, not the
existing `claude_code`.** Keeping them separate means the working setup-token
credential is not disturbed if the oauth login misbehaves, and it lets both
be compared. Promoting it to `claude_code` is a later, separate step.

**What you will see**

A device-code or browser prompt. Approve in a browser signed in to the
account Crucible should use, and paste the code back. On success the CLI
writes `.credentials.json` into that directory, mode 0600. Do not read it,
copy it, or paste its contents anywhere.

**What is needed back**

Only three things, none of them a value:

1. That the login completed, and the local time it completed.
2. That `<dir>/.credentials.json` exists, its size in bytes, and its mode.
3. Whether your own daily Claude session stayed signed in afterwards.

**What to watch for afterwards, which is the actual risk**

Point 3 is the finding, not the quota reading. This is FDY-0019 in another
form. S1b established that all three providers accepted a second
authenticated session on the same account while yours stayed valid, but it did
not establish whether a provider caps sessions or revokes the oldest. Watch
your own daily Claude session over the following hours and the next day for:
a sudden sign-out or a re-authentication prompt you did not trigger; a
session that works in one terminal and is signed out in another; or limits
that behave as though two sessions are drawing on one budget.

This spike has already produced the Codex answer to the same question, and it
is not the comfortable one: Crucible's dedicated Codex credential read
`exhausted_now` at 23:47 CDT on 2026-09-18, at the same time your own Codex
was out, on the same account and the same account-level weekly window. If
Claude behaves the same way, a dedicated Claude oauth session buys Crucible a
credential of its own but not a budget of its own. That is worth knowing
before the reader is adopted, and it is the reason this login is your
decision and not a provisioning step.

## `spendPriority`

**Recommendation: adopt it as the ranker where it is known, and do not
reconstruct it where it is not.** ADR 0014 currently ignores it entirely,
which is defensible for an ineligibility decision and wrong for a preference
decision.

Observed under Crucible's dedicated credentials:

| Provider / scope | `spendPriority` | Why |
|---|---|---|
| codex / all_models | `-1.0712` (drifting to `-1.0704` over eight minutes) | `selection.status: "known"`. Negative means overdrawn against the reset clock. |
| agy / gemini | `unknown` | `selection.unmeasurableWindowIds: ["gemini_weekly"]` |
| agy / claude_gpt | `unknown` | `selection.unmeasurableWindowIds: ["claude_gpt_5h","claude_gpt_weekly"]` |
| claude_code | absent | no reading at all |

So it is known for exactly one of three providers, and S14 saw the same.

The reason AGY comes back `unknown` is structural, not transient.
Antigravity's snapshot carries no cycle history, so pace cannot be computed
for any of its four windows, and `spendPriority` is derived from pace. The
`attention[]` rows name it precisely:
`gemini_5h + gemini_weekly blocks runway · gemini_weekly blocks spendPriority`.
Note that this run's detail string distinguishes the two windows for the
gemini scope, where S14's read `blocks runway + spendPriority` for both. The
field is not going to become known by waiting.

**Is it usable as the ranker given AGY's two overlapping windows?** Where it
is known it is already window-aware in the right way: it is computed for the
scope, and `selection.unmeasurableWindowIds` names which of the bounding
windows blocked it. AGY's two overlapping windows are not the reason it is
unknown; missing cycle history is. So the two-window structure does not
disqualify the field.

What disqualifies it as a **sole** ranker is coverage. A ranker that can only
order one of three providers cannot order the fleet. Firstmate's rule against
reconstructing it by hand from headroom and pace is the right rule and should
be adopted verbatim: where `selection.status` is not `known`, Crucible must
treat the provider as unranked, not synthesize a rank.

Concretely, for ADR 0014: store `spendPriority` and `selection.status` as
observed, use it to order candidates within the set of pools whose
`selection.status` is `known`, and fall back to the existing
least-recent rotation for the rest. Never let it make a pool ineligible.
`effectivePercentRemaining` and `runway` keep that job.

## Pool granularity

**Assessment: 05b's one pool per provider cannot represent what the vendors
bound, and the gap is already load-bearing.** This is an assessment with
evidence. 05b is untouched by this spike and the recommendation sits in the
amendment section below.

What the reader actually returns per provider under the dedicated
credentials:

| Provider | Scopes returned | Underlying windows |
|---|---|---|
| codex | `all_models` | `weekly` |
| agy | `gemini`, `claude_gpt` | `gemini_5h`, `gemini_weekly`, `claude_gpt_5h`, `claude_gpt_weekly` |
| claude_code | none observed | none observed |

Three distinct mismatches with `RoutingPolicyV1`.

1. **One provider, two disjoint allowances.** AGY returns two scopes that are
   not two views of one budget. `gemini` bounds the three `agy` models in
   `google-sub`. `claude_gpt` is Antigravity's own Claude and GPT allowance
   and bounds no 05b pool at all. A single `google-sub` pool per provider has
   no place to put the second scope, and the one pair of names that looks
   like a match, `claude_gpt` and `anthropic-sub`, is the pair that is wrong.
2. **The declared window and the observed window disagree.** `openai-sub`
   declares `window: "5h"`. The only window Codex reported, and the window
   that actually exhausted, is `weekly`. A pool that names its own window
   cannot carry an observation about a different one.
3. **Per-model exhaustion inside a per-account pool.** This is the one the
   C6 worker's termination demonstrated. `anthropic-sub` covers
   `claude-haiku-4-5`, `claude-sonnet-5` and `claude-fable-5-1` together, and
   what actually happened is that Fable 5.1 credit exhausted while Opus
   continued on the same account: the refusal named the model and offered a
   model switch. The pool model says all three are exhausted together. They
   were not. The reader already reports at the finer granularity, with
   `all_models`, `seven_day_opus` and `model:fable` as distinct scopes, so
   the granularity exists in the instrument; it is missing in the schema.

Note that Codex, on the credential Crucible actually holds, reported only
`all_models`. The per-model scopes are a documented capability of the reader
that this run did not itself observe, since only a Claude oauth credential
would show them and there is none. That part rests on the operator's own
account observation on 2026-09-18, not on a reading taken here.

**What a pool would have to become for an ineligibility decision to be
correct: a pool that carries both bounds.** Not a scope-aware pool alone, and
not a pool per model.

- A **scope-aware pool** fixes AGY's two disjoint allowances and mismatch 2,
  by letting a pool declare which provider and scope bounds it and letting
  the observation carry its own window identity. It does not fix mismatch 3,
  because `model:fable` and `all_models` bound the same models at the same
  time.
- A **pool per model** fixes mismatch 3 and breaks rotation: the account-level
  bound would have to be duplicated across every model in the account, and
  nothing would represent the fact that spending on one drains the others.
- A **pool that carries both bounds** is the only shape that is correct. A
  pool keeps its account-level bound, observed from the account-wide scope,
  and additionally carries per-model bounds observed from model scopes. A
  model is ineligible if either bound is exhausted. Eligibility requires
  both. That is exactly what the vendors do, and it is why the C6 worker
  could be refused for Fable and keep working on Opus in the same minute.

This is a schema change to 05b and a change to how `GET /routing/usage`
reports, and it is larger than adopting the reader. It should be sequenced
after ADR 0014, not folded into it, and ADR 0014 should state that its
ineligibility rule is correct only for the account-level bound until 05b
carries the second one.

## Proposed amendment to ADR 0014

Written as a clearly marked amendment rather than a rewrite, because ADR 0014
lives on the unmerged branch `spike/s14-quota` (PR #29) and is `proposed`.
Whether Crucible adopts the reader remains the operator's decision and this
spike does not presume it. If #29 lands first, this section becomes the edit
to make; if S15 lands first, it is the standing proposal.

### Amendment A, AGY scope named explicitly

In the pool-mapping decision bullet, name the scope: the observation that
bounds `google-sub` is **`agy` / `gemini`**, and no other. AGY's `claude_gpt`
scope bounds no 05b pool, must never be mapped to `anthropic-sub` or
`openai-sub`, and should be recorded as an observation with no pool rather
than dropped, so that a later mapping has history.

### Amendment B, why `effectivePercentRemaining` is sufficient alone

State the semantics the ADR currently relies on implicitly:
`effectivePercentRemaining` is the **minimum across the windows jointly
bounding the scope**, listed in `boundedBy`, and `limitedBy` names the window
or windows currently binding, joined with `+` when tied. Because it is
already a minimum over every bounding window, it is sufficient on its own for
an ineligibility decision, and Crucible never needs to inspect the individual
windows to make one. This is what makes the one-field rule safe.

### Amendment C, the read-only mount premise is false as shipped

ADR 0014 states the credential directories are "mounted read-only (12)" and
that the mount "would also stop any write the tool attempted". As shipped,
`compose.yaml` mounts only the `github` directory `:ro`; all three harness
directories are writable, because spec 12's `rw-narrow` sync-back requires
it. The ADR must either say the reader gets its own read-only mount of the
same directories, separate from the writable one the sync-back uses, or drop
the claim. S15 proves the reader works against a read-only mount for Codex,
so the separate read-only mount is achievable and is the recommended shape.

### Amendment D, `--no-credential-refresh` is mandatory, not optional

Add it to the invocation contract alongside `--profile-only` and the
sanitized environment. Without it the AGY path rewrote the dedicated
credential within two seconds of a read and the `agy` CLI it launched
self-updated in place, which ADR 0011 exists to prevent. With it the reading
was identical, the credential was untouched and the updater did not run,
though the CLI still wrote a log into the credential directory. A quota read
must never rotate a credential or upgrade a CLI. The flag is necessary and
not sufficient: the read-only mount of Amendment C is what keeps the rest of
the directory clean.

### Amendment E, observe Codex, leave AGY off by default

S15 confirms the cost ADR 0014 names. AGY cannot be read in the shipped
service image at all, and making it readable means a 224 MB self-updating
harness CLI in the process that holds every credential. Recommend the ADR
adopt Codex observation now, record AGY as specified but disabled, and make
enabling it an explicit operator decision with its own checkpoint. Claude
stays unobserved until the credential shape changes, unchanged from ADR 0014.

### Amendment F, the AGY source cannot be discriminated today

ADR 0014 requires discarding an AGY reading whose source is the loopback
fallback. No field in `schemaVersion: 5` output identifies the source of a
given quota row, and `quota-axi auth --json` does not answer it either. Until
the tool exposes one, the rule is unenforceable, and the ADR should say so
and name the substitute: the service container has its own process namespace
and no Antigravity process, so the loopback fallback cannot find one to read.
That is a structural guarantee rather than a check, and it must be stated as
a deployment requirement, not assumed.

### Amendment G, do not gate on `confidence`

The one `exhausted_now` reading ever captured carried
`confidence: "unknown"`. Ineligibility keys on `runway == "exhausted_now"`
or `effectivePercentRemaining == 0`. `confidence` is stored and reported and
gates nothing.

### Amendment H, pool granularity

Record that the ADR's ineligibility rule is correct for a pool's
account-level bound only. A provider that bounds per model as well as per
account, which Claude demonstrably does, needs a pool that carries both
bounds, where a model is ineligible if either is exhausted. Sequence that as
a 05b change after this ADR, and state the limitation in the ADR rather than
leaving it implied.

### Amendment I, the checkpoint is met for Codex

ADR 0014 makes the first real `exhausted_now` a recorded checkpoint before
the signal may refuse a launch. S15 records it: Codex, `all_models`,
`weekly`, 2026-09-18 23:47:05 CDT, reproduced in the container at 23:48:29
and 23:51:26 CDT. The checkpoint is met for Codex and unmet for AGY and
Claude, neither of which has ever produced one.

## What remains unproven

- **The refill.** The Codex window resets at 10:57 CDT on 2026-09-19, after
  this run. What the tool reports as a window refills is still unobserved.
- **Claude, entirely.** No reading has ever been taken. Blocked on the
  operator login above.
- **`rw-narrow` sync-back for Claude.** Specified, never exercised, and
  cannot be until the oauth credential exists.
- **Per-model scopes as read by this tool.** `seven_day_opus` and
  `model:fable` were not observed here; only Codex's `all_models` was.
- **That the reader leaves the operator's daily files untouched, re-verified
  on the host.** Deliberately not re-run, for the contract reason stated
  above. S14's evidence stands.
- **Whether a second Claude oauth session disturbs the daily one.** The
  question the blocker exists to answer.
- **The reader in the image as it will actually ship.** Node was bind-mounted
  for this spike. Whether a pinned node and the pinned reader can be added to
  the service image within ADR 0011's scheme is an open build question.
