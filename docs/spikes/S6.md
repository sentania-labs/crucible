# S6: Which egress endpoints does each harness need?

Run 2026-09-16, 14:02 to 14:20 CDT, rootful Docker 28.3.1, spec 08 worker
shape on an `internal: true` network (`crucible-s6-internal`,
`10.10.24.0/24`) with a logging CONNECT proxy as the only way out.

Decision: **adjust design.** All three allowlists are provisional. The
Claude Code list comes from an authenticated run that discovered its
destinations through a logging proxy with no filter; no run has yet
completed a task with only `api.anthropic.com` permitted. Two points stay
open for it: whether the CLI tolerates the Datadog intake being refused by
the filter (untested), and `mcp-proxy.anthropic.com`, which was observed
on every authenticated run because the operator's account has connectors
(a template configuration without them has not been run). The Codex and
AGY lists are from unauthenticated runs plus the CLI logs of their one
authenticated run each (S1), because both CLIs refreshed their OAuth token
on their own and the task contract stops authenticated runs at that point.
Completion condition for all three: one authenticated run per harness that
succeeds through the actual allowlist filter in C3. `network: none` was
run for Claude Code only: it fails, slowly.

## The proxy

tinyproxy 1.11.1 from Debian bookworm in a throwaway image (base pinned by
digest, removed afterwards), on the bridge network and connected to the
internal one, config:

```
Port 3128
Listen 0.0.0.0
LogLevel Connect
Allow 0.0.0.0/0
ConnectPort 443
DisableViaHeader Yes
# allowlist variant adds:
Filter "/etc/tinyproxy/filter"
FilterDefaultDeny Yes
FilterType fnmatch
```

Run with `-d` (foreground) and no `LogFile`, it logs to stdout, which is
the requirement spec 13 records against `ubuntu/squid` (S9). `LogFile
"/dev/stdout"` does not work (`The file /dev/stdout has been changed before
it could be opened`, a symlink check). Each CONNECT logs `Request ...
CONNECT host:443` and `Established connection to host "..."`; a filtered
host gets `Request` but no `Established`, and the client sees the
connection close (`curl: http=000`), not a 403. Workers got
`HTTPS_PROXY=http://s6-proxy:3128`, `HTTP_PROXY=http://s6-proxy:3128` and
`NO_PROXY=localhost,127.0.0.1`; the internal network's embedded DNS resolves
the proxy name. All three CLIs honored the proxy variables without any
other setting.

## Hostnames per harness

Counts are CONNECT requests in the proxy log for that one run.

### Claude Code, authenticated trivial prompt (rw-narrow, S1 shape)

| Host | CONNECTs | What |
|---|---|---|
| `api.anthropic.com` | 26 | model API, OAuth-authenticated; also the org skill and plugin sync seen in S1 |
| `mcp-proxy.anthropic.com` | 2 | the two claude.ai MCP connectors on the operator's account (the CLI opened them although the prompt used no tool) |
| `http-intake.logs.us5.datadoghq.com` | 1 | CLI telemetry |

`claude --version` and `claude update` contacted nothing (S11). An
unauthenticated run contacted `api.anthropic.com` only (4 CONNECTs).

Allowlist (provisional): `api.anthropic.com`. Optional:
`mcp-proxy.anthropic.com` if an attempt is meant to use account connectors
(Crucible's template configuration should not enable them; whether the CLI
still contacts the host without them is unobserved). Deny: the Datadog
intake (telemetry; whether the CLI tolerates the refusal is untested). The
list is promoted when an authenticated run completes a task with only
`api.anthropic.com` permitted by the filter.

### Codex, unauthenticated `codex exec` (the same launch line as S1)

| Host | CONNECTs | With `--disable plugins` | What |
|---|---|---|---|
| `api.openai.com` | 13 | 13 | model API: websocket `/v1/responses` first, then the https fallback, with reconnect attempts on each transport and a final failing request (S5); the CONNECT count includes the initial attempt on each transport, so it is above the ten "Reconnecting" lines |
| `chatgpt.com` | 1 | 0 | plugin marketplace sync (`plugins/cache/openai-curated-remote`, S1) |
| `ab.chatgpt.com` | 1 | 0 | experiments, same sync |
| `github.com` | 2 | 0 | the remote plugin repository, same sync |

The `check_for_update_on_startup=false` opt-out made no difference to this
list (identical with and without it); the github.com contacts are plugin
sync, not the update check, and `--disable plugins` removes all three
non-API hosts. `codex --version` and `codex update` contacted nothing.

From the authenticated S1 run (no proxy, so no CONNECT log): the CLI
refreshed its ChatGPT OAuth token at start. The static strings in the
binary name `auth.openai.com` as the OAuth endpoint and `chatgpt.com` for
the ChatGPT backend; the S1 run used `auth_mode = chatgpt`.

Allowlist (provisional): `api.openai.com`, `auth.openai.com`, and
`chatgpt.com` only if the authenticated re-run shows the ChatGPT-plan
backend needs it. Deny: `ab.chatgpt.com`, `github.com`. Adapter launch line
gains `--disable plugins`.

### AGY, unauthenticated `agy -p`

| Host | CONNECTs | What |
|---|---|---|
| `antigravity-unleash.goog` | 2 | feature flags (Unleash) |
| `play.googleapis.com` | 1 | Google client telemetry / experiments |
| `playwright.azureedge.net` | 1 | Playwright browser download check (the CLI ships browser tools; the static strings also name `playwright-akamai` and `playwright-verizon` mirrors) |

`agy --version` and `agy update` contacted nothing (`update` fails on the
read-only `/usr/local/bin` before any request). From the authenticated S1
run's own log (no proxy): `daily-cloudcode-pa.googleapis.com` is the model
and code-assist API (7 references), and the token refresh is a Google OAuth
refresh grant, which the binary's strings place at `oauth2.googleapis.com`
(login itself is `accounts.google.com`, interactive only).

Allowlist (provisional): `daily-cloudcode-pa.googleapis.com`,
`oauth2.googleapis.com`. To be decided by the authenticated re-run whether
the CLI tolerates `antigravity-unleash.goog` and `play.googleapis.com` being
refused (unauthenticated it did; the failures were logged and the run went
on to the auth error). Deny: the Playwright CDN.

## Consequences

- Spec 13: the pinned egress proxy can be tinyproxy from the Debian
  snapshot the images already use, or squid logging to a file that the
  entrypoint tails; either meets "logs to stdout". tinyproxy's filter
  refuses by closing the connection, which every CLI treated as a
  connection error and retried or failed cleanly.
- Spec 07: adapters declare model endpoints as above; Codex adds
  `--disable plugins`; the Claude Code template configuration carries no
  MCP servers so `mcp-proxy` is not needed.
- Follow-up: one authenticated run per harness that succeeds through the
  actual allowlist filter, to promote all three lists from provisional,
  after the credential finding in the task report is handled.
