# S9: dedicated rootless Docker daemon for Crucible

Result: **pass**. Decision: the dedicated rootless daemon for the `crucible`
service user is the default local arrangement from C3, per ADR 0004 and
operator decision 13. The daemon is left installed and running on the
development workstation.

Run on 2026-09-16 (America/Chicago) on the development workstation:
Ubuntu 24.04.5, kernel 6.8.0-139, cgroup v2, rootful Docker 28.3.1 already
present and untouched.

## Question

Can a rootless Docker daemon owned by a service user run the hardened worker
container shape from spec 08, an `internal: true` network, and a CONNECT
egress proxy, and sit behind `docker-socket-proxy`, with acceptable
performance next to the rootful daemon? (spec 21, S9; spec 13, "Docker
authority, stated honestly")

## Host changes made, with reversal

Every change is one of the items the task contract allows. No sysctl,
AppArmor profile, firewall rule, or rootful daemon setting was changed; the
values of `kernel.unprivileged_userns_clone`,
`kernel.apparmor_restrict_unprivileged_userns`,
`net.ipv4.ip_unprivileged_port_start`, `user.max_user_namespaces`, and
`net.ipv4.ip_forward` were checked before and after and are identical.

| # | Change | Command run | Reversal |
|---|---|---|---|
| 1 | Install `uidmap` 1:4.13+dfsg1-4ubuntu3.2 | `sudo apt-get install -y uidmap` | `sudo apt-get remove -y uidmap` |
| 2 | Create service user `crucible` (uid 999, gid 999, no login shell) | `sudo useradd --system --create-home --home-dir /var/lib/crucible-docker --shell /usr/sbin/nologin --comment 'Crucible rootless Docker' crucible` | `sudo userdel -r crucible` (removes the home, the daemon's image store under it, and the subordinate ID entries) |
| 3 | Give the user a subordinate ID range (system uids get none from `useradd`) | `sudo usermod --add-subuids 493216-558751 --add-subgids 493216-558751 crucible` | `sudo usermod --del-subuids 493216-558751 --del-subgids 493216-558751 crucible` (also covered by the `userdel` above) |
| 4 | Enable lingering so the user manager and the daemon run without a login | `sudo loginctl enable-linger crucible` | `sudo loginctl disable-linger crucible` |
| 5 | Install and enable the rootless daemon as the user | `sudo -u crucible -H env HOME=/var/lib/crucible-docker XDG_RUNTIME_DIR=/run/user/999 DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/999/bus PATH=/usr/bin:/bin:/usr/sbin:/sbin dockerd-rootless-setuptool.sh install` | same environment, `dockerd-rootless-setuptool.sh uninstall`, then `rootlesskit rm -rf /var/lib/crucible-docker/.local/share/docker` |

Nothing in the setup asked for a change outside this list. The setup tool's
own preflight (`rootlesskit true`) passed without the `--force` flag.

Reversal order matters: 5, 4, 3, 2, 1. `userdel -r` fails while the user's
systemd manager is running, so after step 4's reversal also run
`sudo loginctl terminate-user crucible` (or `sudo systemctl stop
user@999.service`) and wait for it to exit before step 2's reversal. The
uid 999 was assigned by `useradd --system` and will differ on another host;
every path below that contains `999` should be derived from `id -u crucible`.

Test-only artifacts created and removed during the spike: containers
`s9-worker-a1..a3`, `s9-egress`, `s9-sockproxy`, network
`crucible-s9-internal` (rootless), network `crucible-s9-internal-rootful`
and one image pull (`ubuntu/squid` by digest) on the rootful daemon for the
timing comparison, and `/var/lib/crucible-docker/s9/squid.conf`. All were
removed at the end; the rootful daemon's container and network lists match
the pre-spike baseline.

## Test A: hardened worker shape and limit enforcement

Shape used (spec 08 `launch`, without the repo, identity, credential, and
report mounts, which are plain bind mounts and not what this spike tests):

```
docker run --rm --user 1000:1000 --cap-drop ALL --security-opt no-new-privileges \
  --read-only --tmpfs /tmp:rw,noexec,nosuid,size=512m \
  --memory 256m --memory-swap 256m --pids-limit 64 \
  --network crucible-s9-internal debian@sha256:88200866... bash -c '...'
```

A second run added the remaining spec 08 items, `--tmpfs
/home/worker:rw,noexec,nosuid,size=64m` and `--cpus 1.5`, and observed
`cpu.max=150000 100000` inside the container and a writable tmpfs at
`/home/worker`, so the CPU quota is enforced through the delegated `cpu`
controller as well.

Observed from inside the container:

```
uid=1000 gid=1000 groups=1000
caps: CapEff: 0000000000000000
nnp: NoNewPrivs: 1
memory.max=268435456 memory.swap.max=0 pids.max=64
rootfs-write: touch: cannot touch '/x': Read-only file system
overlay on / type overlay (ro,...)
tmpfs on /tmp type tmpfs (rw,nosuid,nodev,noexec,relatime,size=524288k,uid=999,gid=999)
```

Memory enforcement: writing 400 MiB into the tmpfs under the 256 MiB limit
(tmpfs pages are charged to the cgroup and cannot be reclaimed) killed the
container: exit 137, `OOMKilled=true`.

Pids enforcement: a loop of 100 `(sleep 20 &)` under `--pids-limit 64`
produced `fork: retry: Resource temporarily unavailable`, and one second
after the loop `pids.events` read `max 8` (eight forks refused at the
limit) with `pids.current=39`. The counts do not sum to 100 because each
iteration's subshell exits as soon as it has backgrounded its `sleep`, so
the live process count rises and falls during the loop; the `max` counter
only increments when a fork is actually refused, and that is the
enforcement evidence.

Both limits are enforced through cgroup v2 delegation without any host
configuration beyond the defaults.

## Test B: internal network, egress only through the CONNECT proxy

```
docker network create --internal crucible-s9-internal      # 172.18.0.0/16, Internal=true
docker run -d --name s9-egress --network bridge \
  -v .../squid.conf:/etc/squid/squid.conf:ro ubuntu/squid@sha256:6a097f68...
docker network connect crucible-s9-internal s9-egress      # bridge=172.17.0.3 internal=172.18.0.2
```

Squid config used for the test (CONNECT only to port 443, destination
`github.com` only, no cache). It is a spike config, not the C3 one: the
`localnet` source ACL admits the whole 172.16/12 range, so the daemon's
default bridge would also be accepted, and there is no `deny !Safe_ports`
line, so a plain-HTTP `GET` to `github.com` on any port would also be
allowed. C3's config restricts the source to the workers network's subnet,
denies non-safe ports and non-CONNECT methods, and takes its `dstdomain`
list from the policy (spec 13).

```
acl localnet src 172.16.0.0/12
acl SSL_ports port 443
acl CONNECT method CONNECT
acl allowed dstdomain github.com
http_access deny CONNECT !SSL_ports
http_access allow localnet allowed
http_access deny all
http_port 3128
cache deny all
access_log /var/log/squid/access.log
pid_filename none
```

Worker runs (hardened shape, `--network crucible-s9-internal`, curl
image as the client):

| Case | Command (abridged) | Result |
|---|---|---|
| B1 direct to github by IP | `curl https://140.82.112.3/` | `curl: (7) Failed to connect ... Could not connect to server` (no route off the internal network) |
| B2 direct by name | `curl https://github.com/` | `curl: (6) Could not resolve host: github.com` (no external resolver on the internal network) |
| B3 through proxy | `-e HTTPS_PROXY=http://s9-egress:3128 curl https://github.com/` | `http=200 proxy_used=1` |
| B4 through proxy, host not allowlisted | `-e HTTPS_PROXY=http://s9-egress:3128 curl https://example.com/` | `curl: (56) CONNECT tunnel failed, response 403` |
| B5 internal gateway address from worker | `curl http://172.18.0.1:3128/` | no response within the 5 s timeout (`http=000`) |

Squid access log:

```
TCP_TUNNEL/200 CONNECT github.com:443
TCP_DENIED/403 CONNECT example.com:443
```

One image quirk worth recording for C3: `ubuntu/squid` drops to user
`proxy` before opening logs, so `access_log stdio:/dev/stdout` fails with
`FATAL: Cannot open '/dev/stdout' for writing` and the container exits 1.
Its entrypoint already tails `/var/log/squid/access.log` to the container
log, so the config should log there. Name resolution of the proxy
(`s9-egress`) from the worker works because the internal network is a
user-defined network with Docker's embedded DNS; the default `bridge`
network would not resolve it.

## Test C: timings, rootless versus rootful

Same host, same images by digest, same hardened flags, sequential runs in
the same minute. Pulls come from Docker Hub over the workstation's uplink;
the rootless daemon had never seen the blobs, the rootful daemon already had
`debian:bookworm-slim` so only the squid image could be compared there
(pulled onto rootful for this measurement and removed after).

| Measurement | Rootless | Rootful |
|---|---|---|
| pull `debian:bookworm-slim` by digest (74.8 MB) | 2.13 s | not comparable (already present; no-op pull 0.17 s) |
| pull `ubuntu/squid` by digest (205 MB) | 3.70 s | 3.49 s |
| pull `docker-socket-proxy` by digest (43.5 MB) | 2.05 s | not measured |
| no-op pull of a present image | 0.20 s | 0.17 s |
| `docker run --rm ... true`, hardened shape on an internal network, 5 runs | 0.41, 0.39, 0.36, 0.38, 0.38 s | 0.59, 0.38, 1.24, 0.37, 0.40 s |
| 100 MiB `dd bs=1M conv=fsync` to tmpfs `/tmp`, 3 runs | 1.6, 3.2, 4.2 GB/s | 3.6, 4.0, 2.5 GB/s |
| 100 MiB `dd bs=1M conv=fsync` to the container overlay (rw root), 3 runs | 216, 341, 280 MB/s | 283, 226, 309 MB/s |

Container start and both write paths are within run-to-run noise of
rootful. The 205 MB pull was 6 percent slower on rootless in a single
sample; that is the size of the slirp4netns user-mode networking cost one
would expect, and it is acceptable for worker image pulls, which happen
once per image digest. Network throughput for workers matters less because
worker egress goes through the proxy and is model API traffic, not bulk.

Image build time was not measured. The spec 21 method mentions build and
start times, but builds never run through the socket proxy (`BUILD=0` in
spec 13) and S7 owns the worker image builds; a build on the rootless daemon
exercises the same overlay2 write path measured above.

## Test D: docker-socket-proxy against the rootless socket

```
docker run -d --name s9-sockproxy \
  -e CONTAINERS=1 -e IMAGES=1 -e NETWORKS=1 -e VOLUMES=1 -e POST=1 \
  -e EXEC=0 -e BUILD=0 -e SWARM=0 -e SYSTEM=0 -e PLUGINS=0 -e SECRETS=0 -e CONFIGS=0 \
  -v /run/user/999/docker.sock:/var/run/docker.sock:ro \
  -p 127.0.0.1:23750:2375 tecnativa/docker-socket-proxy@sha256:1f5038b5...
```

Mounting the rootless socket into a container on that same daemon works
(rootlesskit copies `/run` up into its mount namespace). Publishing to
loopback on an unprivileged port works through the builtin port driver.

The loopback publish was a test convenience so the requests could be sent
from the host, and it widens the blast radius while it exists: any local
user who can reach `127.0.0.1:23750` can create containers on the daemon
with `CONTAINERS=1 POST=1`, including binds under
`/var/lib/crucible-docker`, and the socket's `0660` mode does not help. In
normal mode (spec 13) the proxy is reachable only on the Compose internal
network and publishes nothing; developer mode publishes it on loopback and
carries exactly this exposure, which the readiness report should name.

From the host, as a different user with no access to the socket itself:

| Request | Result |
|---|---|
| `GET /v1.51/containers/json` | 200, lists `s9-sockproxy` |
| `POST /v1.51/containers/{id}/exec` (create an exec instance) | **201** |
| `POST /v1.51/exec/{id}/start` | 403 |
| `GET /v1.51/exec/{id}/json` | 403 |
| `GET /v1.51/info` | 403 |
| `POST /v1.51/build` | 403 |
| `ls -l /run/user/999/docker.sock` as another user | Permission denied |

Finding for spec 13: with this image, `EXEC=0` does not block
`POST /containers/{id}/exec`. The relevant rules in the image's
`haproxy.cfg`, in evaluation order:

```
http-request allow if { path,url_dec -m reg -i ^(/v[\d\.]+)?/containers } { env(CONTAINERS) -m bool }
http-request allow if { path,url_dec -m reg -i ^(/v[\d\.]+)?/exec } { env(EXEC) -m bool }
```

Any path under `/containers` is allowed once `CONTAINERS=1`, and the `EXEC`
flag only guards `/exec/...`. So an exec instance can be created but never
started or inspected; no command runs. The spec's phrase
"disables `exec`" is true in effect but not at the endpoint level. The
create-request policy in Crucible (spec 13) already never emits exec
requests, and the isolation test in 18 should include a
`POST /containers/{id}/exec` followed by `/exec/{id}/start` and assert the
403 on start.

## Unit restart

`systemctl --user restart docker.service` as `crucible` returned the daemon
to `active` in under 4 seconds with the same security options; `NRestarts=0`
before the deliberate restart (no crashes during the spike). Lingering is
enabled and the unit is enabled in the user manager, so it starts at boot
without a login. A reboot was not performed.

## Decision

Pass. Rootless Docker for a dedicated service user is the default local
arrangement from C3 (spec 13 arrangement 1, ADR 0004 item 1). The
fallback in ADR 0004 item 2 is not needed on this workstation.

Concretely for C3:

- Compose's `docker-socket-proxy` service mounts
  `/run/user/$(id -u crucible)/docker.sock` (999 on this workstation); the
  Compose project itself runs on the rootless daemon (`DOCKER_HOST` set to
  that socket for the operator's `docker compose` calls, or the `rootless`
  context). The proxy publishes no port in normal mode.
- `postgres` and `crucible` volumes live under
  `/var/lib/crucible-docker/.local/share/docker/volumes`.
- The developer-mode published ports must be above 1024 (already the
  case for the proxy on loopback).

## Limitations

- Measured once, on one workstation, on a warm Docker Hub. Pull numbers
  are indicative, not benchmarks.
- No reboot test of lingering plus the enabled unit; it follows from the
  systemd configuration but was not exercised.
- `io` and `cpuset` controllers are not delegated to user managers by
  default, so per-container block I/O limits and CPU pinning are not
  available on the rootless daemon. The policy in 05b does not use them.
- The socket-proxy test used the current image tag's digest; the exec
  finding above is specific to that image's rule ordering and should be
  rechecked when the pinned digest changes.
- The service user has no login shell. Operating the daemon means either
  `sudo systemctl --user -M crucible@ ...` or `sudo -u crucible -H env
  XDG_RUNTIME_DIR=/run/user/999 DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/999/bus
  DOCKER_HOST=unix:///run/user/999/docker.sock docker ...`. A small
  wrapper for the operator belongs in C3, not here.

## Risks

- The rootless daemon's image store and volumes sit under the user's home
  at `/var/lib/crucible-docker`. Removing the user with `userdel -r`
  deletes Crucible's Postgres volume. Backups (spec 13, later phases) must
  account for the path.
- Anything running as `crucible` on the host is root inside that daemon's
  namespace and owns every Crucible container and volume. That is the
  intended blast radius: one unprivileged user, not the host.
- slirp4netns adds CPU cost per byte of container egress. Not visible at
  spike scale; worth a glance if a worker ever pulls large artifacts.
- The `jammy` build of `docker-ce-rootless-extras` is installed on a
  `noble` host (the apt source pins the jammy channel). It works, and it
  ships the AppArmor profile 24.04 needs, but a future package upgrade that
  drops or renames `/etc/apparmor.d/rootlesskit` would stop the daemon from
  starting after reboot. Add a check to the C3 `make up` preflight.

## Follow-ups

1. C3: Compose and Makefile target the rootless daemon; add a preflight
   that checks the socket, the AppArmor profile, and the delegated
   controllers, and fails with a clear message.
2. Spec 13 and ADR 0004: reword "disables `exec`" to "exec cannot be
   started or inspected"; the isolation test in 18 asserts the 403 on
   `/exec/{id}/start`.
3. Spec 13 egress proxy: pin `ubuntu/squid` by the digest above (or another
   image after S6) and log to `/var/log/squid/access.log`, not stdout.
4. Operator wrapper for running `docker` against the rootless daemon
   without retyping the environment.
5. Reboot verification of lingering and the enabled unit the next time
   the workstation restarts for another reason.
