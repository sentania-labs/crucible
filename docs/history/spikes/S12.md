# S12: what the external reviewer emits on a PR, under which login, and how it is triggered

Result: **pass with a design correction**, on the second run. Decision:
adjust spec 23 and 05b before C1, and add a repository-onboarding
prerequisite. With the repository configured so Codex reviews all pull
requests, a PR opened by the App (`crucible-spike[bot]`) **was** reviewed
automatically, in 101 seconds, with no human in the thread. The reviewer
login default is confirmed. On the **automatic** trigger a clean review
emitted no review object and no comment at all: an `eyes` reaction on the
pull request on pickup, a `+1` reaction on completion, and the `eyes`
deleted. (A clean review triggered by a human `@codex review` on the same
repository two hours earlier came back as issue comments and no reaction,
so the shape depends on the trigger; both are recorded below.) That `+1`
is the one object the App's permission set cannot read:
`GET /issues/{n}/reactions` is 403 without Issues read, so across the 30
minute rerun Crucible's observer recorded zero reviewer signals while the
operator's `gh` recorded the entire lifecycle. Issues read is no longer
optional.

The trigger is a per-repository setting inside the Codex product. Nothing
on the GitHub side, not the installation, the repository object, a ruleset,
an environment or a variable, reflects it, so Crucible cannot check it and
must treat it as an onboarding prerequisite.

**Run 1 of this spike, at 14:27 CDT, is superseded.** It concluded that the
reviewer is triggered by the identity of the PR author and that an App
author is never reviewed. That conclusion was not supported: neither run 1
nor the `@codex review` follow-up ever inspected the throwaway repository's
automatic-review setting, and the human-authored PRs it was compared
against were in a different repository, so author identity was never
isolated from repository configuration. The rerun below changes the
setting and reverses the result. It is not a clean single-variable
experiment either, and this file will not repeat run 1's mistake by
claiming it is: the rerun's PR also carries a small Python file that run
1's PR did not, so "the repository is configured for all PRs" and "the PR
contains reviewable code" both changed. The second is an alternative
explanation the rerun does not exclude. Run 1's endpoint and permission
evidence stands; its trigger finding does not.

## Question

What does the configured external reviewer actually emit on a PR, under
which login, and how does it get triggered? (spec 21, S12; spec 23
"External review"; 05b `external_review` defaults)

### The ten questions

1. **Does the all-PRs setting cause a review of an App-authored PR?**
   Yes. Reaction `eyes` id 510060508 at 16:16:43, 11 s after PR #6 opened,
   and reaction `+1` id 510063292 at 16:18:13, 101 s after, both from
   `chatgpt-codex-connector[bot]` on a PR whose author is
   `crucible-spike[bot]`, with no `@codex review` anywhere in the thread.
   Run 1's conclusion that author identity blocks the reviewer is wrong.
2. **Are code review and security review both triggered automatically?**
   Not separable from the GitHub record. One `eyes` and one `+1` arrived,
   with no comment, no review, and no check run, so nothing distinguishes a
   code-review pass from a security pass. The operator's statement that
   both are enabled is the only evidence that two ran; GitHub shows one
   acknowledgement and one verdict.
3. **Which GitHub objects represent each review?** On this clean run, only
   reactions on the pull request itself, `GET /repos/{o}/{r}/issues/{n}/reactions`
   (GraphQL `pullRequest.reactions`). No review object, no review comment,
   no issue comment, no check run, no check suite, no status.
4. **Which bot login emits each?** `chatgpt-codex-connector[bot]`,
   `user.type: Bot`, for both reactions. Unchanged from run 1 and from the
   live record: the 05b default `reviewer_logins:
   ["chatgpt-codex-connector[bot]"]` holds.
5. **Is the summary comment edited in place?** No summary comment was
   emitted on PR #6 at all, so there was nothing to edit. The observer now
   re-emits an object whenever its body hash or `updated_at` changes, and it
   recorded no such change. Where a summary comment does appear, the live
   record on `crucible` shows it edited in place, so the polling
   requirement stands; it simply does not apply to this shape of result.
6. **What does a clean result produce?** A two-step reaction sequence on
   the PR and nothing else: `eyes` on pickup, then `+1` on completion, with
   the `eyes` **deleted** when the `+1` lands (present at the 16:18:13
   poll, absent at 16:19:15). No thumbs-up on a comment, no review object,
   no updated summary. This is the first time the "no findings" thumbs-up
   has been observed directly; run 1 and the live record both left it
   resting on provider documentation.
7. **Which SHA does each review cover?** Unknowable from this run. A
   reaction carries no `commit_id` and no `content` beyond the emoji, so
   the only SHA association is "the PR's head at the time the reaction was
   created", which is an inference, not a field. Where a review object
   exists it carries `commit_id`, and the review body repeats it; a
   reaction does not.
8. **Can Crucible observe every required signal with the App's current
   permissions?** No, and on this run it observed **nothing**. The App
   token's poll of `GET /issues/{n}/reactions` returned 403 "Resource not
   accessible by integration" on every cycle, `X-Accepted-GitHub-Permissions:
   issues=read`. Every other endpoint returned 200 and every one of them was
   empty. The App-side observer recorded zero actor signals across 30
   minutes while the operator's `gh` saw the whole lifecycle.
9. **Is Issues read still necessary, and for what exactly?** Yes, and it is
   now load-bearing rather than a corner case. It is needed for exactly one
   call, `GET /repos/{o}/{r}/issues/{n}/reactions`, which is the only place
   a clean Codex result appears. `GET /issues/{n}/comments` and
   `GET /issues/comments/{id}/reactions` both returned 200 with Pull
   requests read alone, so Issues read is not needed for the comment path.
10. **Does polling alone observe the complete lifecycle?** No. GitHub emits
    no webhook for reactions, so polling is the only path, and polling
    cannot see a signal that was created and deleted between two cycles.
    The `eyes` reaction existed for at least 90 seconds (its `created_at`
    to the `+1`'s) and at most 152 (to the first poll that did not see it);
    at spec 23's default `poll_interval_seconds: 120` a cycle can miss it
    entirely. The `+1` persists, so the verdict survives any interval, but
    the "review in progress" state does not.
    Polling also cannot tell a deleted reaction from one that never
    existed: the observer sees a set shrink, with no actor and no timestamp
    for the deletion.

### The retrigger check on a corrected head

A second commit was pushed to the same branch by the same publisher at
16:47:53 CDT, moving PR #6's head from `2d345a1c` to `e00fb112`. The new
file contains an obvious bug (`values[len(values)]`, an index one past the
end), so there was something worth a finding this time. Both identities
then observed for a further 15 minutes: the App's observer from 16:48:31 to
17:03:35 CDT, 28 cycles at 30 s, and the operator's `gh` reaction poll from
16:48:32 to 17:02:55 CDT, 15 cycles at 60 s.

**No review re-triggered.** At 17:03 CDT the PR carries: 0 reviews, 0 review
comments, 0 issue comments, 0 check runs on the new head, and exactly one
reaction, the same `+1` id 510063292 created at 16:18:13 CDT against the
**previous** head. No new `eyes`, no new `+1`, no deletion. The only new
objects on the new head were the PR head change itself and another queued
`claude` check suite (95206977264).

For spec 23 this means `retrigger_after_correction: false` is the behavior
the provider gives by default: a corrected head is not reviewed again, and
the surviving `+1` still names no SHA, so a stale accepted signal from an
earlier head is indistinguishable from a fresh one. Two consequences:

- `require_review_on_final_sha` cannot be satisfied at all on this provider
  when the signal is a reaction. Either it is limited to review objects, or
  Crucible must bind a reaction to a head by timestamp and record that the
  binding is inferred.
- If a repository sets `retrigger_after_correction: true`, Crucible's
  trigger comment would be posted under the App identity, which run 1
  showed is refused. Retrigger therefore needs a human, or it needs to be
  off.

### What run 1 and the live record established, and still hold

1. **Login**: `chatgpt-codex-connector[bot]` for the summary comment, the
   review, and every review comment. The 05b default
   `reviewer_logins: ["chatgpt-codex-connector[bot]"]` is confirmed. The
   summary comment posts under the same login, not a different one.
2. **Signal kinds**: issue comment (summary, edited in place), review with
   state `COMMENTED`, review comments. `accepted_signals: ["review",
   "comment", "reaction:+1"]` is right as a list, with two corrections:
   the summary comment must not count as a round on its own (it appears
   before the review and is edited later), so "comment" should mean an
   issue comment from the reviewer that is not the summary marker, or the
   round should key on the review; and `reaction:+1` cannot be observed
   with the current App grant.
3. **Reviewed SHA**: `commit_id` on the review and on each review comment;
   also in the review body as "Reviewed commit".
4. **Trigger**: superseded by the rerun. What holds: `@codex review`
   posted under an App identity is refused with an account prompt, so
   Crucible cannot trigger the reviewer itself.


## Spec changes needed

Run 1's trigger finding is withdrawn. What replaces it:

- **23 External review, trigger**: with the repository configured for
  review on all PRs, the reviewer runs automatically on a PR opened by the
  App, with no connected human in the thread. Crucible's PRs are reviewable
  as spec 23 assumes, **conditional on a per-repository Codex setting that
  GitHub does not expose**. That makes it a repository-onboarding
  prerequisite, not a runtime check: Crucible cannot detect whether a
  repository is configured, and a repository that is not configured looks
  exactly like a reviewer that is slow. `wait_timeout_hours` is the only
  thing standing between "not onboarded" and an indefinite wait.
- **23 Observation, reactions**: `reaction:+1` on the pull request is not a
  corner case, it is the entire signal for a clean review. It needs
  **Issues read** on the App, which ADR 0007 does not grant. Without it
  Crucible sees a silent PR and times out on every clean review. Either add
  Issues read to the App grant and to 23 and ADR 0007, or accept that no
  Crucible PR can ever pass external review automatically.
- **23 Observation, reaction lifecycle**: reactions are added *and removed*
  by the reviewer. Crucible must treat a reaction set as state to diff, not
  a list to append to, and must not treat the disappearance of `eyes` as
  anything other than the provider's own bookkeeping. Only `+1` from an
  allowlisted login is an accepted signal.
- **23 Observation, interval**: the in-progress `eyes` reaction lived about
  100 seconds. A 120 s default poll can miss it. That is acceptable if only
  `+1` is an accepted signal, and it must be stated, because an operator
  reading a task's event log will otherwise wonder why the reviewer's
  pickup was never recorded.
- **23 External review, reviewed SHA**: `require_review_on_final_sha`
  cannot be enforced against a reaction, which carries no `commit_id`.
  Either the policy applies only to review objects, or a reaction is bound
  to a head by the reaction's `created_at` against the head's push time,
  which is an inference Crucible should record as such.
- **05b**: `reviewer_logins` default stays. `accepted_signals`: keep
  `review`; keep `reaction:+1` and mark it as requiring Issues read; define
  `comment` as a non-summary issue comment from an allowlisted login, since
  the summary comment appears before the review and is edited later.
- **21**: S12's expected "reviewer_logins default confirmed" holds. The
  finding is "the trigger is a per-repository provider setting invisible to
  GitHub, and the clean-result signal is a PR reaction the App cannot read".

## The repository-onboarding prerequisite

Because the setting does not appear on any GitHub surface Crucible can
read, it belongs in the registration record as an operator attestation, not
a probe. Proposed wording for spec 23
(repository registration) and for the onboarding checklist:

> **External review prerequisite.** Before a repository is registered with
> `external_review.required_rounds` greater than zero, the operator must
> enable the external reviewer for **all pull requests** on that repository
> in the provider's own settings (for Codex,
> `chatgpt.com/codex/settings`, code review and security review on all
> PRs). The setting is absent from every GitHub surface Crucible can read,
> so Crucible cannot verify it, and a repository that is missing it is
> indistinguishable from a reviewer that has not answered yet. The operator
> records the attestation, with a date, at registration; Crucible stores it
> on the repository record and names it in every
> `external_review_overdue` wake. A repository whose reviewer must be
> triggered by hand, or which cannot be configured this way, registers with
> `required_rounds: 0` instead, because Crucible cannot post the trigger
> itself: an `@codex review` comment from the App is refused.

The second prerequisite is on the App, not the repository: **Issues read**
must be added to the App grant and to ADR 0007 before external review can
work at all, because the clean-result `+1` is the only object a clean review
produces and `GET /issues/{n}/reactions` is 403 without it.

## Limitations

- One repository, one App-authored PR, one 30 minute window and one 15
  minute retrigger window, on one day.
- **Two things changed between run 1 and the rerun, not one.** The
  operator changed the Codex setting, which cannot be read from GitHub and
  is therefore operator-asserted; and the publisher changed, so the
  rerun's PR contains a Python file with reviewable content while run 1's
  PR contained only a text stamp. A reviewer that skips a PR with no code
  in it would produce the same two results. Isolating the setting needs a
  third run: the current publisher against a repository with the setting
  off, or the run-1 publisher against this repository with it on.
- The PR was clean, so the findings path was not exercised on an
  App-authored PR. What a review **with** findings emits for an App author
  (review object, review comments, summary comment, or only a reaction) is
  unknown; the live record on `crucible` shows that shape for human-authored
  PRs only.
- Code review and security review could not be told apart. If both ran,
  they produced one `eyes` and one `+1` between them, and nothing in the
  GitHub record attributes either to one or the other.
- Reaction deletion is inferred from two polls 62 seconds apart. GitHub
  records no deletion event and no actor for it, here or anywhere.
- No webhook receiver, so the webhook path is untested. GitHub emits no
  webhook for reactions in any case, which is the point.
- Whether an installation token can read PR reactions through GraphQL
  without Issues read was not tested: `s10.py` has no GraphQL client. There
  is no separate GraphQL grant on a GitHub App, so GraphQL should enforce
  the same Issues read requirement, but that is reasoning, not a measurement.

## Risks

- A repository onboarded without the Codex setting behaves exactly like a
  repository whose reviewer is slow. Crucible has no way to tell them apart
  and will burn `wait_timeout_hours` on every task.
- Shipping C1 against the ADR 0007 grant means every clean external review
  is invisible and every such task stalls. This is not a degraded mode, it
  is a stuck one.
- The provider can change the shape of a clean result (today a reaction,
  yesterday a "Didn't find any major issues" comment on PR #5 of the same
  repository) without notice. `accepted_signals` must tolerate more than
  one shape.
