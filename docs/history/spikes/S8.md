# S8: Does a running worker survive a supervisor restart?

Run 2026-09-16 at 11:35 CDT on the reference workstation, Docker 28.3.1,
against the S7 Claude Code image as first built (before the review fixes, which changed nothing in how a container runs; the `Image=` line below is that build).

Decision: **proceed, partial.** A worker container in the spec 08 hardened
shape is untouched by restarting, stopping and starting, and removing and
recreating an unrelated "supervisor" container; a new supervisor finds it
again by label; `docker logs --since <offset>` resumes from where the old
supervisor left off; `docker logs -f` re-attaches to the live stream.
Partial because the supervisor here is a stand-in container, not Crucible,
and `docker compose restart` could not be run (no `compose.yaml` yet); both
are repeated in C3 against the real service. One design note for spec 08
came out of it: `--since` is inclusive (below).

## Setup

```
$ docker network create --internal crucible-spike-s8
$ docker run -d --name crucible-spike-worker \
    --label crucible.attempt=spike --label crucible.task=spike-s8 --label crucible.owner=foundry \
    --user 1000:1000 --cap-drop ALL --security-opt no-new-privileges --read-only \
    --tmpfs /tmp:rw,nosuid,nodev,size=64m \
    --tmpfs /home/worker:rw,nosuid,nodev,size=64m,uid=1000,gid=1000,mode=0750 \
    --pids-limit 128 --memory 256m --cpus 1 --network crucible-spike-s8 \
    crucible-worker:claude_code-2.1.273-... sh -c 'i=0; while :; do i=$((i+1)); echo "tick $i"; sleep 1; done'
$ docker run -d --name crucible-spike-supervisor --label crucible.role=supervisor \
    --network crucible-spike-s8 debian:bookworm-slim@sha256:5ae3c39e... sh -c 'while :; do sleep 5; done'
```

The daemon confirms the shape:

```
User=1000:1000 ReadonlyRootfs=true CapDrop=[ALL] CapAdd=[] SecurityOpt=[no-new-privileges]
Tmpfs=map[/home/worker:rw,nosuid,nodev,size=64m,uid=1000,gid=1000,mode=0750 /tmp:rw,nosuid,nodev,size=64m]
PidsLimit=128 Memory=268435456 Network=crucible-spike-s8
```

`--tmpfs` accepts `uid=`, `gid=`, and `mode=` on this daemon, so
`/home/worker` can be owned by the worker rather than mounted 1777.

## Three supervisor restarts

```
$ docker restart crucible-spike-supervisor
$ docker stop crucible-spike-supervisor; sleep 5; docker start crucible-spike-supervisor
$ docker rm -f crucible-spike-supervisor
$ docker run -d --name crucible-spike-supervisor ...       # what a compose restart of the crucible service does
```

## After

```
$ docker ps --filter label=crucible.attempt=spike --format '{{.ID}} {{.Names}} {{.Status}}'
5ffa2dc76f8a crucible-spike-worker Up 34 seconds
$ docker inspect crucible-spike-worker --format '{{.Id}} {{.State.Status}} pid={{.State.Pid}} started={{.State.StartedAt}} restarts={{.RestartCount}}'
5ffa2dc76f8a...  running  pid=2956610  started=2026-09-16T16:35:52.590528262Z  restarts=0
RESULT: worker unaffected (same container ID, pid, StartedAt, restart count 0)

$ docker logs -t --since 2026-09-16T16:35:58.128635142Z crucible-spike-worker | head -n 3
2026-09-16T16:35:58.736146224Z tick 7
2026-09-16T16:35:59.738426680Z tick 8
2026-09-16T16:36:00.739410463Z tick 9
since=56 total=62                       # lines after the offset vs. all lines, no overlap, no gap
$ timeout 3 docker logs -f --tail 0 crucible-spike-worker
tick 63
tick 64
tick 65
ticks=65 gaps=0                          # counter monotonic across the whole run
```

Tick 6 was the last line the old supervisor saw, tick 7 is the first line
`--since` returns. That was clean only because the offset was a wall-clock
read taken 600 ms after tick 6, not tick 6's own timestamp. `--since` is
inclusive, checked separately on the same image:

```
offset = timestamp of tick 3: 2026-09-16T16:49:49.162482250Z
$ docker logs -t --since 2026-09-16T16:49:49.162482250Z ...   | head -2
2026-09-16T16:49:49.162482250Z tick 3                          # repeated
2026-09-16T16:49:50.163457571Z tick 4
$ docker logs -t --since 2026-09-16T16:49:49.162482251Z ...   | head -1
2026-09-16T16:49:50.163457571Z tick 4                          # strict after
```

So a supervisor that stores the timestamp of the last line it saw (the
natural `logs(handle, since)` implementation in spec 08) re-reads that one
line on every resume unless it adds one nanosecond to the stored offset or
drops the first line when its timestamp equals the offset. The Docker
provider's `logs` must do one of those; the spec 08 text should say so.

$ docker rm -f crucible-spike-worker crucible-spike-supervisor
$ docker network rm crucible-spike-s8

(empty)

## What this does and does not show

- Shown: workers are daemon-owned and independent of whichever container
  created them. Nothing about the supervisor's lifetime reaches a worker
  because nothing links them: no `--link`, no shared PID namespace, no
  parent-child relation. The label is the only association, and it is what
  `reconcile()` lists by.
- Not shown: Crucible's own restart path. The "supervisor" was a plain
  Debian container with no relation to the worker; restarting it shows
  that Docker does not tie a container's life to whoever created it,
  which is the property Crucible relies on, not that Crucible's
  `reconcile()` works. That is C3 work with the real service.
- Not shown: `docker compose restart` itself, because no `compose.yaml`
  exists on this branch. The remove-and-recreate step above is the
  container-level operation a compose restart of the `crucible` service
  performs; the compose form is repeated in C3 when the file exists.
- Not shown: a daemon restart. That would have disturbed other containers
  on this shared workstation daemon. Docker's live-restore keeps containers
  running across a daemon restart when enabled; whether it is enabled on
  the Crucible daemon is checked in S9, and a worker that dies with the
  daemon is the `lost` path of spec 16 regardless.
- Not shown: `docker compose down`. Spec 13 says it must not remove
  running workers; that holds by construction (workers are not compose
  services) and is confirmed in C3.
