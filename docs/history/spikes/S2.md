# S2: Can Codex's own sandbox run inside the container as defense in depth?

Run 2026-09-16, 14:10 to 14:13 CDT, rootful Docker 28.3.1, host Ubuntu 24.04
(kernel 6.8, `kernel.unprivileged_userns_clone=1`,
`kernel.apparmor_restrict_unprivileged_userns=1`), image
`crucible-worker:codex-0.153.4-fdfc3a7c883e` in the spec 08 worker shape
with `--network none`. No model and no credential: `codex sandbox linux`
runs a command under the CLI's sandbox without a session, which is exactly
the mechanism `--sandbox workspace-write` would use.

Decision: **proceed; do not enable it.** The Codex sandbox is not available
in the worker image and cannot be made to work inside the hardened container
on this host without weakening the container. ADR 0005 stands: the
container is the boundary, the Codex adapter keeps
`--dangerously-bypass-approvals-and-sandbox`.

## In the base image

```
$ codex sandbox linux --sandbox workspace-write -- id
thread 'main' panicked at linux-sandbox/src/launcher.rs:51:13:
bubblewrap is unavailable: no system bwrap was found on PATH and no bundled
codex-resources/bwrap binary was found next to the Codex executable
```

Codex 0.153.4's Linux sandbox is bubblewrap, and the static musl release
binary neither bundles it nor finds it in the image (spec 13: git, curl, jq,
the CLI, nothing else). Same result under every Docker security profile
below, because the panic happens before any namespace call.

## In a throwaway child image with bubblewrap

To answer the "with and without user namespaces" half, a child image
(`FROM` the Codex base, `apt-get install bubblewrap` 0.8.0 from the pinned
snapshot, removed afterwards) was run under three profiles:

| Docker profile | `unshare -Ur id` | `codex sandbox linux --sandbox workspace-write -- id` | plain `bwrap --unshare-user ... id` |
|---|---|---|---|
| default (seccomp builtin, apparmor docker-default) | `unshare failed: Operation not permitted` | `bwrap: No permissions to create new namespace` | same |
| `--security-opt seccomp=unconfined` | works (uid 0 in the new namespace) | `bwrap: Failed to make / slave: Permission denied` | same |
| `--security-opt seccomp=unconfined --security-opt apparmor=unconfined` | `write failed /proc/self/uid_map: Operation not permitted` | `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted` | `bwrap: setting up uid map: Permission denied` |

Reading: Docker's default seccomp profile refuses `unshare(CLONE_NEWUSER)`
without `CAP_SYS_ADMIN`, so under the spec 08 shape there are no user
namespaces at all. Dropping seccomp lets the namespace be created, but
bubblewrap then needs to change mount propagation on `/`, which the
docker-default AppArmor profile denies. Dropping AppArmor as well runs into
the host's `apparmor_restrict_unprivileged_userns=1` (Ubuntu 24.04 default),
under which an unconfined unprivileged process may not set up a uid map.
(`codex sandbox linux` got one step further under that profile and failed
configuring the loopback address in its network namespace; it takes a
different bubblewrap path than the plain `--unshare-user` probe, and both
end the same way: no sandbox.) The one profile that would
let bubblewrap run (a custom AppArmor profile granting `userns` plus mount,
or `CAP_SYS_ADMIN`) is a larger hole than the sandbox would close.

## Consequences

- Spec 07 Codex section: keep the bypass flag; record that the image ships
  no bubblewrap on purpose and that `--sandbox` flags are not used.
- Spec 08: the `unshare` result is also S4 evidence that user namespaces are
  unavailable to a worker under the default shape.
- If a future Codex release ships a non-bubblewrap sandbox (seccomp or
  landlock only), rerun this spike; landlock alone would likely work under
  the default profile.
