# S1: Does each harness's subscription auth work from a mounted config directory inside a non-root container?

Run 2026-09-16, 13:59 to 14:08 CDT, on the reference workstation against the
rootful Docker 28.3.1 daemon, with the three base images from S7
(`crucible-worker:claude_code-2.1.273-5bb76fb777d0`,
`crucible-worker:codex-0.153.4-fdfc3a7c883e`,
`crucible-worker:agy-1.2.4-a0f410dd9e78`). Rootless is proven separately (S9);
the runs here should be repeated on the rootless daemon in C3.

Decision: **adjust design, and escalate one finding.** All three harnesses
complete a trivial prompt with subscription auth from a mounted copy of the
operator's config directory, as uid 1000, with no commercial API key, so the
host-process provider (spec 08) stays unimplemented. Two harnesses refreshed
their OAuth token on their own during the first authenticated run, which the
task contract treats as a stop condition for that harness, so the Codex and
AGY halves of the later spikes are partial. The Codex refresh rewrote the auth
file inside the scratch copy (a new sha256 and a new `last_refresh`; the
token values themselves were not compared, by rule); the operator's host
copy was never touched and still holds the pair from ten days earlier.
Whether that older pair still works was not tested. That is the
escalation, in the report, not here.

## Shape

Every run used the spec 08 worker shape: `--user 1000:1000 --cap-drop ALL
--security-opt no-new-privileges --read-only`, tmpfs `/tmp` and
`/home/worker` (`uid=1000`), `HOME=/home/worker`, a throwaway git checkout at
`/crucible/repo` (rw), an identity dir at `/crucible/identity` (ro, one
`IDENTITY.md` telling the worker to answer in one line and do nothing else), a
report dir at `/crucible/report` (rw), 2 GiB memory, 256 pids, and the
default bridge network for these runs (S6 covers the proxy). Prompt on stdin:
"Reply with exactly the word PONG and nothing else."

Credentials were copies (`cp -a`) of the operator's `~/.claude`,
`~/.claude.json`, `~/.codex` and `~/.gemini` in a mode 700 scratch
directory outside the repository, deleted at the end of the task. The
originals were never mounted or written. No token was forced to expire.

`ro` means the whole copied directory bind-mounted read-only at the path the
CLI expects. `rw-narrow` means a per-attempt directory seeded with only the
harness's auth file(s), mounted writable at that path, with the CLI's
settings file mounted read-only on top from a Crucible-owned template (an
empty `{}` for Claude Code, a one-line comment for Codex).

## Claude Code

| Mode | Mounts | Result |
|---|---|---|
| ro | copy of `~/.claude` at `/home/worker/.claude:ro`, copy of `~/.claude.json` at `/home/worker/.claude.json:ro` | exit 0, `PONG`, 4.2 s |
| rw-narrow | dir seeded with `.credentials.json` and `.claude.json` at `/home/worker/.claude` (rw), `settings.json` template ro on top, `CLAUDE_CONFIG_DIR=/home/worker/.claude` | exit 0, `PONG`, 4.1 s |
| two concurrent rw-narrow workers (separate seeded dirs) | as above, started in the same second | both exit 0, `PONG`, 3.9 s and 3.6 s |

Launch line, as spec 07: `claude -p --permission-mode bypassPermissions
--append-system-prompt-file /crucible/identity/IDENTITY.md --output-format
stream-json --verbose`, no `--model` (the subscription default answered as
`claude-fable-5-1` in one run and `claude-opus-5` in another; the adapter
should pass the model explicitly).

The auth path in use is the OAuth file pair (spec 07's first option), not
the long-lived token environment variable. `.credentials.json` holds
`claudeAiOauth` with an access token that expired later the same afternoon
(15:59 CDT) and a refresh token good for a month; no run refreshed it, and
its sha256 was identical before and after every run, including the
concurrent pair. `CLAUDE_CONFIG_DIR` moves both files into one directory,
which is the shape `rw-narrow` wants: one per-attempt volume, no file-level
bind mount of `~/.claude.json` (a rename over a file bind mount would fail).

The ro run worked with the operator's full directory, including the
operator's `settings.json` hooks, which ran and failed harmlessly
(`Failed to run: EROFS: read-only file system, mkdir
'/home/worker/.claude/session-env/<session>'`, reported as
`hook_response` events with exit 0 for the run). So a read-only config
directory is enough for a trivial prompt; nothing Claude Code needs to write
is required for completion. The template must not carry the operator's
hooks (they name host paths and would run inside every worker).

Files Claude Code wrote in the rw-narrow run (217 files, from `find -newer`
inside the container plus the host view afterwards):

- `.claude.json` rewritten in place (299,420 to 299,797 bytes; new sha256)
  and `backups/.claude.json.backup.<epoch-ms>`, a copy of the old one.
  `.credentials.json` untouched.
- `sessions/`, `projects/-crucible-repo/` (transcript), `cache/model-catalog/`.
- `plugins/synced/<org-bucket>/.marketplaces.json` and
  `skills/synced/<org-bucket>/{docx,pdf,pptx,xlsx,skill-creator}/...`: the
  operator's claude.ai organization skills, downloaded on every run.
- outside the config directory:
  `/home/worker/.cache/claude-cli-nodejs/-crucible-repo/mcp-logs-*` for the
  two claude.ai MCP connectors on the account.
- Docker created an empty `settings.json` in the seeded directory as the
  mount point for the read-only template; harmless, but the sync-back step
  must ignore it.

Read set that matters: `.credentials.json`, `.claude.json`, `settings.json`.
The `rate_limit_event` lines in stream-json report the subscription's
five-hour and seven-day utilization, useful for the quota class in 16.

## Codex

| Mode | Mounts | Result |
|---|---|---|
| ro | copy of `~/.codex` at `/home/worker/.codex:ro` | exit 1 in 1.3 s: `WARNING: proceeding, even though we could not create PATH aliases: Read-only file system`, then `Error: failed to initialize in-process app-server client: Permission denied (os error 13)`; auth never reached |
| rw-narrow | dir seeded with `auth.json` only at `/home/worker/.codex` (rw), `config.toml` template ro on top | exit 0, `PONG`, 14.7 s, `codex-last-message.md` written |

Launch line: `codex exec --dangerously-bypass-approvals-and-sandbox
--skip-git-repo-check -c check_for_update_on_startup=false --json -o
/crucible/report/codex-last-message.md -C /crucible/repo`, prompt on stdin.
`--skip-git-repo-check` is needed because the checkout is owned by a host
uid the container user is not; the adapter should keep it (the checkout
lease and the collector, not Codex, own git state). The JSON stream carried
one non-fatal `error` item: `Code Mode is unavailable because failed to
spawn code-mode host /usr/local/bin/codex-code-mode-host` (not in the
image; the run continued).

The ro result matches spec 07: Codex is `rw-narrow` from the start.

**Refresh finding.** The seeded `auth.json` (`auth_mode = chatgpt`, no API
key) had `last_refresh` 2026-09-06 12:17 CDT. After the run its sha256 had
changed and `last_refresh` read 2026-09-16 14:01:10 CDT, the second the
container started. The CLI refreshed its ChatGPT OAuth state on its
own at start; the access token in a ten-day-old copy was presumably past
its expiry, which is the condition the CLI refreshes on. Nothing was forced. Per the task
contract this stopped Codex's authenticated spikes; the two-worker
concurrency test was therefore run with Claude Code instead, and the Codex
half of S5, S6 and S11 is unauthenticated only. Whether the operator's
older refresh token still works was not tested, by rule.

Files Codex wrote beside `auth.json` in the rw-narrow run (203 files):
`sessions/2026/09/16/rollout-<ts>-<thread>.jsonl`, `state_5.sqlite`,
`logs_2.sqlite`, `thread_history_1.sqlite`, `goals_1.sqlite`,
`memories_1.sqlite`, `queue_1.sqlite` (each with `-wal` and `-shm`),
`models_cache.json` (228 KB), `installation_id`, `.sandbox_migration`,
`shell_snapshots/`, `thread-writer-locks/`, `tmp/`, `cache/`, `skills/`, and
`plugins/cache/openai-curated-remote/...` (a remote plugin marketplace
index). Nothing under `/tmp`. Only `auth.json` should sync back; the rest
is per-attempt state and the volume removal in spec 12 discards it.

## AGY

| Mode | Mounts | Result |
|---|---|---|
| ro | copy of `~/.gemini` at `/home/worker/.gemini:ro` | exit 0, `PONG`, 22 s, stream-json `result` with `status: SUCCESS` |

Launch line: `agy -p "<prompt>" --dangerously-skip-permissions --add-dir
/crucible/identity --output-format stream-json`. The credential is
`antigravity-cli/antigravity-oauth-token` (a JSON file with `auth_method`,
`id_token` and a `token` object holding access, refresh, expiry and type).

**Refresh finding.** The CLI's own log (stderr) shows the stored token was
already expired (expiry 2026-09-16 00:54 CDT) and print mode refreshed it
silently at 13:59:37 CDT before answering:

| stderr line (source file in the CLI's glog output) | Text (values as logged; no secret is in these lines) |
|---|---|
| `keyring.go:64` | `keyringAuth: loaded token` with `expiry` 2026-09-16 00:54:51 CDT and `expired=true` |
| `browser.go:265` | `token refreshed` with a new `expiry` one hour out, 14:59:36 CDT (logged as 19:59:36 UTC) |
| `browser.go:267` | `Failed to save refreshed token: failed to write token to file: open /home/worker/.gemini/antigravity-cli/antigravity-oauth-token: read-only file system` |

The read-only mount prevented the write, so the copy on disk is byte
identical to before (sha256 checked), and the run still completed because the
refreshed access token lived in memory. Per the task contract this stopped
AGY's authenticated spikes: no rw-narrow run, no concurrency run, and S3's
live half is blocked (S3.md). What AGY wanted to write in ro mode, from the
log: `antigravity-cli/log/cli-<ts>.log`, `antigravity-cli/crashes/...`, the
conversation summary database, and the token file itself.

Two things the log makes plain for the design: AGY refreshes on every run
once the access token is past its one-hour expiry, so an `ro` mount (spec 12's
current choice for `credential:agy`) means a refresh per attempt and never a
saved token; and the refresh is a Google refresh-grant, which the log shows
returning a new expiry only. Whether the refresh token itself rotates was not
tested.

## What was not done

- Forced expiry ("repeat after forcing token expiry where possible" in spec
  21): excluded by the task contract, and made moot for AGY and Codex by
  their own refreshes.
- Two concurrent Codex workers: stopped by the refresh finding; the Claude
  Code pair exercised the shape but not a refresh race, because no refresh
  was due.
- Exact read set per harness: inferred from what the CLIs needed to succeed
  under `ro`, not traced (no strace in the images).

## Design consequences

1. Spec 07 Claude Code: use `CLAUDE_CONFIG_DIR` pointing at the per-attempt
   volume so both auth files live in one directory; template `settings.json`
   without the operator's hooks; expect the CLI to write sessions, project
   transcripts, plugin and skill syncs, and a backup of the state file into
   that volume, and `.cache/claude-cli-nodejs` into the tmpfs home. Sync back
   only `.credentials.json` and `.claude.json`. Pass `--model` always.
2. Spec 07 Codex: `--skip-git-repo-check` in the launch line; the
   config template replaces the operator's `config.toml` (it carries
   per-project trust, MCP servers and hook trust hashes that must not reach
   a worker). The refresh happened at attempt start with a stale token;
   per-harness concurrency of one and the newest-`last_refresh` sync-back in
   spec 12 are not optional.
3. Spec 12 AGY: `ro` is workable only if a per-attempt refresh is
   acceptable; otherwise `rw-narrow` on the token file, same as the others.
4. The operator's host copy of `~/.codex/auth.json` is now behind the copy
   the worker produced (and that copy is deleted). For AGY nothing newer
   exists anywhere: the refreshed access token was never saved, and whether
   Google rotated the refresh token server-side was not tested. Handled in
   the task report, not in this repository.
