# C14: the worker image publish works against GHCR, proved on GHCR (FDY-0090)

## Result

`make images-publish` now publishes both worker images to
`ghcr.io/sentania-labs/crucible-worker`, and that is proved on GHCR itself by a CI job,
not by a local `registry:2` or a fake. The release's publish step is unchanged: the same
make target, the same script, no edit to `release.yml`.

## What failed

The v0.5.0 release (run 35830898223, 2026-09-23 at 2:20 AM) built and proved both
images, then stopped on the first blob's finalizing PUT:

```
PUT /v2/sentania-labs/crucible-worker/blobs/upload/9.ca03f4e0-...?digest=sha256%3Aa1f01f... -> 404
{"errors":[{"code":"BLOB_UPLOAD_INVALID","message":"invalid content-type"}]}
```

Nothing was published and the version tag was never pushed. The chunked upload
(FDY-0074) had only ever been proved against `registry:2` and the unit tests' fake.

## Diagnosis, on GHCR

The new `ghcr-publish` job ran the unchanged upload once (run 35831556330, 2:26 AM) with
each step's answer logged. POST and a one-chunk PATCH were accepted; the finalizing PUT
got the same 404. The cause is on the client: urllib gives any request with a body and no
Content-Type `application/x-www-form-urlencoded`, including the PUT's empty body.
`registry:2` ignores it; GHCR refuses it.

With the Content-Type fixed (run 35831883997, 2:30 AM) the first blob completed (PUT 201),
and the second stalled: GHCR stopped reading its first 8 MiB `Content-Range` PATCH until
the write timed out two minutes later. GHCR does not take the spec's PATCH-per-chunk
shape for a chunk that size.

What GHCR answers, as the fake now models it: the POST's Location is
`/v2/<name>/blobs/upload/<n>.<uuid>` (singular `upload`), echoed in `Docker-Upload-UUID`,
with no query string; each PATCH answers an inclusive `Range: 0-<last byte>`; a PATCH or
PUT without `Content-Type: application/octet-stream` is 404 `BLOB_UPLOAD_INVALID`.

## The fix

- Every upload request carries `Content-Type: application/octet-stream`, and the POST
  and PUT an explicit `Content-Length: 0`.
- Each blob goes up as POST, one PATCH that streams the whole blob with chunked transfer
  encoding (one bounded 8 MiB archive read per wire chunk, never the whole blob in
  memory), then PUT with the digest on the Location's own query string. This is the
  shape `docker push` and go-containerregistry use. The PATCH's answered Range must cover
  exactly the bytes sent.
- The tamper check still aborts mid-PATCH, before the finalizing PUT is sent. A streamed
  body is never re-sent on a 401.
- A relative Location must be an absolute path (`@evil.example/x` or `:8443/x` glued onto
  the host would move the credential), and an off-host refusal names only the hostname.
- Each upload step and manifest push logs its status, Location, Range,
  Docker-Upload-UUID and Docker-Content-Digest, and the body of a refusal. No request
  header is ever logged; query values other than a digest are logged as their length.

image pulled by digest and ran.

## The CI job

`ghcr-publish` in `ci.yml` runs `make images-publish` with
`WORKER_TAG_PREFIX=ci-<12-char sha>-` on every branch push and every pull request from
this repository (a fork has no package write and is skipped). `ci.yml` now triggers on
every branch push for this job; every other job keeps its old triggers, main pushes and
pull requests, through an `if`. The `ci-` tags accumulate on GHCR; deleting them is an
operator call.
