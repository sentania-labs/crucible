# C2 implementation notes: gates, claims, review, acceptance, corrections, wakes

Phase C2 per `docs/spec/20-implementation-phases.md`. Where the specification left
something open, the simplest choice consistent with it was taken and is recorded here.
Nothing here changes the specification; proposed spec changes are listed at the end.

## What C2 adds

`PolicyV1` and `RoutingPolicyV1` as models plus the policy and routing API; the evidence
model; every pre-PR gate that needs only the collected tree, the report, or the artifact
store; `awaiting_internal_review` with both review paths; acceptance, corrections,
amendments, decisions, escalations, and dispositions; wakes with poll and webhook; the
on-disk artifact store; `AttemptMetrics`.

## Decisions

1. **Gate evaluators are pure functions over evidence.** `crucible/domain/gates.py` holds
   the gate names, the phase sets, and one evaluator per pre-PR gate. An evaluator sees a
   `GateInput` (contract, policy, head SHA, evidence tuple) and returns a `GateOutcome`.
   It reads no database, no file, and no clock, which is what makes the unit tier able to
   cover every gate against synthetic evidence.
2. **Only verified, non-worker evidence is admissible.** `EvidenceItem.admissible` is
   `verified and source != "worker"`, and every evaluator filters through it. The rule is
   also in the schema: a CHECK on `evidence` refuses `verified = true` with
   `source = 'worker'`, so a forged row cannot exist to be read.
3. **The claim travels as `artifact_present` evidence, not a new kind.** 11 fixes the
   evidence-kind list, so the facts a gate needs from the report (`parsed_ok`,
   `mapped_criteria`, `claimed_head_sha`, `run_evidence`) ride on an `artifact_present`
   row with `role: completion_claim`, recorded by Crucible after it parsed the report. A
   second row with `role: worker_claim`, `source: worker`, `verified: false` carries the
   worker's own document so Foundry can read it and no gate can consume it.
4. **Absent evidence fails a gate, it does not hold it pending.** Gates run once the
   attempt is collected, so "no exit_info" means the attempt produced nothing, which is
   the case 09 describes: a failed attempt still reaches `reported` and its gates then
   fail. `pending` is reserved for `internal_review_recorded` (a real wait) and for the
   two C3 gates.
5. **`verification_ran` and `workspace_clean` are `pending` with a marker.** Both need the
   verifier container (C3). They are evaluated so the row exists, they never report
   `pass`, and their detail starts `deferred:c3-verifier`. They do not block
   `gates_passed` in C2; C3 makes them blocking when the verifier lands.
6. **`artifacts` deliverables reach `accepted`; `branch` and `pull_request` stop.** 09
   sends the latter through `publishing`, which is C4. An accept on those records the
   AcceptanceResult, writes a `task_publish_pending` event, raises `tasks.publish_pending`,
   wakes Foundry with reason `publish_pending`, and leaves the state at
   `awaiting_acceptance`. Nothing is accepted unpublished.
7. **`needs_more_work` does not move the task.** It records the AcceptanceResult and wakes
   Foundry; the task stays in `awaiting_acceptance` until a correction is attached, which
   is the `awaiting_acceptance --needs_more_work (correction attached)--> scheduled` edge.
   A correction from `awaiting_acceptance` is refused unless a `needs_more_work` verdict
   exists.
8. **The role of a new execution comes from the contract version.** A version carrying a
   `correction` section materializes as a `correct` execution, anything else as
   `implement`, and at most one execution per (contract version, role). That makes
   `_materialize_scheduled` idempotent without a separate queue.
9. **Review executions are materialized like every other one.** `executions` and
   `attempts` are fenced to the supervisor (14), so `POST /tasks/{id}/review` with an
   execution request writes a `review_execution_requested` event and the next tick creates
   the `review` execution and its attempt. The head under review is passed to the provider
   as `CRUCIBLE_REVIEW_HEAD_SHA` in the launch spec's env.
10. **`reviewer_must_not_be_author` is mechanical.** The reviewer the document names wins:
    an uploaded report naming an attempt of this task is refused 403, and a review
    execution never shares an attempt with the implementing one. The `review_received`
    evidence row carries `reviewer_is_author: false` and the gate reads it.
11. **An uploaded review does not itself resolve the gate.** `gate_results` is fenced to
    the supervisor, so the API records the report and its evidence and the next tick
    re-evaluates the gates and moves the task. `POST /review` therefore returns the task
    still in `awaiting_internal_review`.
12. **Gate re-evaluation is a no-op when nothing changed.** A task waiting in
    `awaiting_internal_review` is re-evaluated on every tick; the rows and the
    `gates_evaluated` event are written only when the answer differs from what is stored,
    which keeps "reconciliation changes nothing the second time" true.
13. **`tasks.head_sha` holds the collected head.** Everything after `reported` is bound to
    it (09), and a correction clears it until the corrected head is collected. The
    alternative, deriving it from `bundle_head` evidence on every read, is the same value
    with more joins.
14. **A wake's event principal is the actor.** Events whose principal is `crucible` are
    fenced (14), so a wake an API call causes carries the acting principal's name on its
    `wake_created` event while the row itself still belongs to the task's principal.
15. **Wake delivery uses the standard library.** `urllib.request` in a thread with an
    HMAC-SHA256 signature in `X-Crucible-Signature-256`. The retry schedule is
    30s, 60s, 120s, 300s, 600s, 1800s, 3600s, then 3600s, until the policy's
    `limits.wake_retry_hours` elapses; after that the row stops being retried and stays
    for poll. The webhook URL and secret come from settings (`CRUCIBLE_WAKE__WEBHOOK_URL`,
    `CRUCIBLE_WAKE__SECRET`); the secret is read from the environment and never stored.
    17 says "the principal's configured URL"; C2 has one configured target for all
    principals, because there is one orchestrator.
16. **Artifacts are content-addressed on disk.** `<artifact_root>/blobs/<aa>/<bb>/<sha256>`,
    written to a temporary file and renamed, so a reader never sees a half-written blob
    and identical content is stored once. Every blob passes the secret scanner first: a
    match is refused with the pattern name and the byte offset, never the value, and the
    refusal is an `artifact_rejected` event.
17. **Artifact upload takes the bytes as the request body.** 04 describes multipart;
    parsing multipart needs `python-multipart`, which Crucible does not depend on, so
    `POST /v1/attempts/{id}/artifacts?type=&filename=` takes the raw body with the
    media type from `Content-Type`. Listed as a proposed spec change below.
18. **A rejection that rolls back is recorded afterwards.** Review-report rejections and
    artifact rejections ride on the `ApplicationError.event` field the C1 contract
    rejection path already used, so the event survives the rollback of the request
    transaction.
19. **Policy versions are immutable once referenced.** `PUT /policies/{name}/{version}`
    replaces an unreferenced version and returns 409 once a task names it. A routing
    policy counts as referenced when a policy's `routing.policy` points at it.
20. **Operator-only policy fields are checked and recorded.** `allow_no_ci`,
    `allow_branch_only`, and `release.require_operator_approval: false` are refused for a
    principal that is neither operator nor admin, and each is written as a
    `policy_operator_setting` decision. Upload itself is admin-only per 04, so in practice
    the check bites when an operator-role principal is given upload rights.
21. **`concurrency.per_harness` must be 1 for `claude_code` and `codex`**, whose
    credential `mount_mode` is `rw-narrow` (12). The harness list is in the application
    layer, not the policy document, because it follows the credential spec.
22. **`execution_request.tier` is now a required contract field.** 05 shows it and 05b
    needs it to bound the model choice. Contracts written before C2 need it added.
23. **The routing check runs twice.** Advisory at submit (422 naming the rule so Foundry
    picks again) and authoritative at launch, inside the fenced transaction that moves the
    attempt to `launching`. The fake provider consumes no quota, so the reservation is
    structural: it resolves the pool, records `quota_reserved`, and writes the
    `attempt_metrics` row that C3's real launch will decrement against. Every seeded pool
    has `soft_limit: 0`, which 05b defines as observe-only, so nothing is refused yet.
24. **AttemptMetrics is written in two places.** The supervisor writes the row at launch
    and folds in wall time and exit class at collect; the gate counts, the correction
    count, and the acceptance verdict are backfilled on a later tick, because
    `attempt_metrics` is fenced and the API cannot write it. The backfill only writes when
    a value differs, so it is idempotent.
25. **`GET /routing/usage` states how it counted.** When no attempt in the window reported
    token counts, the pool falls back to counting attempts and the response says
    `fallback_to_attempts: true` with `counting: "attempts"`, per 05b.
26. **Migration 0004 corrects the C1 policy seed as data.** 0001 predates `PolicyV1`: its
    seeded `default-software` version 1 carries no `routing` section and says
    `round_counting: per_pull_request` where 05b says `completed_cycles`. 0001 is applied
    and is never edited (C1's own rule), so 0004 patches the stored document instead.
    `examples/policies/default-software.yaml` is that corrected document, and a unit test
    keeps the two equal.
27. **Downgrading past 0004 deletes the events only C2 can name.** The `ck_events_kind`
    constraint is the C1 list again on the way down, and `events` is append-only, so the
    downgrade stands the trigger down for exactly that one DELETE.
28. **Dispositions have a table and an endpoint but nothing to attach to yet.**
    `review_dispositions` exists and `POST /tasks/{id}/dispositions` validates and refuses
    with a 404 naming C4, because the external review comments a disposition refers to are
    recorded by the GitHub delivery phase. `store_disposition` is the row-writing half,
    kept separate so C4 calls it once comments exist.
29. **Escalations close in one step.** A `Decision` that references an open escalation
    moves it `open -> answered -> closed` in the same transaction and, with
    `reschedule: true`, takes a blocked task back to `scheduled`. An escalation older than
    `limits.escalation_stale_hours` produces a repeat wake, not a state change.
30. **`POST /tasks/{id}/amend` exists**, allowed in `submitted`, `blocked`, and
    `awaiting_acceptance` per 04. `POST /start` overrides are still refused; the amendment
    path is the way to change the contract.

## Not in C2

The Docker provider, the verifier container, `verification_ran` and `workspace_clean` as
real gates, log chunks and heartbeats, checkout leases, publishing and every GitHub
interaction, external reviews and their dispositions, CI certification, `head_diverged`,
releases, and the bootstrap import.

## Proposed specification changes

- **04**: `POST /attempts/{id}/artifacts` is described as multipart. Parsing multipart
  needs a dependency Crucible does not carry, so C2 takes the bytes as the request body
  with `type` and `filename` as query parameters. Suggest describing it that way, or
  naming `python-multipart` as a dependency.
- **04**: `POST /tasks/{id}/review` with an execution request cannot create the execution
  in the API transaction while 14 fences `executions`. Suggest the same wording `start`
  needs: "the API records the request; the supervisor creates the review execution on its
  next tick".
- **04 and 11**: an uploaded ReviewReportV1 cannot resolve `internal_review_recorded`
  inside the request either, because `gate_results` is fenced. Suggest stating that the
  gate resolves on the next supervisor tick, so a client polls rather than reading the
  response.
- **11**: the evidence-kind list has no kind for a parsed CompletionClaim. C2 uses
  `artifact_present` with a `role` discriminator. Suggest either naming that convention or
  adding a `claim_parsed` kind.
- **11**: state that a pre-PR gate whose evidence is absent after collection is `fail`,
  not `pending`, so the failed-attempt path of 09 is unambiguous.
- **05b**: the policy schema has no field for which harnesses mount `rw-narrow`, so the
  concurrency rule needs the credential spec of 12. Suggest saying so explicitly.
- **05b and 17**: wake delivery is described per principal, but nothing in the schema
  holds a principal's webhook URL. Suggest either a column on `principals` or stating that
  one configured target serves all principals in v0.x.
- **09**: the transition table has no edge for a `branch` or `pull_request` deliverable
  that is accepted while the publisher does not exist. C2 uses a flag on the task and a
  `publish_pending` wake. Suggest recording that as the C2-only arrangement, or adding the
  edge.
- **14**: add `head_sha` and `publish_pending` to the `tasks` row, and `phase` to
  `gate_results`, which distinguishes the pre-PR rows from the publication and post-PR
  rows that arrive in C4.
- **14**: the fenced list should name `gate_results` and `attempt_metrics` explicitly, and
  say that `acceptance_results`, `decisions`, `artifacts`, and `wakes` are the API role's,
  which is what stops the API from evaluating its own gates.
- **20**: C2's acceptance criterion says runs reach `awaiting_acceptance`. Worth stating
  that only an `artifacts` deliverable continues to `accepted` in C2, since the others
  need C4's publisher.
- **examples**: `examples/task-contracts/example-software-task.yaml` predates
  `execution_request.tier` and no longer validates. It is outside this task's allowed
  paths; it needs one line added.
