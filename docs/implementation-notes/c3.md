# C3 implementation notes: the Docker provider and the worker images

Phase C3 per `docs/spec/20-implementation-phases.md`. Where the specification left
something open, the simplest choice consistent with it was taken and is recorded here.
Nothing here changes the specification; proposed spec changes are listed at the end.

## What C3 adds

The Docker execution provider against the dedicated rootless daemon behind the socket
proxy; the egress proxy and the `crucible-workers` internal network; the create-request
policy; workspace preparation with dissociated clones and the checkout lease; the
collector (full diff, changed paths, HEAD, log, branch bundle, report copy), the bundle
verifier, and the verifier container, which turn `verification_ran` and
`workspace_clean` from `deferred` into real gates; log capture with
timestamp-and-hash resume; cleanup after `logs_drained`; retention actions; reconcile by
label; harness version ranges and image digest recording; and the script-harness e2e
image with the end-to-end tier of 18.

## Decisions

1. **Four throwaway containers per attempt, and the Crucible process runs no git.**
   Spec 08 says `collect` never runs git or reads worker-written files as the Crucible
   process. C3 applies the same rule to preparation, because the Crucible image carries
   no git at all: a **preparer** clones and seals the checkout, the **collector**
   produces the diff, the bundle and the report copy, a **bundle verifier** runs
   `git bundle verify` and nothing else, and the **verifier** re-runs the contract's
   required commands. All four use the attempt's own image in the worker's hardened
   shape.
2. **The verifier never sees the collector's output.** The verifier is the one container
   that runs commands the repository defines, which is to say code a worker may have
   changed. It gets a fresh tree the collector cloned from the collected state, and a
   verify directory for its logs; it cannot reach the diff, the bundle or the report
   copy the gates read. That is why `git bundle verify` is a separate container rather
   than a step of the verifier: the spec has Crucible run it, and this is the version of
   "Crucible runs it" that keeps untrusted commands away from it.
3. **The checkout lease is taken by the supervisor, not inside `prepare`.** 08 says
   `prepare` takes the lease first. The lease is a database row with a fenced token, and
   the provider has no database, so the supervisor takes it in the same fenced
   transaction that begins the launch and passes the workspace on. A second attempt on
   the same repository url and work branch is not failed: it stays `pending`, one
   `checkout_lease_denied` event is recorded, and it launches when the holder releases.
   Release happens when the attempt reaches a terminal state and again at cleanup.
4. **The workspace root is what the preparer mounts.** Under rootless Docker a bind
   source keeps the host uid it already had, and container uid 1000 is a subordinate
   host uid (S9 Test E). If Crucible pre-created the checkout directory, git inside the
   container would find a directory owned by a uid it is not, and refuse it as
   "dubious ownership". So the preparer gets the workspace itself and git creates the
   checkout, which then belongs to the container's own uid end to end. The shims and
   `.git/info/exclude` moved into the preparer for the same reason.
5. **The preparer is the only container with a `safe.directory` exception.** It is
   written into a global config file in the container's own tmpfs, because git ignores
   `safe.directory` given on the command line. The collector keeps
   `GIT_CONFIG_GLOBAL=/dev/null`: what it reads is a tree a worker wrote.
6. **The artifact root is shared as a named volume, not a host path.** S9's
   recommendation is that the Crucible service runs as uid 1000 with the artifact root
   owned by uid 1000, so workspaces, identity renders, report dirs and collector output
   share one owner. Normal mode does exactly that and mounts workspace subdirectories
   into every container with `VolumeOptions.Subpath`, so the daemon never needs a host
   path and no chown step exists anywhere. Developer mode sets `mount_kind = "bind"`
   with the daemon-visible path of the artifact root and `workspace_dir_mode = 0o777`,
   because two different uids then touch the tree; that mode is what the e2e tier uses.
7. **`--since` is converted to Docker's wire form.** The stored resume position is an RFC
   3339 timestamp plus the sha256 of the last line (10). The daemon's `since` parameter
   is not RFC 3339: it splits the value on the dot and parses both halves as integers,
   so an RFC 3339 string is a 500. The provider converts at the call. The overlap
   `--since` returns because it is inclusive (S8) is dropped by hash: everything up to
   and including the stored hash is skipped, and if that hash is not in the batch,
   every line at the boundary instant is dropped instead. Both cases are unit-tested.
8. **The egress proxy is `ubuntu/squid` pinned by the digest S9 used.** The requirement
   is a CONNECT proxy whose decisions reach the container log. squid itself cannot open
   `/dev/stdout`, because it drops to the unprivileged `proxy` user before it opens its
   logs (S9), but this image's entrypoint tails `/var/log/squid/access.log` into the
   container log, so `docker compose logs egress-proxy` carries every `TCP_TUNNEL/200`
   and every `TCP_DENIED/403`. Verified on the rootless daemon with the generated
   configuration: `github.com` tunnels, `example.com` is refused with 403, and both
   lines appear in `docker logs`. tinyproxy logs to stdout natively (S6) but has no
   trustworthy pinned upstream image, and a fourth image under `images/` is not in this
   phase's scope.
9. **The proxy's allowlist is policy-wide; the per-attempt allowlist is enforced by
   refusal.** One squid instance serves every worker, so its filter is the union of the
   hostnames the deployment permits. Crucible still computes the attempt's own allowlist
   (the policy's `egress_allowlist` plus the adapter's declared endpoints, S6) and
   refuses to launch when that is not a subset of what the running proxy permits, rather
   than letting an attempt run with less network than the policy promised. The computed
   list is recorded in the worker's environment as `CRUCIBLE_EGRESS_ALLOWLIST`.
   A per-attempt proxy is the thing that would make the filter exactly per-attempt; it
   is not needed while one policy is in use and is listed as a follow-up.
10. **The collector's safe copy is by enumeration, not `O_NOFOLLOW` per open.** 08 asks
    for `O_NOFOLLOW` on every file the report copy opens. The worker images carry shell,
    git, curl and jq, and no program that can pass that flag. The collector instead
    enumerates with `find -P`, which never descends through a symlink, and rejects
    symlinks, non-regular files, hard-linked files and files above the policy size cap
    by name before reading them; every rejection is a `collector_rejected_file` event.
    The guarantee about path components is the same; what is missing is the race
    protection, and there is no writer to race: the report directory is mounted
    read-only into a container with no network, and the worker is already gone.
11. **`workspace_clean` means nothing of this attempt is left running.** The provider
    lists containers labelled `crucible.attempt=<id>` after the collector, the bundle
    verifier and the verifier have been removed, and reports everything except the
    worker itself as leftover. The gate fails if the provider could not look.
12. **Cleanup runs after the gates, never before.** 08 requires `logs_drained` first and
    16 requires that nothing a gate consumed is deleted while the task still needs it,
    so the cleanup and retention steps are the last two of the tick. Everything a gate
    reads is an evidence row or a stored artifact by then, so `keep_diff_only` removing
    the checkout and the verifier's tree costs nothing.
13. **Retention resolves the window per subject.** Each deletion names the policy version
    that authorized it, so the window comes from the task's own policy rather than a
    global default. `retention_actions` has one row per (kind, subject), which is what
    makes a second pass a no-op; running the tick twice changes nothing.
14. **The script harness takes its case from the repository.** The e2e worker reads
    `e2e-behavior` from the checkout, so a test chooses the case by building the
    repository rather than by a flag Crucible would have to carry into a launch spec.
    Its sha256 is a build argument of the image, so a changed script and an unchanged
    Dockerfile fail the build instead of producing a second image under one tag.
15. **`script-harness` is a real harness name.** A contract has to be able to name the
    e2e worker, and the path it exercises is the real provider path, so it is a value of
    `HarnessName` with its own declared version range and an empty endpoint list.

## S4's completion condition, re-run

S4 ended `proceed, partial`: three of its probes were made against an empty environment
(no control plane, no credential mounted, no socket proxy), so they proved only that
nothing was reachable in that emptiness. `tests/e2e/test_isolation.py` is the re-run it
asked for, on the rootless daemon, with PostgreSQL up, the socket proxy up, the egress
proxy filtering, a credential directory mounted for the worker's own harness and the
other three harnesses' credential directories present on the host. Twenty probes, every
one refused:

| Probe | Result |
|---|---|
| `/var/run/docker.sock`, `/run/docker.sock` | refused |
| the socket proxy by name and by the host bridge address | refused |
| PostgreSQL by name and through the internal gateway | refused |
| the Crucible API | refused |
| another harness's credential file (Codex, Claude Code, AGY) and the credential root | refused |
| `git push` | refused |
| a non-allowlisted host through the egress proxy | refused |
| a direct connection by IP and by name, bypassing the proxy | refused |
| writing to `/`, the identity mount, `/usr/local/bin` | refused |
| `chown` of the report directory, `mknod` | refused |

One correction to S4's own probe list came out of it: `curl` exits 0 on any HTTP
response, including the egress proxy's own 403, so a probe that does not pass `--fail`
reports "reached" when the proxy answered for a host the worker cannot reach. The
control-plane probes also bypass the proxy explicitly: the question is whether the
worker can reach the socket, the database or the API, not whether squid will answer.

## Image digests, rootless versus rootful

S7 built the three harness base images on the rootful daemon and claimed
reproducibility. Rebuilding them with an unmodified `images/build.sh` on the rootless
daemon of the `crucible` service user produced byte-identical results, manifest digest
and config digest both:

| Image | OCI manifest digest | docker image ID |

| `crucible-worker:agy-1.2.4-a0f410dd9e78` | `sha256:4569e89e7a938cc8d53941abde46a0e01495ca6c8534ebb30eb11bc8ad2b402b` | `sha256:f9a5b738ab8dde2b5f77a968443cc82f58edbcadc5e6babf84a7582605761843` |

Every value matches `docs/spikes/S7.md` exactly, so the reproducibility claim holds
across daemons and not only across runs on one. The e2e image is
`crucible-worker:script-harness-1.0.0-6a2bee03d6f1`, and CI's build of it on a
GitHub-hosted runner produced the same manifest digest
(`sha256:9b2d6a12180a85408d9b7460675732b8baa1619a866b7c65aae08cecb8b65395`) and the
same image ID as the local rootless build, which retires S7's limitation that
reproducibility had only been checked on one machine. The two runs report different
`docker image inspect` sizes, which is the storage driver's accounting and not a
difference in the image. `images/build.sh` is unchanged by
this phase, which is deliberate: any edit to it changes `crucible.build_inputs` and so
the tag of every harness image, for no change in content.

## Where the local arrangement is not finished

`make up` on the reference workstation cannot bring the whole Compose project up on the
rootless daemon, and no code change fixes it. The daemon runs as the `crucible` service
user, whose only path to the project directory is through `/home/<operator>`, which is
mode 750. The compose client must read `compose.yaml`, the build context and the
generated proxy configuration as that user, and it cannot. The arrangement needs an
operator decision, not a patch: either the project lives somewhere the service user can
read, or the operator gains read access to the socket and runs the project from a
daemon that can see the working tree. Recorded as a follow-up; nothing in the provider
depends on it, and CI, which has an ordinary daemon, runs `make up` unchanged.

The local e2e tier therefore runs in developer mode (13): PostgreSQL, the socket proxy
and the egress proxy as containers on the rootless daemon, Crucible in the test process
with the provider pointed at the socket proxy, and the artifact root a world-traversable
directory outside the operator's home. Same provider, same proxy, same worker shape,
same tier definition CI runs.

## Proposed specification changes

1. **11, evidence kinds.** `verification_ran` and `workspace_clean` now consume evidence,
   and the `EvidenceV1` kind list in 11 has no name for either. C3 adds
   `verification_run` and `workspace_state`; 11's list should name them.
2. **08, `O_NOFOLLOW`.** The collector's report copy runs in a worker-shaped container
   whose image has no program that can open with `O_NOFOLLOW`. Either 08 should describe
   the guarantee (no symlink is followed, no hard link, device or oversize file is
   copied, every rejection recorded) and leave the mechanism open, or the worker images
   must gain a small helper for it.
3. **08, the checkout lease.** 08 puts the lease inside `prepare`; the lease is a fenced
   database row and the provider has no database. The sentence should say the supervisor
   takes it before `prepare` runs.
4. **08, `git bundle verify`.** 08 has Crucible run it. Running it in the Crucible
   process means git in the Crucible image over a file a worker's tree produced. It is
   run in a throwaway container with `--network none` instead, which is the stronger
   reading of the same rule; 08 should say so.
5. **08 and 13, preparation in a container.** The same argument applies to the clone,
   the shims and the git configuration. 08 reads as though `prepare` is Crucible's own
   process; the rootless uid mapping and the absence of git in the Crucible image both
   argue for a container, and that is what C3 does.
6. **06, the bundle.** The identity bundle carries `contract.json` beside
   `contract.yaml`, because a worker image has jq and no YAML parser and the two are the
   same document. 06's layout should list it.
7. **07 and 18, the e2e harness name.** 18 requires a script harness; 07's `HarnessName`
   has only the three real ones. `script-harness` is now a fourth value.
8. **13, the egress proxy's allowlist granularity.** 13 says the worker allowlist is the
   union of the policy's list and the adapter's endpoints, which reads as per-attempt.
   One Compose-level proxy makes the filter deployment-wide; Crucible refuses an attempt
   whose allowlist exceeds it. 13 should either state that, or call for a per-attempt
   proxy.
9. **13, `/tmp` and `noexec`.** S9's probe shape mounted `/tmp` with `noexec`. C3 does
   not: a harness that writes a helper into `/tmp` and runs it would fail, and the
   phase has no evidence either way for the three real harnesses. 13 should say which
   it wants, and C5 should test it with a real harness.
10. **14, fenced tables.** `log_chunks` and `retention_actions` are written only by the
    supervisor and are fenced accordingly; 14's list should name them.

## Follow-ups

1. An operator decision on where the Compose project lives so `make up` can run on the
   rootless daemon (above).
2. A per-attempt egress proxy if a deployment ever runs policies with different
   allowlists at once.
3. Heartbeat rows (10) are still not written; the log-advance signal exists as a pull
   each tick but no `heartbeats` table. Stall detection is unimplemented.
4. Retention covers log chunks and acknowledged wakes. Completed workspaces are removed
   by the cleanup pass rather than by a dated retention sweep, and the bootstrap archive
   window has nothing to act on until C6.
5. S9's follow-up 5, a reboot test of the lingering service user and the enabled unit,
   is still open; `make preflight` warns when the AppArmor profile the rootless daemon
   needs after a reboot is missing.
