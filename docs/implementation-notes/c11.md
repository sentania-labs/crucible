# C11: one worker image, built by CI and published by the release

## Result

The four per-harness worker images are now one, `images/worker/Dockerfile`, carrying
Claude Code, Codex (with its code-mode host), AGY and Hermes at the current releases.
The operator decided this on 2026-09-22 at 3:09 PM: "let's go with one image, it'll make
the tests cheaper and easier in the long run." The script-harness image stays separate;
it exists for CI.

`make images` builds both images on the rootless daemon from a staged copy of `images/`
(FDY-0072). CI's `images` job builds them from the pinned inputs on a fresh runner and
fails on any tag, harness version or OCI digest that differs from `images/manifest.env`.
The release builds them from scratch again, refuses to publish unless the manifest is
reproduced, and pushes both to `ghcr.io/sentania-labs/crucible-worker` under the
service image's never-overwrite rule. No tag was pushed and nothing was pushed to GHCR
from this branch: the first publication happens on the release Foundry cuts.

Claude Opus 5.5 is in the Claude Code routing pool, disabled.

## One image, per-harness labels

`build.sh` reads each `ARG HARNESS_<NAME>_VERSION` of a Dockerfile and labels the image
`crucible.harnesses=<list>` and `crucible.harness.<name>.version=<pin>` for each. A pin a
later stage redeclares must agree with the first or the build refuses. The worker tag is
`crucible-worker:<YYYYMMDD>-<build>`, the date being the UTC day of `SOURCE_DATE_EPOCH`;
the build hash already changes with every pin. `manifest.env` records the tag, the
digest and the harness list per image, `check-manifest.sh` holds the list equal to the
Dockerfile, and `tests/unit/test_harness_versions.py` holds every recorded version inside
its adapter's range, so the manifest-versus-range guard still covers each harness.

The launch check reads the version label of the harness being launched. Images built
before C11 carry `crucible.harness` and `crucible.harness_version` and are still read,
so older tags on a daemon remain usable as a rollback.

Each adapter launches its CLI by absolute path (`/usr/local/bin/claude`, `codex`, `agy`,
`crucible-hermes`). The Hermes image used to put its virtual environment first on PATH;
the shared image does not, so no other harness's `python3` resolves into Hermes's
dependencies, and the Hermes launch sets that PATH for its own process.

**Promotion.** A promotion row now records every harness the image carries (migration
0018, a JSONB `harnesses` column; existing rows become one-harness documents). Promoting
the worker image makes it the default for all four harnesses, and it is refused whole if
any of them is outside its range. A previous default is retained only when the new image
carries every harness it did, so promoting a narrower image never leaves a harness with
no default. Rollback is promoting the previous digest, which rolls all four back
together. The migration's down step keeps a combined row under its alphabetically first
harness; re-promote after a downgrade.

## CI and the release

The CI `images` job runs `make images-check` on `ubuntu-24.04`. Pull requests import the
BuildKit layer cache the last push to main exported, through `actions/cache`, as a local
cache directory passed to `build.sh`. A cached layer is content-addressed on its
instruction and inputs, so a hit is the layer a from-scratch build of those inputs
produced; every push to main builds with `NO_CACHE=1` and nothing restored before it
exports the cache, and the release builds from scratch again before publishing.

registry's challenge asks.

## Review round

One non-author adversarial review round ran before the push. It attacked a release step
that could pull or publish a wrong image, a pin whose checksum was copied rather than
computed, and a CI job that could pass on a stale cache without proving the digest.
Its findings were addressed in 5634c2a:

- The worker images now carry a label naming their source repository.
- `build.sh` checks the image it loads into the daemon against the OCI archive it
  wrote. Before this, a replaced docker archive could load an image other than the one
  the digest describes.
- The staged `out/` directory is sticky, so another local user cannot replace an
  archive once it is written.
- The publisher sends registry credentials only to the registry host itself: not across
  a redirect, and not to an upload location on another host.
- The two live tiers that still read the pre-C11 label shape were fixed.
- The CI cache comment was corrected. Pull requests restore the cache; a push to main
  builds from scratch before it saves the cache.
- The Opus 5.5 migration's downgrade removes only its own routing version and skips a
  routing policy that has been retired.
- The rollback limit is documented. After a schema downgrade, a combined promotion row
  keeps only one harness.

The run that did the round did not keep its raw output. The list above is that
commit's own record, and the commit defers none of the findings. There was no second
round.

## FDY-0074: streamed publish, ARG-driven Hermes wheel, manifest-driven test

Foundry's review of the pushed branch (FDY-0073) found three things, corrected here.

**1. The publisher no longer holds a blob whole in memory.** `tools/release/worker_images.py`
read each layer of the OCI archive fully into memory and sent it as one monolithic PUT: a
memory spike for a 1.23 GB image and a single long request against a path (GHCR's
bearer-token challenge, a real network hop) the local proof never exercised. `push_blob` now
streams the registry's own chunked-upload sequence: POST opens the upload, a bounded
`CHUNK_SIZE` (8 MiB) read from `OciArchive.blob_chunks` goes out in each PATCH with the
byte range it covers, and an empty-bodied PUT with the declared digest finalizes it. The
archive's own tamper check (a blob's bytes must hash to the name the manifest gave it) now
runs incrementally over those same reads instead of a full buffer: the mismatch can only be
known after the last chunk, so `blob_chunks` yields every chunk it read and then raises,
which happens before the finalizing PUT is ever sent (the chunks already sent sit as an
unfinalized, unreferenced upload the registry garbage-collects). The bearer-token challenge
(401, `WWW-Authenticate`, token fetch against the realm the challenge names, retry) was
already implemented in `Registry.request()`; it is now exercised end to end, not just
monkeypatched around, by a real fake registry server in
`tests/unit/test_release_worker_images.py` (TLS, a self-signed cert generated per test run,
threaded `http.server`) that actually 401s the first request, serves a token, and drives the
POST/PATCH/PUT sequence, including a case where it moves the upload `Location` mid-stream
and one where it redirects the upload off-host (refused by the existing `_url` check,
unchanged). 13 new or changed unit tests; `tests/unit/test_release_worker_images.py` has 14
total.

A non-author adversarial review (a fresh agent, no prior context, told only what the code
does and asked to attack the three vectors the operator named: a chunk boundary that
corrupts a blob, a token or credential leaking into a log or a redirect, a retry that
re-PUTs a manifest or duplicates a blob) found nothing exploitable on any of the three. It
found one real test gap: the existing "tampered stream is never finalized" test proved the
*registry* rejects a bad digest, not that the *client* stops before sending the finalizing
PUT at all. `test_a_tampered_archive_blob_never_reaches_the_finalizing_put` was added to
close it, counting finalize attempts at the fake registry and asserting zero. A second
finding (a `TimeoutError` on a stalled read surfaces as a raw traceback instead of
`PublishError`) was left as is: cosmetic, no credential or header in a traceback, and adding
handling for a timeout the two-attempt retry loop does not need would be scope beyond this
contract. No second review round.

**Proof against a local registry, this time with an auth challenge.** `registry:2` under
TLS from a throwaway CA, run locally with `REGISTRY_AUTH=htpasswd` (bcrypt via Apache's
`htpasswd -B` format, generated with Python's `bcrypt` module) rather than `auth.token`:
standing up a spec-compliant JWT token server (RSA keypair, `rootcertbundle`, a token
endpoint that mints and signs tokens the registry's public key verifies) is real
infrastructure for a proof run whose actual subject is the chunked-upload path and the
publisher's memory footprint, not the token protocol itself. The bearer-token protocol *is*
proved, end to end including the 401 challenge, by the fake-registry unit tests above,
which is what requirement 1 allows ("its `auth.token` mode with a local token server, or
htpasswd if token mode is impractical"). htpasswd still forces every publish call through
the same `request()` 401-challenge-and-retry code path the token flow uses, just answering
with `Basic` instead of `Bearer`, so the proof below still exercises "the same code the
challenge exercises," only the credential scheme differs.

**2. The Hermes wheel filename now follows `HARNESS_HERMES_VERSION`.**
`images/worker/Dockerfile` spelled `hermes_agent-0.19.0-py3-none-any.whl` as a literal in
the `ADD` destination, the final stage's `COPY --from=fetch-hermes`, and the `pip install`
argument; bumping the version ARG alone would build a stage that fetches the new version's
wheel and then look for the old filename in three other places and fail. All three now read
`hermes_agent-${HARNESS_HERMES_VERSION}-py3-none-any.whl`. The PyPI URL's directory prefix
(`e5/30/c85be8...`) is unchanged and stays a literal: it is PyPI's own blake2-256 hash of
that specific wheel file, a different hash than the sha256 `HARNESS_HERMES_SHA256` ARG
checks, and nothing in the Dockerfile can derive it from the version alone. A real version
bump still needs both ARGs (version and checksum) updated together with that prefix, which
is inherent to how PyPI names files, not a hardcoding bug.

Rebuilt with `make images`. The **digest changed**: `WORKER_DIGEST` went from
`sha256:63777532fb1217f56ce1d1fcf9c829cbcb91f64023610db06e6047de6f53cfba` to
`sha256:26904db9ae2913fff93e46f45be2967b1cb5664b4c230be592044e6089d993e0`, tag
`crucible-worker:20260916-339d2e1994a8` (the build-hash suffix is a sha256 over
`pins.env`, `build.sh` and every file in the image directory, so any text edit to the
Dockerfile changes it, whether or not it changes a resolved instruction). This was checked
before trusting it: `docker history --no-trunc` on the old and new images shows the built
layers are otherwise identical (same 181 MB Hermes-install layer size, same everything
else) except the one `RUN` step's recorded command text, which BuildKit embeds verbatim
(ARG references unexpanded) into the image config as `history[].created_by`. That text
necessarily changed, because the fix replaces the literal `0.19.0` inside it with
`${HARNESS_HERMES_VERSION}`. So the image's installed files are byte-identical to the
previous build; the digest differs only because Docker's own provenance metadata quotes
the Dockerfile source, and the Dockerfile source is exactly what this fix had to change.
The contract's expectation that the tag and digest stay unchanged does not hold for this
specific kind of fix; a build-input hash computed over literal Dockerfile text cannot stay
the same when the Dockerfile text does, no matter how functionally equivalent the change
is. `images/manifest.env` now carries the reproduced tag and digest.

**3. `WORKER_LABELS` in `tests/unit/test_harness_versions.py` now reads
`images/manifest.env`.** It was a hardcoded copy of the four harness versions, so a pin
bump in the manifest would leave the test asserting the old ones without failing (a version
this test claims the image carries could differ from what the image actually carries,
silently). `_worker_labels()` parses `WORKER_HARNESSES` out of the manifest the same way
`test_every_manifest_harness_version_is_supported_by_its_adapter` already did, and
`test_the_worker_image_labels_are_checked_per_harness` now iterates that parsed list
instead of a second hardcoded tuple.

## FDY-0082: digests across machines, and the two review findings

### Why CI built different digests

PR 83's first CI run (35803062344, job `images`, 7:40 PM on 2026-09-22) rebuilt both
images on `ubuntu-24.04` with the same tags but different digests from the ones in
`images/manifest.env`:

| Image | Workstation (manifest) | CI run 35803062344 |
|---|---|---|
| script-harness | `sha256:fdbd14b5...` | `sha256:68fa6164...` |
| worker | `sha256:26904db9...` | `sha256:68c37b0c...` |

The suspects in order:

- **Builder.** Both used the pinned `docker-container` builder (BuildKit v0.32.2 from
  the digest in `pins.env`); the CI log shows it pulling that digest and creating
  `buildx_buildkit_crucible-images0`. Not the daemon's built-in builder.
- **Daemon.** A from-scratch build on the workstation's rootful daemon gave the same
  `fdbd14b5` as the rootless one. Not the daemon.
- **apt, base image, compression, cache.** The CI and workstation step logs are the
  same line for line (same 9377 kB of indexes, the same 31 packages, the same
  certificate counts). The image config digest differed too (`eb84655b` in CI,
  `5d89dda6` here), and the config holds only the uncompressed layer digests,
  so layer contents differed, not their compression. The CI run imported no cache.
- **Host state `SOURCE_DATE_EPOCH` does not cover: the file mode.** The workstation's
  umask is 002, so the checkout holds `images/ca/sentania-lab-root.crt` and
  `images/worker/requirements.lock` at 0664; `actions/checkout` on the runner writes
  them at 0644. A `COPY` without `--chmod` keeps the source mode, so that mode goes into
  the layer. `crucible.build_inputs` hashes file contents but not modes, so the tag
  stays the same while the digest changes.

Proof: the same build with only the certificate set to 0644 produced CI's
`68fa616441cf26db...` and CI's config `eb84655b...` exactly.

The fix is `--chmod=0644` on the two build-context COPYs (the others already set
`--chmod` or copy from another stage). `build.sh` now refuses a build-context `COPY`
or `ADD` (any case, including after `ONBUILD`) whose own flags carry no `--chmod`, so a
new one cannot bring the problem back. The review round found one more host input in
the same family: the file's mtime. `rewrite-timestamp` only clamps a file *newer* than
`SOURCE_DATE_EPOCH`, so a checkout from before an epoch bump would keep old mtimes in
the COPY layer. It would also change which files the later `touch` RUN layer holds. An
attempted fix that stamped the staged copy to the epoch proved this: the script-harness
layer lost the 7374-byte `harness.sh` from its `touch` layer, which would have given
`make e2e-image` (direct `build.sh`, no staging) a different digest under the same tag.
So `build.sh` instead refuses any context file that is not strictly newer than the
epoch, and every path clamps the same way. The Dockerfiles and `build.sh` changed, so
both tags moved and `images/manifest.env` was rebuilt. **The images are
byte-reproducible across machines. The CI job still compares the full digest, not a
reduced check.**

The earlier "clean clone on the host daemon" proof in this file did not catch this:
that clone was made by the same workstation user with the same umask, so it inherited
the same 0664.

### Reviewer P1: the 0019 downgrade and referenced policy versions

The downgrade deleted the policy version 0019 wrote even when a task had been submitted
against it, so a rollback left the task naming a row that no longer existed. Now it:

- retires that version (`retired_at`) when any task references it, and deletes it only
  when none does. The task still resolves its policy, and the version before 0019 is
  back in force because "in force" is the latest non-retired version;
- deletes the routing version only when no policy (retired or not) names it, as 0011
  does;
- targets the lowest marked version that is *not retired*. Without this, a
  down/up/down cycle would find the version the first downgrade retired and leave the
  re-upgrade's new version in force;
- acts only when that version's routing version still holds the Opus 5.5 entry exactly
  as 0019 wrote it. After a first downgrade, the lowest marked version left can be a
  copy the operator uploaded (it keeps the description, marker included). If that copy
  names a routing version where they enabled Opus, it is theirs and is left in force.

After the downgrade, the latest version that is not retired is in force. That is the
version before 0019, unless the operator uploaded a newer one.

`test_0019_downgrade_keeps_the_version_a_task_was_submitted_against` submits a task
through the API against the 0019 version, downgrades, and resolves the task's policy
and routing through the unit of work (`policies.get`, `load_routing`), the lookups the
supervisor makes. It then upgrades and downgrades again, and checks that the second
round removes only the new policy and routing versions. Against the old downgrade it
fails with `NoResultFound` on the deleted row.
`test_0019_downgrade_leaves_an_operator_copy_that_enabled_opus_alone` covers the
operator copy. Without the exact-entry check it fails: the copy is removed and version
5 is in force instead of the operator's 7.

### Reviewer P2: host-mode login commands

C11 had changed the login defaults to the worker image's absolute paths, which broke
host-mode logins from user-scoped installs such as `~/.local/bin`. `LoginFlow.argv` is
back to the bare names, found on `PATH`. A new `image_binary` field holds the image path,
and `LoginRegistry.resolve` swaps it in only when a provider runs the login in a
container. An operator-configured command is used as given in both modes.
`test_a_host_login_finds_the_cli_on_path_and_a_container_login_uses_the_image_path`
covers both modes. Against the old defaults it fails with "/usr/local/bin/claude is not
installed on this host".
