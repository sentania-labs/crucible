# C9: cluster deployment manifests, proven on kind

## Result

`deploy/kubernetes` is the deployable shape of Crucible: a kustomize base for the
`crucible` and `crucible-workers` namespaces, a lab overlay of named placeholders, a
kind overlay for the proof, the shape of every Secret, and an Argo Application with
automated sync off. `docs/deployment.md` is the operator-facing runbook.

`make manifests` renders all four kustomizations, validates every object with a pinned
`kubeconform`, and asserts the security-relevant fields on the rendered objects.
`make deploy-kind` brings the whole thing up on a disposable kind cluster with the C8b
tooling, confirms the admin status page reports the Kubernetes provider green, and runs
one script-harness task end to end through the deployed API on the Kubernetes provider.

No real cluster, no kubeconfig under `~/.kube`, and no DNS record was touched.

## The 0.4.0 release reference is what the proof renders

`0.4.0` is the first release carrying the Kubernetes provider, and its tag is cut after
this change merges. The base pins `ghcr.io/sentania-labs/crucible:0.4.0` in one place.
`make deploy-kind` builds the working tree under that exact reference, loads it directly
into kind without a pull, and applies the committed overlay with no image-name or tag
transformer. The manifest reference and the image under test are therefore byte-for-byte
the release reference. The working-tree image still reports `0.0.0.dev0` on `/v1/health`,
which correctly distinguishes proof provenance from a published artifact.

## What the real cluster exposed

Six things that a rendered manifest and a unit test cannot tell you, each found by
running it.

1. **The supervisor's ServiceAccount cannot live in `crucible-workers`.** 26 puts it
   there, but a Pod can only use an account from its own namespace and the supervisor Pod
   runs in `crucible`. The account moved to `crucible`; the RoleBinding stayed in
   `crucible-workers` and names it across the namespace boundary, so the permission is
   still namespaced exactly as 26 requires. 26 records this.

2. **The api needs the same account as the supervisor.** `GET /v1/admin/status` asks every
   provider for its health, and the Kubernetes provider answers by running 26's readiness
   canary: a real Pod, created and read and deleted in `crucible-workers`. An api with a
   weaker account would render a status page saying the cluster is broken when it is not.

3. **`pods/exec` needs `create`, not only `get`.** The client opens the reader Pod's tar
   stream as a GET WebSocket upgrade, so `get` looked like the whole answer. The API
   server authorizes an exec against `create` as well, and a Role with only `get` returns
   403 at the upgrade. Every `prepare` failed with an unreadable `prepared-head.txt` until
   the verb was added. 26 now carries the exact verb set and a unit test holds the
   manifest to it.

4. **The readiness canary runs the first configured image reference, and a bare
   repository is not one.** `kubernetes.image_repositories` holds bare repositories
   because `list_images` appends each tag; the canary takes the first entry verbatim, so a
   kubelet reads it as `:latest`. On kind that was an `ImagePullBackOff` that blocked
   `GET /v1/admin/status` for the whole launch timeout and reported the namespace as not
   ready. The new `kubernetes.probe_image` setting names one exact, pullable reference and
   `crucible/cli/wiring.py` passes it as its own provider field, so image enumeration
   never treats it as a repository; two unit tests cover it.

5. **A headless PostgreSQL Service does not resolve until it has a ready endpoint.** First
   boot failed on name resolution rather than on a refused connection, which is a much
   worse thing to find in a log. The Service is a normal ClusterIP now, and both
   Deployments and the migration Job carry a `wait-for-database` init container, so a
   first sync does not depend on restart backoff being shorter than someone's patience.

6. **The api's liveness probe has to tolerate a provider health call.** Opening the status
   page runs a canary Pod and blocks the event loop for tens of seconds. A probe tight
   enough to kill the api for that would restart the process every time an administrator
   looked at it. The probe is now 30 s period, 10 s timeout, six failures.

None of these is a Kubernetes subtlety anyone would have guessed from the spec. They are
the reason `make deploy-kind` exists.

## Decisions

**Pod Security admission is `restricted` on both namespaces.** The untrusted half is
`crucible-workers` and 26 is explicit about it; `crucible` holds Crucible's own trusted
pods, so `baseline` there would have been defensible and was what the first draft had.
The review pointed out that every pod the base creates already satisfies `restricted`,
PostgreSQL included: uid 999, read-only root, capabilities dropped, an emptyDir for the
socket the entrypoint writes. Enforcing what is already true costs nothing and refuses a
later edit that adds a root container, a hostPath or a hostPort rather than warning
about it.

**One ResourceQuota, and it is also the concurrency bound.** 26 reports `max_concurrency`
from the quota, so the numbers in the lab overlay are the lever for how many attempts run
at once. The quota also demands requests and limits on every container in the namespace,
which is how the smoke's own origin-seed Pod discovered it.

**The artifact claim is `ReadWriteMany`.** The api serves what the supervisor wrote and
they are separate Deployments. That is a new prerequisite on the cluster's storage and it
is in 26's checklist and the runbook. Object storage would remove it and is a later
phase. The kind overlay uses `ReadWriteOnce` because kind's local-path provisioner is
single-node, which is exactly the class of thing kind cannot prove.

**The migration Job is an Argo sync hook.** `crucible serve` refuses to start against a
schema that is not at head, so a deployment without it is a CrashLoopBackOff with the
right reason rather than a corrupt database. The hook annotations make it run on every
sync; a plain `kubectl apply -k` creates it once, and `make deploy-kind` deletes it first.

**Automated sync is off.** The first sync creates two namespaces, a database, RBAC and
the Secret objects, and the SealedSecret placeholders are not real ciphertext until
lab-admin seals them. A person reading the diff is what catches one that was missed.
Turning automation on afterwards is lab-admin's record to make, not this repository's.

**The secrets directory is `secret-shapes/`, not `secrets/`.** `.gitignore` ignores
`secrets/` at any depth, so a directory with that name would never have been committed
and the omission would have been silent. Renaming is better than negating the ignore
rule, which exists for a good reason.

## The external review round, and one deviation from the allowed paths

Two findings, both real, both acted on.

**The probe image was polluting the image listing.** The first implementation gave
`probe_image` effect by prepending it to `kubernetes.image_repositories` in the wiring,
which kept the change inside C9's allowed paths. `list_images` walks that same tuple: it
takes the repository part of each entry to list tags, then builds `<entry>:<tag>` to
resolve each one, so a tagged entry cost a second tag listing and, per tag, a reference
that `crane digest` refuses to parse (one failing crane process each, suppressed like
an unavailable image) on every `GET /v1/admin/images`; `parse_reference` itself accepts
the shape. On a registry with many historical tags that is an admin endpoint that
crawls.

Fixing it properly means one field on `KubernetesConfig` and three lines in
`_probe_image`, in `crucible/adapters/execution/kubernetes.py`, **which is not in this
task's allowed paths**. It was changed anyway, deliberately and minimally, with two unit
tests, because the defect is in code this branch introduced and the review round exists
to catch exactly that. The deviation is named here and in the task report rather than
buried: no other provider behaviour was touched.

**The ResourceQuota was overstating capacity.** One attempt creates a preparer,
worker, collector, bundle-verifier and verifier Job. The quota retains its
15-Job guardrail, and the provider divides that count by five before reporting attempt
capacity. The status page therefore reports three, and a unit test holds the conversion.

## The kind proof

`make deploy-kind`:

1. builds the Crucible image under the exact `ghcr.io/sentania-labs/crucible:0.4.0`
   reference the manifests render, then loads it into kind without a pull;
2. generates a per-run CA and starts the disposable OCI registry **over TLS**, because
   `k8sregistry.py` speaks HTTPS only and is right to: resolving a tag to a digest is
   where the harness version refusal happens, before a kubelet pulls (07, 26), so it must
   not be a plaintext hop. The host pushes over loopback, which the Docker daemon treats
   as insecure and does not verify; the cluster pulls by the registry's own name, which
   is what the certificate covers;
3. creates a kind cluster with Calico (the C8b pin and hash, now shared in
   `tools/kind/cluster.sh`), a pod PID limit, and a containerd `certs.d` host file for
   the CA. `registry.configs` in `containerdConfigPatches` is silently ignored by
   containerd 2.x, which is why the CA goes in `certs.d` and `config_path` is set;
4. applies `overlays/kind` with a generated overlay carrying the image under test, the
   registry's address and the CA;
5. runs `tools/smoke/kubernetes_smoke.py`;
6. deletes the cluster, the registry, the image tags and the scratch directory on every
   exit path, and fails the run if anything remains.

The smoke seeds its throwaway origin repository with a Pod that mounts the same
reference-cache claim the preparer does, under the same `restricted` admission. There is
no hostPath anywhere in the run, so the claim being exercised is the one the manifests
describe.

## CI placement

The `manifests` job runs on `ubuntu-24.04`. It needs neither a Docker daemon nor lab
access, and the repository is public, so hosted minutes are free: rule 4 of the
`github-ci` skill. It is deliberately not the `lab` pool, which exists to reach the lab
and would only queue for a job that needs nothing from it.

`kubectl` and `kubeconform` are both pinned by sha256 in the job rather than taken from
the runner image: kubectl carries the kustomize build, and a different kustomize renders
differently, which would break the one property this job exists to guarantee, that what
CI renders is what `make manifests` rendered locally.

`make deploy-kind` is **not** in CI. It builds an image, runs a kind cluster with Calico,
a TLS registry and a full task lifecycle, which is the `e2e-kind` job's cost again on
every pull request, and `e2e-kind` is still establishing its own runtime and flake
history (C8b). It is a local gate for a change to `deploy/kubernetes`, named in
`docs/deployment.md`. Proposing it as a CI job belongs with whatever makes `e2e-kind` a
required check.

## Limitations

- Nothing cluster-specific is proven. No ReadWriteMany storage, no ingress controller, no
  certificate issuer, no image pull secret, no lab network, no DNS. Those are seen for the
  first time on the lab cluster, which is why the first Argo sync is manual.
- Single node, so ReadWriteOnce behaviour on kind and not cross-node attachment.
- The proof ran a locally built image named with the pinned `0.4.0` reference, not a
  published artifact with that tag.
- `latest_attempt.image_digest` reads null on the finished attempt in the task view, while
  the digest is resolved and recorded at launch. Not chased here; it is a view question,
  not a deployment one.
- The `kind` Docker network is created when absent and never removed, by either kind
  tier. It is shared with every other kind cluster on the host, including another
  agent's, so removing it would be worse than leaving it; both cleanup traps therefore
  report success with it still there.
- The lab overlay's SealedSecret placeholders are not valid ciphertext by design. A sync
  of the overlay as committed creates SealedSecrets the controller refuses, and no
