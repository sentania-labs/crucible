# C6 implementation notes: bootstrap import and readiness

Phase C6 per `docs/spec/20-implementation-phases.md`: the bootstrap import API and
commit of 15, the `crucible-admin bootstrap` commands, and the readiness report of 19
(`docs/readiness.md`). Same rule as the earlier phases: where the specification left
something open, the simplest choice consistent with it was taken and is recorded here;
nothing here changes the specification, and the changes it needs are listed at the end.

One boundary shaped everything below: this phase implements and tests the import path
against synthetic bundles only. The operator's real ledger was never read, exported or
imported, and `foundry-ledger mark-migrated` was never run. The real handoff (15 steps
1, 5 and 6 on the real ledger) is Foundry's act with the operator's explicit go, after
this phase merges.

## Findings: where 15 and the real producer disagree

The contract for this phase asked that validation match what `foundry-ledger export
--format crucible` actually writes rather than what 15's prose implies, and that any
disagreement be a finding rather than something papered over. Three were found. The
producer (`/home/scott/devel/foundry/tools/foundry-ledger`, its `crucible_bundle` and
`bundle_content_hash`) was read, and a bundle it wrote for its own synthetic fixture is
committed as `tests/fixtures_data/bootstrap/foundry_ledger_example.json` and imported
by the unit and integration tiers.

1. **The task key is `id`, not `external_id`.** 15's example writes each task as
   `{ "external_id": "FDY-0001", ... }`; the producer writes the task record exactly as
   its YAML shape has it, with `id`. The import accepts `id` and stores it as Crucible's
   `external_id` (03: "the orchestrator's stable ID"). A bundle written to 15's example
   would be refused with `tasks[0].external_id: unknown field` and `tasks[0].id:
   required`, which is the right outcome: there is one producer and the import matches
   it. 15 should say `id` (proposed change 1).
2. **Two producer states have no row in 15's table.** foundry-ledger's lifecycle is
   `proposed, dispatched, running, reported, accepted, rejected, blocked, missing,
   abandoned, done`. 15 maps eight of those and says nothing about `rejected` and
   `missing`. The import does not guess: a bundle carrying either is refused, naming the
   task and the state (`tasks[i].state: state 'rejected' has no mapping in 15's table;
   the import does not guess`). **This is the one finding that can stop the real
   handoff:** if the operator's ledger holds a task in either state when it is exported,
   the import refuses the whole bundle and the operator has to decide the mapping first.
   The obvious candidates are `rejected` to Crucible's `rejected` (a terminal state with
   the same name and near enough the same meaning) and `missing` to `cancelled` with
   the source state kept in the record, but that is a decision for 15, not for this
   phase (proposed change 2). Whether the real ledger holds such a task is unknown here
   by design.
3. **`source.migrated` is the import id or null, not a boolean.** 15's example shows
   `"migrated": false`; the producer writes the Crucible import id it was frozen with,
   or `null` before `mark-migrated`. The import accepts a string, a boolean or null,
   records the value on the import row and in the report (`source_migrated`), and never
   decides anything by it, which is what 15's own paragraph on the field says (proposed
   change 3).

Two smaller shape facts, not conflicts: the producer's task record has nineteen fields
(15 lists ten of them), and every timestamp is local wall time with the zone
abbreviation, `YYYY-MM-DD HH:MM CDT|CST`, never RFC 3339. Both are handled below.

## Decisions

1. **The bundle is validated in full, then written in one transaction, or nothing is
   written.** `crucible/domain/bootstrap.py` collects every problem of 15 step 2 over
   the parsed JSON (schema version, the top-level and per-record field sets, types,
   `counts` against the arrays, the content hash recomputed the producer's way, `id`
   uniqueness, the state map, strictly increasing `seq`, every event naming a task in
   the bundle, `source.migrated` present) and the service adds what needs the database:
   the owning principal exists, and no imported `id` collides with a task that
   principal already has. The response is the whole list with a path per problem; the
   refusal is recorded as `admin_refused` through a unit of work of its own (25), and
   the tables are exactly as they were. The rollback is tested by failing the write
   after the fourth event and counting every table.
2. **Unknown fields are refused, not dropped.** A bundle with a field the import cannot
   name (a nineteenth task field the producer does not write today, a seventh event
   field, a top-level key) is refused with that path. This is the only way "a field
   that silently vanishes is a defect" can hold against a producer that may grow.
3. **The record travels whole, and the report names what the columns did not carry.**
   Each imported task gets one `bootstrap_task_imported` event whose payload holds the
   producer's task record verbatim plus the per-task `uncarried` list; each source
   event becomes one `bootstrap_event_imported` event with the original `seq`, the
   original timestamp string, `task`, `event`, `who` and `detail` in its payload, its
   `ts` column the normalized UTC instant, a new global `seq`, `verified: false` (a claim
   from another ledger, not something Crucible observed), and the importing principal
   as `principal`. The verification report's `uncarried` block lists, per task, every
   field with a value that has no `tasks` column (`scope`, `objective`, `contract`,
   `model`, `harness`, `execution`, `refs`, `evidence`, `blockers`, `decisions_pending`,
   `last_report`, `parent`), a title or project the column had to truncate, a null
   title or project carried as empty, and a `repository` that matched no registration;
   and once for the events, where each of the six producer fields went.
4. **Timestamps are normalized by the abbreviation, exactly.** `CDT` is UTC-5 and `CST`
   is UTC-6, so the conversion needs no zone database and cannot be wrong on either
   side of a change. RFC 3339 with an explicit offset is accepted as well; a timestamp
   with neither is a problem.
5. **A task's repository is matched by name, or it lands on the `bootstrap` sentinel.**
   `tasks.repository_id` is a non-null foreign key and the producer's `repository` is a
   free string (a name, a path, or null). A value that names a registered repository
   is used; anything else puts the task on a sentinel registration named `bootstrap`
   (url `bootstrap://foundry-ledger`, created by the import on first need, registered
   by the importing principal), the report lists every task on it under
   `repositories.sentinel`, and the task's `uncarried` names the original string.
   Registering a real repository is the operator's act (04); the import never invents
   one with a URL.
6. **Imported tasks belong to the principal the caller names, default the caller.**
   `?owner=<principal name>` on the submit and `--owner` on the CLI. After the handoff
   Foundry's own principal should own its tasks, so `GET /v1/tasks` and the external
   id uniqueness rule (`uq_tasks_principal_external`) apply to them as to anything
   Foundry submits later; a bootstrap principal of a different name would leave the
   historic ids free for reuse. The report records both the owner (`principal`) and
   the importer (`imported_by`).
7. **No contract, and the policy in force.** An imported task has `contract_version 0`
   and no `task_contracts` row: the producer's `contract` is Foundry's own shape, not
   a `TaskContractV1`, and storing it as one would lie to every reader of the task
   view. The view returns `contract: {}` for such a task. `policy_name` and
   `policy_version` are the newest `default-software` version that is not retired,
   because the ledger carries no policy reference and the columns are not nullable.
8. **`running` and `dispatched` get a synthetic `bootstrap` execution and an
   unsupervised attempt, and the supervisor never sees the attempt.** The execution
   has provider and image `bootstrap`, the task's `harness` and `model` where they fit
   the columns (else `bootstrap`, named in `uncarried`), `policy_snapshot.bootstrap`
   naming the import, state `active`; the attempt is number 1, state `running`, no
   handle, and the new column `attempts.unsupervised` set. `Attempts.list_in_states`
   excludes unsupervised rows, so every scan that drives the supervisor (launch,
   observe, timeout, reconcile, cleanup, retention, the per-harness cap, the status
   document's workers, the concurrency in use) leaves them alone without a change to
   any of those paths; `list_for_task` and `list_for_execution` still return them, so
   the task view shows the attempt. Cancelling such a task closes its execution and
   moves it to `cancelled` without a worker to drain; the attempt row stays `running`
   as the record of a run Crucible never observed (limitation 2).
9. **The synthetic rows are written under the live supervisor's fenced token.**
   `executions` and `attempts` are fenced to the supervisor (14). The import is an
   administrative mutation and so already requires a live supervisor lease (25); it
   reads that lease's token inside its own transaction and presents it for the two
   inserts. A takeover between the guard and the insert makes the database reject the
   write and the whole import rolls back, which is the fence doing exactly its job. No
   other path presents a token it does not hold, and this one is the only place
   outside the supervisor that writes those tables.
10. **The same bundle twice is one import.** A submit whose `content_sha256` matches an
    existing import replays that import's report (200 rather than 201) and writes
    nothing, whatever the import's state. A retried handoff is therefore idempotent
    without an `Idempotency-Key`, and works the same from the CLI.
11. **Several imports may be verified; one holds authority.** Two bundles with disjoint
    ids can both be verified (the second is refused only where its ids collide). The
    commit is refused unless the import is `verified`, and refused while another import
    is `authoritative`, naming it and ADR 0006; the database enforces the second rule
    as well with a partial unique index on `state = 'authoritative'`. A verified import
    cannot be undone: its tasks and events are written, and events are append-only.
12. **The commit records the handoff on every task and touches nothing else.** One
    `bootstrap_handoff` event per imported task (`before.authority: foundry-ledger`,
    `after.authority: crucible`), the import row moved to `authoritative` with who and
    when, and one `bootstrap_import_committed` admin event. Task states and
    `updated_at` do not move.
13. **Both entry points, one service, guarded the same way.** `POST /v1/import/bootstrap`
    (the body is the bundle itself, exactly as the producer writes it, so the reason
    and the owner are query parameters), `GET /v1/import/bootstrap`,
    `GET /v1/import/bootstrap/{id}`, `POST /v1/import/bootstrap/{id}/commit` (reason in
    the body, as the other admin routes); `crucible-admin bootstrap submit --file
    [--owner]`, `show`, `list`, `commit`, in local and remote mode. Submit and commit
    take `guard_mutation` (a reason, a live supervisor) and write one admin event each
    with the before-and-after summary; both kinds are in the audit tail. The admin
    status document gains a `bootstrap` part (the authoritative import, the imports)
    because 25 says the API exposes the import state.
14. **The secret scanner runs over every record.** A task or event whose JSON matches a
    credential pattern is refused by path and pattern, never stored, never echoed (12,
    25): the records are served back by `/v1/tasks/{id}/events`.
15. **Five event kinds, one migration.** `bootstrap_import_verified`,
    `bootstrap_import_committed`, `bootstrap_task_imported`, `bootstrap_event_imported`,
    `bootstrap_handoff`. Migration 0010 adds them with the archive-on-downgrade pattern
    of 0007 to 0009, creates `bootstrap_imports` (14's columns plus `content_sha256`,
    `schema_version`, `source`, the owning principal, who imported and who committed),
    and adds `attempts.unsupervised`. The downgrade drops the flag and the table,
    leaves the synthetic execution and attempt rows, and archives the five kinds'
    events in `events_c6_archive` for the next upgrade to restore: events are
    append-only and the audit log is never deleted to make a constraint fit.
16. **The integration fixture truncates on the way out as well.** A downgrade archives
    task-bound events and the upgrade puts them back by foreign key, so rows the last
    test of a module leaves behind break the migration tests that run after it. The
    `engine` fixture now truncates on teardown too, which is what let
    `test_bootstrap_import.py` and `test_migrations.py` share one run.

## The live tier

`make e2e-admin` gains a third test: a synthetic bundle submitted through the API on the
live stack (the rootless daemon, real PostgreSQL), shown and listed through the CLI,
committed through the CLI, then the orchestrator's start-of-session over the result and
a supervisor tick that leaves the two unsupervised attempts alone. The recorded entries
and the run times are in the phase report, not here.

## Where this differs from the specification

- **15, the task key.** `id` rather than `external_id` (finding 1).
- **15, the state table.** Two producer states are refused rather than mapped (finding
  2).
- **15, `source.migrated`.** A string, a boolean or null (finding 3).
- **15 step 3, "under a `bootstrap_imports` row".** The row carries no foreign key from
  `tasks`; the link is the import id in every `bootstrap_task_imported` payload and the
  task ids in the import's manifest. 14's `tasks` table is unchanged.
- **15 step 2, "the full problem list".** Two rules run only against the database (the
  owner exists, no external id collides) and so come after the pure rules; they are in
  the same list.
- **25, "`import` is CLI-only".** The API of 15 exists as well, and the CLI calls the
  same service; the CLI docstring now names the remaining gap (`export`).

## Proposed specification changes

1. **15, the import contract.** Write the task record as the producer emits it: the key
   is `id`, there are nineteen fields, and timestamps are `YYYY-MM-DD HH:MM CDT|CST`.
   Say that `id` becomes Crucible's `external_id`.
2. **15 step 2, the state table.** Decide `rejected` and `missing`. Until then the
   import refuses a bundle that carries either, and the real handoff can be refused on
   that ground.
3. **15, `source.migrated`.** The Crucible import id the ledger was frozen with, or null.
4. **15 step 3.** Name the `bootstrap` sentinel repository, the owning principal, the
   synthetic execution's shape (provider `bootstrap`, `contract_version 0`), and that
   the unsupervised attempt is invisible to the supervisor's scans and stays `running`
   through a cancellation.
5. **15 step 4.** Define "a diff of any field that could not be carried" as the
   per-task `uncarried` list and the per-field event map above.
6. **15 and ADR 0006.** State the idempotence rule (same content hash, one import) and
   that several imports may be verified while exactly one is authoritative.
7. **14.** `bootstrap_imports` as built (the extra columns), `attempts.unsupervised`,
   and the partial unique index on the authoritative state.
8. **10.** The five event kinds.
9. **25.** The `bootstrap` group in the CLI table and the `bootstrap` part of the status
   document; `export` remains the one named gap.
10. **04.** `GET /import/bootstrap` and `GET /import/bootstrap/{id}`, and the query
    parameters of the submit.

## Limitations

1. **The real ledger was not imported.** Everything above is proven on synthetic
   bundles and on the bundle the real producer wrote for its own synthetic fixture. The
   readiness row that needs the real ledger imported, verified and committed is
   unproven in `docs/readiness.md` with that gap named; it is Foundry's act after this
   phase merges, and finding 2 may refuse it.
2. **An unsupervised attempt never ends.** It stays `running` for ever, through a
   cancellation as well, because no observation of its end exists. The task view shows
   it as such; nothing counts it.
3. **An imported `awaiting_acceptance` task has no head.** Accepting it records an
   acceptance for head `""` and moves it to `accepted`, which is what the acceptance
   service does for any task without a head. Whether Foundry should accept such a task
   through Crucible or close it is Foundry's call; nothing here prevents either.
4. **The fenced token race is a 500, not a refusal.** A supervisor takeover between the
   guard and the insert of a synthetic attempt rejects the write and the import rolls
   back (decision 9), but the caller sees a server error rather than a
   `supervisor-not-live` problem, because the rejection surfaces as the transaction
   ends. It is the correct outcome with the wrong status.
5. **The `bootstrap` sentinel is a real registration row.** It has no installation and
   no usable URL, so a contract naming it would fail at publication; nothing submits
   against it, but it appears in `GET /v1/repositories` and in the GitHub status's
   repository list.
